# Stage 2：Android 平台基础总结

## 阶段目标

这一阶段的重点不是记住大量 Android API，而是建立一张基本的 **Android 平台地图**。

最终希望达到的状态是：

> 看到一个需求时，能先判断它主要涉及生命周期、进程与 Task、后台运行、权限、存储、系统交互还是版本 / 设备差异，再去寻找具体实现方式。

---

# 1. Android 应用不是普通的 `main()` 程序

Android App 的运行由系统控制。

应用不会简单地：

```text
main()
↓
一直运行
↓
退出
```

而更像：

```text
Android 系统
    ↓
根据用户操作和系统状态
    ↓
创建 / 恢复 / 暂停 / 销毁应用组件
```

因此 Android 开发中的一个基本前提是：

> **应用必须适应系统控制自己的运行状态。**

---

# 2. Activity、Task、进程是不同层次

这几个概念不能混在一起。

```text
进程
└── 承载 App 正在运行的代码和内存

Task
└── 组织一组 Activity 的用户操作历史

Activity
└── 一个可以参与用户界面流程的 Android 组件
```

例如：

```text
Activity A
   ↓
Activity B
   ↓
Activity C
```

它们可以处在同一个 Task 中。

用户按 Back 时，主要涉及的是 **Task 中 Activity 的返回关系**，而不是“进程返回”。

同样：

> Task 被移除，也不等于系统一定在同一瞬间杀死应用进程。

---

# 3. 生命周期本质上是“系统通知你状态发生变化”

Activity 有一套生命周期。

常见状态变化包括：

```text
创建
↓
进入前台
↓
用户可以交互
↓
部分被遮挡
↓
进入后台
↓
销毁
```

生命周期回调不是我们主动决定 Activity 必须经历什么，而是：

> **系统告诉应用：当前运行状态变化了。**

所以开发时应该根据生命周期安排资源获取、释放和状态恢复，而不是假设 Activity 会一直存在。

---

# 4. Activity 重建和进程死亡不是一回事

这是 Stage 2 中很重要的一条。

### Activity 重建

例如配置变化时：

```text
旧 Activity
↓
销毁
↓
创建新的 Activity
```

但应用进程可能仍然活着。

这种情况下 `ViewModel` 通常可以继续存在。

---

### 进程死亡

系统内存紧张时，可以直接杀掉后台应用进程：

```text
Activity
ViewModel
普通 Kotlin 对象
静态变量
……
全部消失
```

用户之后重新回来时：

```text
创建新进程
↓
重新创建 Activity
```

所以：

> **内存中的对象不能被当作可靠的数据保存方式。**

---

# 5. `savedInstanceState` 是“界面恢复”，不是长期存储

`savedInstanceState` 的作用是帮助 Activity **之后重新创建时恢复少量状态**。

它甚至可以跨越一次系统导致的进程死亡：

```text
Activity
↓
保存 instance state
↓
后台进程被系统杀掉
↓
用户返回
↓
建立新进程
↓
重新创建 Activity
↓
恢复 savedInstanceState
```

但它不是数据库。

适合：

```text
输入了一半的文字
当前选中的 Tab
滚动位置
一些小型 UI 状态
```

不适合：

```text
用户创建的重要业务数据
长期保存的登录信息
笔记
订单
真正必须可靠保存的数据
```

一个很好用的区别：

```text
恢复“刚才那个界面”
→ savedInstanceState / rememberSaveable

未来重新打开 App 仍必须存在
→ 持久化存储
```

如果用户把对应 Task 真正移除，例如从 Recents 中划掉，就不能继续把 `savedInstanceState` 当作长期数据恢复机制。

---

# 6. 前台、后台和进程存活是不同概念

应用进入后台以后：

> **不代表进程立刻死亡。**

可能出现：

```text
App 在前台
↓
用户按 Home
↓
App 进入后台
↓
进程仍然存在
↓
过一段时间
↓
系统因为资源需要杀掉进程
```

因此：

```text
后台 ≠ 已死亡
Activity 销毁 ≠ 进程死亡
Task 消失 ≠ 一定立即杀进程
```

这是理解 Android 行为的基础。

---

# 7. Android 的权限建立在应用隔离之上

Android 中，不同 App 默认是互相隔离的。

例如：

> App A 不能直接跑进 App B 的私有目录读取数据库。

所以遇到：

```text
访问相册
定位
相机
其他 App 的数据
系统受保护能力
```

首先应该想到：

> **权限 / 安全隔离。**

而不是先想具体 API。

如果 App B 希望主动把某些数据提供给 App A，就需要通过 Android 提供的跨应用机制进行受控共享，而不是直接暴露整个私有目录。

---

# 8. 存储首先要判断“这个数据属于谁、要活多久”

看到存储需求，可以先问两个问题：

### 谁应该访问？

```text
只有当前 App
→ 应用私有存储

需要与用户或其他 App 共享
→ 共享数据 / 系统提供的访问机制
```

### 要保存多久？

```text
随时可以重新生成
→ cache 可以考虑

App 重启后还要存在
→ 持久化存储

只是 Activity 重建时恢复 UI
→ savedInstanceState 一类
```

特别要记住：

> **cache 不是可靠的数据保存位置。**

系统可以根据需要清理它。

---

# 9. 后台任务不能简单理解成“开个线程继续跑”

现代 Android 会限制后台运行。

看到需求：

> “用户离开 App 以后还要继续做……”

首先应该归类到：

> **后台任务 / 后台运行限制**

然后才判断具体方案。

几个典型思路：

```text
用户明确感知、正在持续执行
例如音乐播放、大文件上传
→ Foreground Service 一类

可以延迟，但最终应该完成
例如后台同步
→ WorkManager 一类

时间点本身非常重要
例如真正的闹钟
→ AlarmManager 一类
```

不要看到“后台”就默认 Service。

---

# 10. App 可以与 Android 系统和其他 App 交互

Android 应用不是孤岛。

典型交互包括：

```text
打开浏览器
分享文字
调用相机
响应系统事件
访问其他应用主动提供的数据
```

其中一个很重要的机制是 **Intent**。

例如：

```text
我要打开一个网页
```

App 不一定需要知道：

```text
Chrome 在哪里
Edge 在哪里
其他浏览器 Activity 是什么
```

而是描述：

> “我想打开这个 URL。”

然后让 Android 找能够处理这个动作的应用。

这就是典型的 **隐式 Intent** 思路。

---

# 11. 系统事件通常属于“系统 → App”

例如：

```text
设备启动完成
网络状态变化
某些系统状态发生变化
```

首先应该想到：

> **系统 / App 交互**

`BroadcastReceiver` 是其中一种经典机制。

但：

> “收到系统事件”与“收到以后允许做什么”是两个问题。

后者还可能受到 **后台运行限制**。

所以一个需求经常同时跨多个平台领域。

---

# 12. Android 版本和设备差异必须当成正常情况

Android 应用并不是运行在一个完全一致的环境里。

可能存在：

```text
Android 版本不同
API Level 不同
设备硬件不同
厂商实现不同
系统行为限制不同
```

几个重要概念：

### `minSdk`

应用最低支持哪个 Android API Level。

### `targetSdk`

应用主要按照哪个版本的 Android 行为规则进行适配。

它不等于最低支持版本。

---

所以出现：

```text
这台手机正常
另一台不正常

Android 14 正常
老系统不正常
```

第一反应应该包括：

> **版本 / 设备环境差异。**

---

# 13. 一个需求通常不只有一个分类

真实需求经常跨多个平台能力。

例如：

> App 在后台上传用户选择的大文件。

可能涉及：

```text
后台运行
+
文件 / 存储
+
权限
+
网络
```

但判断需求时最好先找：

> **哪个平台问题决定这件事首先能不能成立？**

例如：

```text
App 切到后台以后还要持续上传
```

首先是：

> 后台运行问题。

具体文件在哪、权限是什么，是下一层。

---

# 14. 不要从 API 名字倒推需求

Stage 2 后面练习中最容易出现的情况就是：

```text
看到“定时”
→ AlarmManager

看到“后台”
→ Service

看到“系统”
→ BroadcastReceiver

看到“跨 App”
→ ContentProvider
```

这种反应太快了。

正确顺序应该是：

```text
需求
↓
判断平台问题属于哪一类
↓
理解系统约束
↓
再寻找具体 API / Jetpack 组件
```

也就是：

> **先理解问题，再选工具。**

---

# 15. Stage 2 平台地图

最后可以把这一阶段压成这一张图：

```text
Android 平台问题
│
├── App 怎么运行？
│   ├── Activity
│   ├── Task
│   └── 应用进程
│
├── 状态为什么发生变化？
│   ├── 生命周期
│   ├── Activity 重建
│   └── 系统进程回收
│
├── 离开前台还能做什么？
│   └── 后台运行限制
│
├── 我有没有资格访问？
│   └── 权限 / 安全隔离
│
├── 数据放在哪里？
│   ├── 临时状态
│   ├── 私有持久化数据
│   ├── cache
│   └── 共享数据
│
├── 怎么和外部世界交流？
│   ├── Intent
│   ├── Broadcast
│   └── 跨 App 数据共享
│
└── 为什么换台设备行为不一样？
    ├── API Level
    ├── minSdk / targetSdk
    ├── Android 版本差异
    └── 设备 / 厂商差异
```

# Stage 2 最终应该形成的思维方式

以后拿到一个需求，例如：

> App 退到后台后继续播放音乐。

第一反应：

```text
后台运行
↓
用户可感知的持续任务
↓
再考虑 Foreground Service
```

而不是：

```text
Foreground Service！
```

另一个需求：

> 用户旋转屏幕后输入不能丢。

应该先想到：

```text
Activity 重建
↓
生命周期 / 状态恢复
↓
再判断 ViewModel、savedInstanceState 等方案
```

再例如：

> Android 14 正常，Android 10 不正常。

应该先想到：

```text
版本差异
↓
API Level / 行为差异
↓
再查具体 API
```

---

# 阶段完成标准

到这里，不要求背下所有 Android API。

真正需要具备的是：

> **看到一个 Android 需求，大致知道应该去 Android 平台地图的哪一块找答案。**

具体开发时再查官方文档、API、示例和实现方式就可以。

这比提前背大量 API 更重要。
