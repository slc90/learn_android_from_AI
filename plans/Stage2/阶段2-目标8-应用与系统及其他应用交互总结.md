# Stage 2 - 目标 8：应用与 Android 系统、其他应用交互的基本机制

## 目标

理解 Android 应用如何与：

- 自己的其他组件
- Android 系统
- 其他应用

进行基本交互，并能根据需求判断应该使用哪类机制。

---

## 1. Intent：表达“我要做什么”

`Intent` 可以理解成一个请求或意图：

> 我想做某件事。

常见用途：

- 启动 Activity
- 启动 Service
- 发送 Broadcast
- 携带少量参数

### 显式 Intent

明确指定目标组件：

```kotlin
val intent = Intent(this, DetailActivity::class.java)
startActivity(intent)
```

含义：

> 我知道具体要找谁。

### 隐式 Intent

只说明要做什么，不指定具体组件：

```kotlin
val intent = Intent(
    Intent.ACTION_VIEW,
    Uri.parse("https://developer.android.com")
)

startActivity(intent)
```

含义：

> 我要查看这个网址，Android 帮我找能处理它的组件。

隐式 Intent 主要通过下面这些信息参与匹配：

- Action：要做什么
- Data：对什么数据做
- Category：附加使用场景约束

例如：

```text
ACTION_SEND + text/plain
```

表示：

> 分享一段普通文本。

---

## 2. MIME type：描述数据是什么类型

MIME 是：

**Multipurpose Internet Mail Extensions**

现在可以直接把 MIME type 理解成：

> 标准化的数据类型标签。

例如：

```text
text/plain
image/png
image/jpeg
application/pdf
```

基本格式：

```text
大类 / 具体类型
```

例如：

```text
image/png
```

表示 PNG 图片。

在 Intent 中，MIME type 可以帮助 Android 判断哪些组件有能力处理这份数据。

---

## 3. Intent Filter：声明组件能处理什么 Intent

`intent-filter` 是接收方组件的声明：

> 我愿意处理这些类型的 Intent。

例如：

```xml
<intent-filter>
    <action android:name="android.intent.action.SEND" />
    <category android:name="android.intent.category.DEFAULT" />
    <data android:mimeType="text/plain" />
</intent-filter>
```

可以先记成：

```text
Intent
= 请求 / 意图

Intent Filter
= 组件声明自己愿意处理哪些请求
```

注意：

`Intent Filter` 描述的是组件的能力，不是整个 App 的能力列表。

---

## 4. exported：组件是否允许外部 App 进入

```xml
android:exported="true"
```

表示这个组件允许外部应用访问。

可以和 `intent-filter` 分开理解：

```text
intent-filter
= 我能处理什么

exported
= 外部 App 能不能进入
```

如果：

```text
exported = false
```

外部 App 不能直接调用这个组件。

典型的跨 App 隐式 Intent 场景：

```text
intent-filter
+
exported=true
```

如果组件只在自己 App 内部使用，通常直接使用显式 Intent 更简单。

---

## 5. BroadcastReceiver：事件通知机制

`BroadcastReceiver` 可以理解成：

> 某件事发生后，用来接收事件通知的组件。

基本结构：

```text
发送方
  ↓
Intent
  ↓
Android 广播机制
  ↓
一个或多个 BroadcastReceiver
```

与 Activity 的区别：

```text
Activity Intent
→ 通常最终选择一个 Activity

Broadcast
→ 所有满足匹配和访问条件的 Receiver 都可以收到
```

接收广播：

```kotlin
class MyReceiver : BroadcastReceiver() {
    override fun onReceive(
        context: Context,
        intent: Intent
    ) {
        // 处理广播
    }
}
```

`BroadcastReceiver` 更像一个事件入口，不是长期后台任务执行器。

`onReceive()` 应尽快结束。

---

## 6. BroadcastReceiver 中的 Context

```kotlin
override fun onReceive(
    context: Context,
    intent: Intent
)
```

这里两个参数可以这样理解：

```text
intent
= 收到了什么消息

context
= 接收方这一侧的 Android 运行环境入口
```

假设：

```text
App A 发广播
    ↓
Android
    ↓
App B 的 Receiver 收到
```

那么：

```text
intent
→ 发送过来的消息

context
→ App B / Receiver 所处的环境
```

它不是发送方 App 的 Context，也不是 Android 系统自己的 Context。

---

## 7. ContentProvider：受控的数据访问接口

`ContentProvider` 更偏向：

> 把某些结构化数据通过受控接口暴露给其他组件或应用。

整体结构：

```text
App A
  ↓
ContentResolver
  ↓
content:// URI
  ↓
ContentProvider
  ↓
数据
```

可以类比成本机上的 API。

### ContentResolver

调用方使用的统一访问入口：

```kotlin
contentResolver.query(...)
```

### ContentProvider

数据提供方，负责决定：

- URI 代表什么数据
- 是否允许访问
- 数据从哪里读取
- 返回什么结果

### URI

例如：

```text
content://com.example.notes/notes/42
```

粗略拆分：

```text
content://
→ ContentProvider 体系

com.example.notes
→ authority，用于定位 Provider

notes/42
→ 具体资源路径
```

---

## 8. ContentProvider 不等于数据库

Provider 后面可以是：

- SQLite
- Room
- 文件
- 内存
- 其他数据源

所以：

> ContentProvider 是数据访问接口，不是数据存储本身。

它的价值之一就是隐藏底层实现。

---

## 9. 为什么系统联系人使用 ContentProvider

“是不是 Android 系统提供的东西”并不能决定它一定走 Manager。

更重要的是它对外暴露的是什么：

```text
系统能力
→ XxxManager

结构化数据
→ ContentProvider
```

联系人本质上是一套结构化数据，因此 Android 使用：

```text
Contacts Provider
+
ContentResolver
```

来访问联系人。

---

## 10. System Service / Manager：使用 Android 系统能力

很多系统能力通过各种 Manager 暴露给 App，例如：

```text
ConnectivityManager
NotificationManager
ClipboardManager
PowerManager
```

可以理解成：

```text
你的 App
   ↓
Manager API
   ↓
Binder IPC
   ↓
Android System Service
```

其中：

```text
Manager
= App 日常使用的高层 API

System Service
= Android 系统真正实现能力的一方
```

日常 App 开发通常只需要看到 Manager 这一层。

---

## 11. IPC：进程间通信

IPC 是：

**Inter-Process Communication**

即：

> 不同进程之间进行通信。

它不是 Android 独有概念。

Android 中非常重要的一套 IPC 机制是：

**Binder**

关键判断不是：

```text
是不是不同 App
```

而是：

```text
是不是跨了进程边界
```

同一个 App 也可以有多个进程。

---

## 12. Binder：Android 的核心 IPC 机制之一

Binder 可以先理解成：

> Android 本机内部的一套跨进程调用机制。

它经常把跨进程通信包装得像普通方法调用：

```kotlin
service.someMethod()
```

背后可能实际发生：

```text
App 进程
   ↓
Proxy
   ↓
Binder IPC
   ↓
Stub
   ↓
另一个进程里的真正实现
```

其中：

```text
Proxy
= 客户端代理

Stub
= 服务端入口
```

---

## 13. Parcel：Binder 搬运数据时的“包裹”

跨进程不能直接共享普通对象内存，因此需要把参数转换成可以传输的数据。

例如：

```text
add(10, 20)
↓
参数写入 Parcel
↓
Binder 传输
↓
另一边从 Parcel 读取
↓
真正执行 add(10, 20)
```

可以理解成：

```text
Binder
= 负责运送

Parcel
= 运送参数和返回值的数据容器
```

不是所有对象都能直接放进 Parcel。

常见可传数据包括：

- 基本类型
- String
- 数组 / List
- Bundle
- Parcelable 对象
- 一些 Binder 引用

自定义对象通常需要明确说明如何 Parcel 化。

---

## 14. IPC 有性能成本

同进程函数调用：

```text
调用
→ 直接执行
```

Binder 跨进程：

```text
参数打包
→ IPC
→ 进程切换
→ 解包
→ 执行
→ 返回结果
```

因此 IPC 比普通函数调用更贵。

需要避免：

- 高频大量 IPC
- 大量细碎调用
- 通过 Binder 传很大的数据

---

## 15. PendingIntent：把未来执行 Intent 的权利交出去

普通 Intent：

> 现在我要做这件事。

`PendingIntent`：

> 我把“以后替我执行这个 Intent”的权利交给系统或其他组件。

典型流程：

```text
你的 App
  ↓
创建 Intent
  ↓
包装成 PendingIntent
  ↓
交给系统
  ↓
未来某个时机
  ↓
系统替你的 App 执行
```

常见场景：

- 通知点击
- App Widget 点击
- AlarmManager 定时触发

所以：

```text
Intent
= 请求内容

PendingIntent
= 请求内容 + 未来代为执行的授权
```

现代 Android 中创建 PendingIntent 时通常还需要明确：

```text
FLAG_IMMUTABLE
或
FLAG_MUTABLE
```

多数普通场景优先使用不可修改的 `FLAG_IMMUTABLE`。

---

## 16. 最终交互地图

面对一个 Android 需求，可以先问：

```text
我要让某个组件做一件事？
→ Intent

我要通知“某件事发生了”？
→ BroadcastReceiver

我要访问结构化数据？
→ ContentProvider / ContentResolver

我要使用 Android 系统能力？
→ XxxManager / System Service
```

再往下一层：

```text
Intent
ContentProvider
Broadcast
System Service
      ↓
Android Framework
      ↓
很多跨进程场景最终会使用
Binder IPC
```

但日常开发通常停留在 Framework API 这一层即可。

---

## 17. 一句话压缩

```text
动作
→ Intent

事件
→ Broadcast

数据
→ ContentProvider

系统能力
→ Manager

跨进程底层
→ Binder

未来代执行 Intent
→ PendingIntent
```

真正需要掌握的不是死记 API 名字，而是看到需求时能够判断：

> 这是“动作、事件、数据、系统能力”中的哪一种交互问题？

做到这一点，就已经建立起 Android 应用与系统、其他应用交互的基本地图。
