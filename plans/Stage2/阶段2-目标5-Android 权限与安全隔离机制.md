# 阶段 2 - 目标 5：Android 权限与安全隔离机制

## 目标

理解 Android 为什么能够让不同应用彼此隔离，以及应用需要访问受保护的系统能力时，权限机制是怎样参与其中的。

这一目标需要建立的核心模型是：

> **Android 默认先隔离每个 App；当 App 确实需要访问沙箱之外的受保护资源或能力时，再通过权限机制有控制地开放访问。**

---

# 1. 安全隔离是默认状态

Android 并不是：

```text
安装 App
↓
App 默认可以访问整台设备
↓
再通过权限把某些东西禁止掉
```

实际思路正好相反：

```text
安装 App
↓
默认进入自己的隔离环境
↓
只能访问默认允许的资源
↓
需要额外能力时
↓
再通过 Android 的权限机制获得访问
```

因此：

> **隔离是默认规则，权限是在默认隔离之上打开的受控入口。**

即使一个 App 没有申请任何权限，它依然处在 Android 的安全隔离之中。

---

# 2. Android App Sandbox

每个普通 Android App 默认运行在自己的应用沙箱中。

可以先粗略理解成：

```text
Android 系统

├── App A
│   ├── 自己的进程
│   └── 自己的私有数据
│
├── App B
│   ├── 自己的进程
│   └── 自己的私有数据
│
└── 系统管理的受保护能力
    ├── 相机
    ├── 麦克风
    ├── 位置
    ├── 联系人
    └── ...
```

默认情况下：

```text
App A
不能直接读取 App B 的私有数据

App B
也不能直接读取 App A 的私有数据
```

这种隔离并不是要求每个 App 自己写代码保护自己。

真正的安全边界由操作系统强制执行。

---

# 3. UID：App 在 Linux 中的身份

Android 基于 Linux。

安装一个 App 时，系统通常会给它分配一个独立的 Linux UID。

例如：

```text
App A
UID = 10123

App B
UID = 10456
```

UID 可以先理解为：

> **这个 App 的 Linux 身份。**

它和 PID 不是一回事。

```text
UID
→ 你是谁

PID
→ 当前这个运行中的进程是哪一个
```

例如：

```text
App A
UID = 10123

第一次启动：
PID = 4567

进程死亡后重新启动：
PID = 8120

UID 仍然属于 App A
```

所以：

```text
PID
会随着进程创建和销毁变化

UID
用于标识 App 所使用的系统身份
```

一个 App 即使存在多个进程，不同进程也可以使用同一个 App UID。

---

# 4. UID 是安装环境中的身份，不是全球固定编号

UID 不是写死在 APK 中的永久身份证。

例如同一个 App：

```text
设备 A：
UID = 10123

设备 B：
UID = 10582
```

完全正常。

因此更准确地理解是：

```text
某个 App
+
当前设备
+
当前 Android 用户 / Profile
+
当前安装环境
↓
系统为它分配 UID
```

App 被关闭、进程被杀死再重新启动，并不会因此重新随机分配一个 UID。

---

# 5. Linux 根据 UID 执行访问控制

UID 本身只是身份。

真正使用这个身份进行限制的是 Linux 的访问控制机制。

例如：

```text
App A
UID = 10123

A 的私有文件
属于 UID 10123
```

App B：

```text
UID = 10456
```

如果 App B 试图直接打开 App A 的私有文件：

```text
App B
↓
访问 App A 私有文件
↓
Linux 检查身份和访问权限
↓
UID / 权限不允许
↓
拒绝访问
```

因此：

```text
UID
→ 表示身份

Linux 文件 / 进程访问控制
→ 根据身份判断允许做什么
```

---

# 6. App 私有数据属于沙箱的一部分

App 自己的内部存储属于自己的应用沙箱。

可以粗略理解成：

```text
App A
UID 10123
│
└── 私有数据
    ├── 文件
    ├── 数据库
    └── 其他内部数据
```

普通情况下：

```text
App A → 自己的数据 ✅

App B → App A 的私有数据 ❌
```

这里通常不会出现：

```text
“是否允许 App B 读取 App A 的 user.txt？”
```

这样的用户权限弹窗。

因为这是**应用沙箱本身的隔离问题**，不是运行时权限问题。

Android 的文件系统和共享存储会在阶段 2 目标 6 中继续学习。

---

# 7. SELinux：额外的一层强制安全策略

Android 不只依赖普通 Linux UID 和文件权限。

系统还大量使用：

```text
SELinux
```

SELinux 可以先理解为：

> **在普通 Linux 权限之上，再增加一层由系统强制执行的安全规则。**

大致模型：

```text
App 发起操作
    ↓
Linux 身份 / 普通访问控制
    ↓
SELinux 安全策略
    ↓
满足系统规则
    ↓
允许
```

因此 Android 的应用隔离不是单纯依赖某一个 `if` 或某个 Java / Kotlin API。

它的关键安全边界位于操作系统和内核层。

---

# 8. Native C++ 代码同样受到沙箱限制

因为应用沙箱是在系统层执行的：

```text
Kotlin / Java 代码
        │
        ├── 都运行在 App 的安全环境中
        │
C++ Native 代码
```

进入 Native 层并不会自动获得：

```text
root 权限
绕过 UID
绕过 SELinux
任意读取其他 App 数据
```

所以以后阶段 5 使用 Android NDK 和 C++ 时，Native 代码依然受到 Android 应用沙箱约束。

---

# 9. 为什么已经有沙箱，还需要权限

沙箱解决的是：

> **App 默认能够访问什么？**

权限解决的是：

> **App 在什么条件下可以额外访问某些受保护资源或能力？**

例如录音 App：

```text
App 自己的 UI          ✅
App 自己的私有文件    ✅

使用麦克风            默认受到限制
```

因此需要权限机制。

这里访问的不一定是所谓的“公共资源”。

很多东西实际上非常敏感，例如：

```text
麦克风
相机
位置
联系人
```

更准确的说法是：

> **沙箱之外、由 Android 系统保护的数据或能力。**

---

# 10. 权限不是解除沙箱

获得一个权限，并不是：

```text
App 获得权限
↓
沙箱消失
↓
App 可以随便访问系统
```

而是：

```text
App 仍然处在沙箱中
        ↓
Android 针对某一种具体能力
开放一个受控制的入口
```

例如：

```text
获得 CAMERA 权限

只代表：
允许在规定条件下使用相机

不代表：
可以读取别的 App 私有文件
可以读取联系人
可以使用麦克风
```

因此：

> **权限是能力级别的授权，不是整个 App 沙箱的解除。**

---

# 11. AndroidManifest.xml 中的权限声明

如果 App 的功能需要某项权限，通常需要先在 `AndroidManifest.xml` 中声明。

例如：

```xml
<uses-permission android:name="android.permission.CAMERA" />
```

这个声明可以理解成：

> **这个 App 的功能设计中可能需要使用相机能力。**

它并不意味着：

```text
Manifest 写了 CAMERA
↓
系统立即把相机权限永久交给 App
```

Manifest 声明和用户授权是两个不同层次的问题。

---

# 12. Manifest 声明与运行时授权

对于某些敏感权限：

```text
Manifest 中声明
        ↓
App 运行
        ↓
用户真正执行需要该能力的操作
        ↓
检查当前权限状态
        ↓
没有权限
        ↓
向系统请求
        ↓
用户决定允许 / 拒绝
```

因此可以先这样理解：

```text
Manifest：

“我的 App 可能需要这个能力。”
```

而运行时授权：

```text
“用户现在是否允许这个 App 使用这个能力？”
```

两者不能混为一件事。

---

# 13. Normal Permission

一些风险较低的权限属于普通权限。

例如：

```text
INTERNET
```

App 在 Manifest 中声明后，通常不需要专门向用户弹一个运行时授权框。

可以粗略理解成：

```text
风险较低
↓
Manifest 声明
↓
系统自动授予
```

这类权限称为：

```text
normal permission
```

---

# 14. Runtime / Dangerous Permission

涉及敏感数据或敏感设备能力的权限，通常需要运行时让用户决定。

例如：

```text
CAMERA
RECORD_AUDIO
某些位置权限
```

基本过程：

```text
Manifest 声明
        ↓
App 真正需要该功能
        ↓
检查权限
        ↓
无权限
        ↓
请求权限
        ↓
系统显示授权界面
        ↓
用户允许 / 拒绝
```

这类权限在当前学习阶段最重要。

---

# 15. 为什么不是所有权限都弹窗

如果所有能力都必须运行时询问：

```text
联网？
允许。

震动？
允许。

普通系统能力？
允许。

相机？
允许。

麦克风？
允许。
```

用户很快就只会机械地点：

```text
允许
允许
允许
允许
……
```

权限机制反而失去意义。

因此 Android 会根据能力的风险采用不同授权方式。

可以先粗略理解成：

```text
风险较低
→ normal permission
→ 通常自动授予

涉及敏感数据 / 能力
→ runtime / dangerous permission
→ 用户运行时决定
```

---

# 16. 其他权限类型

Android 还有其他权限类型。

当前阶段只需要知道它们存在。

## Signature Permission

某些能力只允许具有特定签名关系的 App 使用。

可以粗略理解成：

```text
App A
提供某项能力

App B
和 A 满足签名要求
→ 允许

App C
不满足签名要求
→ 拒绝
```

它更多和 App 身份以及 App 间受控交互有关。

当前暂不深入。

---

## Special Permission

还有一些能力特别强，不适合放进普通的运行时权限模型。

例如某些：

```text
特殊系统能力
特殊文件访问能力
悬浮显示能力
```

系统可能要求用户在：

```text
Special app access
```

之类的设置页面中单独授权。

当前只需要知道这种机制存在，真正遇到时再学习。

---

# 17. 当前最重要的权限分类

现阶段可以按下面的权重理解：

```text
normal
★★★
必须理解

runtime / dangerous
★★★
必须理解

special
★
知道存在

signature
★
知道存在
```

对于普通 Android App 开发，当前最常需要考虑的是：

```text
normal
+
runtime / dangerous
```

---

# 18. 权限是一种动态系统状态

权限不是：

```text
用户授权一次
↓
App 永远拥有
```

用户可以之后进入系统设置撤销权限。

系统在某些情况下也可能对权限状态进行调整或重置。

因此：

```text
昨天有权限
≠
今天一定有权限

刚才有权限
≠
以后永远有权限
```

更好的理解是：

> **权限表示系统此刻是否允许当前 App 使用某项能力。**

---

# 19. 不同授权方式的持续时间也可能不同

权限并不存在一个统一的：

```text
有效期 = 24 小时
```

不同权限和授权方式可能具有不同生命周期。

例如某些敏感权限可以出现：

```text
仅限这一次
```

这种授权不会像长期授权一样永久保持。

因此 App 不应该自己假设：

```kotlin
hasPermission = true
```

然后长期相信这个变量。

真正的权限状态由 Android 系统维护。

---

# 20. App 可以查询自己当前是否拥有权限

App 并不是完全不知道自己的权限状态。

Android 提供 API，可以询问系统：

```text
“我现在有没有 CAMERA 权限？”
```

系统返回的核心结果可以理解为：

```text
GRANTED
或
DENIED
```

因此权限状态应该来自系统，而不是 App 自己维护一个永久记录。

具体 Kotlin / Compose 权限代码暂时不在目标 5 深入。

以后真正实现相机、麦克风等功能时再学习具体写法。

---

# 21. 权限检查应该靠近真正的能力边界

不能只在：

```text
App 启动时
```

检查一次权限。

例如：

```text
进入拍照页面
↓
有 CAMERA 权限
↓
用户切到设置
↓
关闭 CAMERA 权限
↓
重新回到 App
```

之前的判断已经可能失效。

因此概念上更合理的是：

```text
准备真正使用相机
↓
确认当前 CAMERA 权限
↓
有权限
→ 执行

没权限
→ 请求权限 / 功能降级
```

所谓“集中处理权限”，不是：

```text
进入页面检查一次然后永久相信
```

而是：

> **在真正准备跨越权限边界的功能入口附近统一处理。**

具体代码组织以后再展开。

---

# 22. App 的权限检查不是最终安全防线

App 自己检查：

```text
我有没有权限？
```

主要是为了：

```text
正确控制业务流程
给用户合理反馈
避免功能直接失败
```

真正的安全边界仍然由 Android 系统执行。

所以：

```text
App 忘记写权限判断
```

并不意味着：

```text
Android 就会放它过去
```

系统仍然会在受保护能力的实际访问过程中执行自己的安全检查。

因此：

```text
App 自己检查权限
→ 为了正确程序行为和 UX

Android 系统检查权限
→ 真正的安全保证
```

---

# 23. 最小权限原则

App 应该只申请真正需要的权限。

例如一个只做普通文本笔记的 App，没有理由申请：

```text
相机
麦克风
联系人
位置
```

因此应该遵循：

> **完成当前功能需要什么，就申请什么；不需要的权限不要申请。**

这样既减少安全风险，也让用户更容易理解 App 为什么需要某项能力。

---

# 24. 权限被拒绝时应能够降级

用户不给某项权限，并不应该意味着整个 App 无法使用。

例如聊天 App：

```text
没有麦克风权限

文字聊天        ✅
查看历史消息    ✅
其他普通功能    ✅
语音消息        ❌
```

而不是：

```text
麦克风权限被拒绝
↓
整个 App 无法运行
```

因此权限设计需要考虑：

```text
授权
→ 使用完整功能

拒绝
→ 相关功能不可用
→ 其他功能继续工作
```

---

# 25. Android 权限系统不等于“权限弹窗”

这是一个容易误解的地方。

权限系统真正解决的是：

> **什么身份，在什么条件下，可以访问什么能力。**

权限弹窗只是其中一种机制。

例如：

```text
normal
→ 通常没有运行时弹窗

runtime
→ 用户运行时决定

signature
→ 根据 App 身份 / 签名关系

special
→ 可能由专门系统设置管理
```

所以不能简单理解成：

```text
Android 权限
=
弹窗问用户
```

# 26. Android 安全模型的整体关系

目前可以建立这样一张图：

```text
Android App
    │
    ├── UID
    │    ↓
    │  Linux 身份
    │
    ├── Linux 访问控制
    │    ↓
    │  限制文件 / 进程等访问
    │
    ├── SELinux
    │    ↓
    │  强制安全策略
    │
    └── App Sandbox
         ↓
       默认隔离
         ↓
       Permission
         ↓
       在规定条件下
       开放特定受保护能力
```

因此：

> **UID / 沙箱负责建立默认安全边界；权限负责控制哪些额外能力可以在什么条件下开放。**

# 28. 最终模型

目标 5 可以压缩成：

```text
安装 App
    ↓
系统分配应用身份（UID）
    ↓
App 进入自己的 Sandbox
    ↓
Linux 访问控制 + SELinux
强制建立安全边界
    ↓
App 默认只能访问允许的内容
    ↓
需要沙箱之外的受保护能力
    ↓
Manifest 声明需求
    ↓
Android 根据权限类型决定授权方式
    │
    ├── normal
    │    ↓
    │  通常自动授予
    │
    ├── runtime / dangerous
    │    ↓
    │  用户运行时决定
    │
    ├── signature
    │    ↓
    │  根据签名身份控制
    │
    └── special
         ↓
       特殊机制管理
    ↓
获得某项具体能力
    ↓
App 仍然处于 Sandbox 中
```

最重要的一点是：

```text
获得权限
≠
解除沙箱

而是：

在沙箱仍然存在的前提下
获得某项受控制的额外能力
```

# 29. 本目标需要记住的结论

1. **Android App 默认就处于安全隔离中，不申请权限也一样存在沙箱。**
2. **普通 App 通常拥有独立的 Linux UID，UID 表示它在系统中的身份。**
3. **PID 标识具体进程，UID 标识运行身份；进程重新创建时 PID 可以改变，而 App 的 UID 不会因为普通进程重启而改变。**
4. **Linux 访问控制利用 UID 等身份信息限制文件和进程访问。**
5. **Android 还使用 SELinux 提供额外的强制安全策略。**
6. **Native C++ 代码同样受到 Android 应用沙箱约束。**
7. **权限不是解除沙箱，而是在沙箱基础上开放特定受保护能力。**
8. **Manifest 权限声明与用户运行时授权不是一回事。**
9. **当前最重要的权限类型是 normal 和 runtime / dangerous。**
10. **权限状态由系统管理，用户可以撤销，因此不能把曾经授权当成永久事实。**
11. **App 应在真正需要受保护能力时确认当前权限状态。**
12. **App 自己检查权限主要负责程序流程；真正的安全边界仍然由 Android 系统强制执行。**
13. **应该遵循最小权限原则，并在用户拒绝权限时让功能合理降级。**
14. **App 间组件权限留到目标 8，文件与共享存储留到目标 6。**
