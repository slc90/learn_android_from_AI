# 阶段 2 - 目标 4：应用前台、后台与系统回收

## 目标

理解 Android 应用在前台、后台以及被系统回收时的行为，并能够区分：

* Task 的前台与后台
* Activity 的生命周期状态
* 应用 Process 是否仍然存在
* Service 等其他组件是否仍然运行

核心原则是：

> **应用界面不可见，不等于应用进程已经死亡。**

---

# 1. Task、Activity、Process 是三个不同层次

Android 中可以先建立下面这层关系：

```text
Task
  ↓ 包含
Activity
  ↓ 运行在
Process
```

三者有关联，但不能混为一个“App 状态”。

## Task

Task 表示用户正在进行的一组界面操作，是一组 Activity 的返回栈。

例如：

```text
Task
┌─────────────────┐
│ DetailActivity  │ ← 栈顶
│ MainActivity    │
└─────────────────┘
```

Task 可以：

* 位于前台
* 进入后台
* 再次回到前台
* 被用户从最近任务中移除

---

## Activity

Activity 有自己的生命周期，例如：

```text
RESUMED
   ↓
PAUSED
   ↓
STOPPED
```

Activity 是否可见、是否可以交互，由它自己的生命周期状态描述。

Task 进入后台时，栈顶 Activity 通常也会进入 `STOPPED`。

但是：

```text
Activity STOPPED
≠
Activity 对象已经消失
≠
Process 已经死亡
```

---

## Process

Process 是实际承载应用代码和内存对象的运行环境。

其中可能包含：

```text
Process
├── Activity 对象
├── Application 对象
├── Service
├── singleton
├── 普通 Kotlin 对象
└── 各种内存变量
```

Activity 进入后台后，Process 通常仍然可以继续存在。

只有 Process 真正被系统结束后，这些内存对象才会全部消失。

---

# 2. 应用进入后台不等于进程死亡

假设 `MainActivity` 当前正在前台：

```text
MainActivity
RESUMED
```

用户按 Home：

```text
onPause()
↓
onStop()
```

此时通常变成：

```text
Task：后台

MainActivity：STOPPED

Process：仍然存在
```

因此如果用户马上回来：

```text
onRestart()
↓
onStart()
↓
onResume()
```

Android 很可能继续使用原来的 Activity 对象。

这也是 Android 保留后台进程的重要原因之一：

```text
用户暂时离开
↓
Process 暂时保留
↓
用户很快回来
↓
避免重新启动整个应用
```

这样恢复速度更快。

---

# 3. Home 和 Back 的区别

## Home

Home 的主要含义是：

> 暂时离开当前 Task。

典型结果：

```text
Task
前台 → 后台

Activity
RESUMED
↓
PAUSED
↓
STOPPED

Process
通常继续存在
```

Task 仍然保留，因此之后可以从最近任务重新回到它。

---

## Back

普通情况下，Back 表示退出当前 Activity。

例如：

```text
Task
┌──────────────┐
│ Detail       │ ← 当前
│ Main         │
└──────────────┘
```

按 Back：

```text
Detail
↓
finish
↓
从 Back Stack 移除
```

然后：

```text
Task
┌──────────────┐
│ Main         │ ← 重新显示
└──────────────┘
```

所以可以先记成：

```text
Home
→ Task 进入后台
→ Activity 通常只是 STOPPED

Back
→ 当前 Activity 通常从返回栈中移除
```

Android 12 及以上，对于 launcher Task 的根 Activity，Back 的默认行为有所变化：通常会把 Task 放到后台，而不是直接销毁根 Activity。

因此不能简单记成：

```text
Back = 一定 onDestroy()
```

---

# 4. 最近任务中上划移除

从最近任务中把应用上划移除，主要影响的是：

```text
Task
```

即：

```text
最近任务上划
↓
Task 被移除
↓
用户无法再通过最近任务恢复这个 Task
```

因此原来那套 Activity Back Stack 也不再作为这个 Task 等待用户返回。

但是：

```text
Task 被移除
≠
Process 必然立即死亡
```

Process 中还可能存在其他组件，例如 Service。

所以需要分别判断：

```text
Task 是否还存在？
Activity 是否还能通过这个 Task 返回？
Process 是否仍然存在？
其他组件是否仍然工作？
```

---

# 5. Service 与 Task 是独立的

Task 被移除以后，某些 Service 仍然可能继续运行。

例如音乐播放：

```text
Activity / Task
已经不在最近任务

但：

Foreground Service
仍然播放音乐
```

这不是“僵尸进程”。

Service 是 Android 明确管理的组件。

---

## 普通后台 Service

现代 Android 对后台 Service 有很强的运行限制。

应用进入后台后，普通 Service 不能任意长期运行。

---

## Foreground Service

如果应用确实需要在没有 Activity 的情况下继续执行用户可感知的任务，可以使用 Foreground Service。

典型场景：

* 音乐播放
* 导航
* 运动记录
* 某些长时间设备操作

可以理解为：

```text
Activity 不可见
        ↓
Foreground Service
仍然有明确工作
        ↓
系统继续管理
        ↓
用户也能感知它正在运行
```

因此：

> **Process 还活着，不代表代码可以在后台无限制运行。**

---

# 6. Cached Process

如果应用：

```text
没有前台 Activity
没有重要 Service
没有其他需要保持活跃的组件
```

Process 可能成为 cached process。

它存在的主要价值是：

```text
用户可能很快回来
↓
先把进程保留在 RAM
↓
回来时恢复更快
```

但 cached process 只是缓存。

系统不保证它继续存在。

---

# 7. Process Importance

Android 会根据 Process 当前承载的组件判断它的重要程度。

可以粗略理解成：

```text
Foreground Process
        ↓
Visible Process
        ↓
Service Process
        ↓
Cached Process
```

越靠下：

```text
对当前用户越不重要
↓
越容易在内存不足时被回收
```

一个 Process 的重要程度不是永久固定的。

例如：

```text
MainActivity RESUMED
↓
Process 很重要
```

按 Home：

```text
MainActivity STOPPED
↓
Process 重要性下降
```

如果此时又有 Foreground Service：

```text
Foreground Service
↓
Process 重要性重新提高
```

因此 Android 判断的不是简单的：

```text
这个 App 是前台还是后台？
```

而更接近：

```text
这个 Process 当前有哪些组件？
↓
这些组件现在对用户有多重要？
```

---

# 8. Process 存活和后台执行是两个问题

这是一个非常重要的区别：

```text
Process 仍然存在
≠
应用可以继续任意执行代码
```

Android 实际上分别考虑两个问题。

## Process 是否继续保留

取决于：

* 当前组件的重要程度
* 用户是否可能很快回来
* 系统当前内存压力

## App 是否允许继续后台工作

则取决于：

* 是否存在前台 Activity
* 是否存在合法 Service
* 是否使用 Foreground Service
* 是否使用系统认可的后台任务机制

因此完全可能出现：

```text
Process：仍然存在

但：

应用基本没有继续执行代码
```

---

# 9. 系统回收 Process

如果应用进入后台，Process 的重要程度下降，同时系统又需要内存：

```text
后台 Process
↓
系统内存压力增加
↓
Process 被系统结束
```

这时：

```text
Activity 对象      ×
Application 对象   ×
singleton          ×
普通 Kotlin 对象   ×
内存变量           ×
```

整个进程中的内存状态都会消失。

---

# 10. Process 被杀时不保证 onDestroy()

不能认为：

```text
系统准备杀进程
↓
onDestroy()
↓
保存数据
↓
Process 死亡
```

Android 不提供这样的保证。

实际情况可能只是：

```text
Activity 已经 STOPPED

……过了一段时间……

Process
×
```

系统可以直接结束 Process。

因此：

```kotlin
override fun onDestroy() {
    saveImportantData()
}
```

不能作为重要数据的可靠保存机制。

`onDestroy()` 是 Activity 生命周期回调，不是“系统准备杀进程”的通知。

---

# 11. ProcessLifecycleOwner

`ProcessLifecycleOwner` 是 Jetpack Lifecycle 提供的一个工具。

它可以从整个应用的 Activity 状态推导：

```text
整个应用进入前台

或者

整个应用进入后台
```

例如：

```kotlin
ProcessLifecycleOwner.get().lifecycle
```

可以观察类似：

```text
ON_START
→ App 整体进入前台

ON_STOP
→ App 整体进入后台
```

但是它不是操作系统的 Process 管理器。

特别是：

```text
ProcessLifecycleOwner
不会提供可靠的 ON_DESTROY
```

因为 Process 真正被系统杀死时：

```text
Process
×
```

应用代码本身已经没有执行机会。

因此它不能用于：

```text
“进程马上要死了，赶快保存数据”
```

---

# 12. Process 死亡以后 Activity 如何恢复

假设：

```text
Task
┌────────────────┐
│ DetailActivity │
│ MainActivity   │
└────────────────┘
```

Task 进入后台以后，Android 可以保存一些用于 Activity 重建的状态。

Activity 也可以通过：

```kotlin
onSaveInstanceState(outState: Bundle)
```

保存适合恢复的临时界面状态。

之后：

```text
旧 Process
×
```

旧 Activity 对象已经彻底不存在。

用户之后重新回来时：

```text
新的 Process
↓
新的 Application
↓
新的 Activity
↓
onCreate(savedInstanceState)
```

Android 可以利用之前保存的信息恢复界面。

所以：

> **恢复 Activity，不是让旧 Activity 对象复活。**

而是：

```text
旧对象保存状态
↓
旧对象死亡
↓
创建新对象
↓
恢复之前的状态
```

---

# 13. savedInstanceState 和持久数据不是一回事

`savedInstanceState` 主要用于 Activity 重建所需的临时界面状态。

适合：

```text
当前选中的 Tab
输入框临时内容
滚动位置
某些 UI 状态
```

不适合：

```text
用户账号
正式保存的笔记
订单
聊天记录
长期业务数据
```

后者应该保存到真正的持久化存储中。

因此需要区分：

```text
实例状态
│
└── 为 Activity 重建服务


持久数据
│
└── App 真正拥有的数据
```

---

# 14. 常见用户操作对三层结构的影响

## Home

```text
Task
→ 后台

Activity
→ 通常 STOPPED

Process
→ 通常仍然存在
```

---

## Back

```text
Task
→ Back Stack pop

当前 Activity
→ 通常 finish

Process
→ 通常仍然存在
```

---

## 最近任务切换

```text
不同 Task
→ 在前台和后台之间切换
```

相应 Activity 生命周期随之发生变化。

---

## 最近任务上划

```text
Task
→ 被移除

原来的 Activity Back Stack
→ 无法再通过该 Task 恢复

Process
→ 不应该简单认为一定立即死亡
```

---

## 点击桌面图标

可能：

```text
恢复已有 Task
```

也可能：

```text
创建 / 启动新的 Task
```

具体行为取决于当前 Task 状态以及 Activity 的启动配置。

---

## 通知、Deep Link、快捷方式

也可以成为 Activity 的入口。

因此：

> Activity 并不一定只通过“点桌面图标”进入。

不同入口也可能影响 Task 和 Back Stack 的组织。

---

## Force Stop

设置中的“强行停止”属于比 Home、Back、Recents 更强的操作。

它不是普通的 Activity 导航行为，而是系统层面对整个应用包运行状态的停止操作。

# 16. 最终模型

可以把整个目标压缩成：

```text
用户正在使用 Activity
        ↓
Foreground / Visible Process
        ↓
用户离开
        ↓
Activity STOPPED
        ↓
Process 重要性降低
        ↓
可能成为 Cached Process
        │
        ├── 内存充足
        │      ↓
        │   Process 继续保留
        │      ↓
        │   用户回来
        │      ↓
        │   原 Activity 对象可能继续使用
        │
        └── 系统需要内存
               ↓
          Process 被结束
               ↓
          所有内存对象消失
               ↓
          用户之后重新回来
               ↓
          创建新 Process
               ↓
          创建新 Activity
               ↓
          根据保存状态恢复界面
```

Android 最终判断的是：

```text
当前 Process 有哪些组件？
        +
这些组件对用户现在有多重要？
        +
系统当前资源是否紧张？
```

而不是简单的：

```text
App 在前台？
还是后台？
```

---

# 17. 本目标需要记住的结论

1. **后台不等于 Process 已经死亡。**
2. **Activity、Task、Process 是三个不同层次。**
3. **Activity STOPPED 后，旧 Activity 对象仍然可能存在。**
4. **Process 是否存在，和应用是否允许继续后台工作，是两个问题。**
5. **Task 被移除，不等于 Process 必然立即死亡。**
6. **系统可以在不调用 `onDestroy()` 的情况下结束 Process。**
7. **Process 死亡意味着所有普通内存状态全部消失。**
8. **用户之后看到的 Activity 可能是重新创建的新对象，而不是旧对象恢复执行。**
9. **`savedInstanceState` 用于重建临时界面状态，不应该代替真正的数据持久化。**
10. **Android 根据组件当前对用户的重要程度动态决定 Process 的重要性和回收优先级。**
