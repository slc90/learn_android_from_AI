# Stage 6 · 目标 4：真实设备上的权限、系统限制和运行环境

## 这一目标学到了什么

这一节的核心不是“会申请权限”本身，而是建立下面这个判断模型：

```text
App 想做某件事
    ↓
Manifest 是否声明？
    ↓
当前权限是否已经获得？
    ↓
系统当前是否允许？
    ↓
设备/硬件当前是否可用？
    ↓
功能才真正执行
```

最重要的一句话：

> **有权限，不等于当前一定能执行。**

---

## 1. Android 权限的基本分类

### normal

`normal` 是一种权限保护级别。

特点：

- 风险较低
- 在 Manifest 中声明即可
- 不需要运行时向用户弹权限框

例如：

```xml
<uses-permission android:name="android.permission.INTERNET" />
```

这里 `<uses-permission>` 只是表示“这个 App 需要这个权限”。

---

### dangerous / 运行时权限

这类权限除了 Manifest 声明以外，还需要在运行时向用户申请。

例如：

```xml
<uses-permission android:name="android.permission.CAMERA" />
```

仅仅写到 Manifest 中，并不会自动弹出权限框，也不代表已经获得权限。

完整流程：

```text
Manifest 声明
    ↓
运行时检查
    ↓
没有权限
    ↓
必要时解释原因
    ↓
发起系统权限请求
    ↓
用户允许 / 拒绝
    ↓
App 接收结果
```

---

### signature

`signature` 不是某个具体权限，而是一种授权规则。

例如：

```xml
<permission
    android:name="com.example.SECRET"
    android:protectionLevel="signature" />
```

这里：

```text
android:name
→ 权限的名字

android:protectionLevel="signature"
→ 这个权限采用“签名匹配才授予”的规则
```

App 本身的数字签名发生在 APK 构建/签名流程中，不是在这里完成的。

如果两个 App 使用满足要求的同一签名证书，系统就可以允许它们通过这种权限进行受保护的交互。

这一部分当前只建立概念，不继续深入。

---

## 2. `<permission>` 和 `<uses-permission>` 的区别

### 定义权限

```xml
<permission
    android:name="com.example.SECRET"
    android:protectionLevel="signature" />
```

表示：

> 我定义一个叫 `com.example.SECRET` 的权限。

---

### 请求已有权限

```xml
<uses-permission android:name="android.permission.CAMERA" />
```

表示：

> 我的 App 想使用这个已经存在的权限。

因此，仅从：

```xml
<uses-permission android:name="..." />
```

一般看不出它属于 `normal`、`dangerous` 还是其他类型，需要查对应权限的官方定义。

---

## 3. Camera 运行时权限实验

### Manifest

加入：

```xml
<uses-permission android:name="android.permission.CAMERA" />
```

同时 Android Studio 提示相机硬件声明，可以加入：

```xml
<uses-feature
    android:name="android.hardware.camera"
    android:required="false" />
```

含义：

> App 可能使用相机，但没有相机也仍然可以安装和运行。

---

## 4. 使用 Activity Result API 请求权限

注册权限请求：

```kotlin
val cameraPermissionLauncher =
    registerForActivityResult(
        ActivityResultContracts.RequestPermission()
    ) { granted ->
        println("camera permission granted = $granted")
    }
```

请求：

```kotlin
cameraPermissionLauncher.launch(
    Manifest.permission.CAMERA
)
```

实际观察：

```text
拒绝
→ granted = false

允许
→ granted = true
```

当权限已经允许以后，再次请求时系统不会重复询问，通常直接得到当前结果。

---

## 5. “仅在使用此应用时允许”

实际观察到：

```text
仅在使用此应用时允许
→ 当前权限状态仍然是 GRANTED
```

因此：

```kotlin
granted == true
```

只表示：

> **当前这一刻可以使用这个权限。**

它并不能告诉 App 用户具体选择的是哪一种系统授权策略。

---

## 6. 主动检查当前权限

加入：

```kotlin
val permissionStatus =
    ContextCompat.checkSelfPermission(
        this@MainActivity,
        Manifest.permission.CAMERA
    )

if (permissionStatus == PackageManager.PERMISSION_GRANTED) {
    println("camera permission already granted")
} else {
    println("camera permission not granted, requesting...")

    cameraPermissionLauncher.launch(
        Manifest.permission.CAMERA
    )
}
```

流程变成：

```text
点按钮
    ↓
checkSelfPermission()
    ↓
已经允许？
 ┌──┴──┐
是     否
↓       ↓
直接用  请求权限
```

### Compose 中 `this` 的一个坑

在 `Column {}` 内部直接写：

```kotlin
this
```

这里的 `this` 可能是 `ColumnScope`，并不是 `Context`。

因此要明确写：

```kotlin
this@MainActivity
```

## 7. shouldShowRequestPermissionRationale()

加入：

```kotlin
val shouldShowRationale =
    ActivityCompat.shouldShowRequestPermissionRationale(
        this@MainActivity,
        Manifest.permission.CAMERA
    )
```

实际观察：

```text
第一次请求前
→ false

第一次拒绝后，再次请求前
→ true
```

它表达的是：

> **现在是否适合先向用户解释一下，为什么还需要这个权限。**

它不是“权限是否已经允许”的判断，也不能简单当成“永久拒绝”的判断。

---

## 8. 自己显示解释 UI

当：

```kotlin
shouldShowRationale == true
```

时，可以先显示 App 自己的 `AlertDialog`：

```kotlin
if (showCameraRationale) {
    AlertDialog(
        onDismissRequest = {
            showCameraRationale = false
        },
        title = {
            Text("需要相机权限")
        },
        text = {
            Text("这个功能需要使用相机权限。")
        },
        confirmButton = {
            Button(
                onClick = {
                    showCameraRationale = false

                    cameraPermissionLauncher.launch(
                        Manifest.permission.CAMERA
                    )
                }
            ) {
                Text("继续申请")
            }
        }
    )
}
```

于是流程变成：

```text
用户之前拒绝过
    ↓
App 自己解释原因
    ↓
用户选择继续
    ↓
再弹 Android 系统权限框
```

这里要区分：

```text
AlertDialog
→ App 自己画的 UI

系统权限框
→ Android 系统提供
```

## 9. Special Permission

Special permission 不完全等同于 `normal` / `dangerous` 这种 `protectionLevel`。

它更像 Android 为一些特殊能力设计的独立授权流程。

本次实验使用：

```xml
<uses-permission
    android:name="android.permission.SYSTEM_ALERT_WINDOW" />
```

也就是：

> 显示在其他应用的上层。

检查方式：

```kotlin
Settings.canDrawOverlays(this@MainActivity)
```

如果没有：

```kotlin
val intent =
    Intent(Settings.ACTION_MANAGE_OVERLAY_PERMISSION)

startActivity(intent)
```

实际观察：

```text
第一次
→ canDrawOverlays = false
→ 跳转到系统设置
→ 用户手动开启“显示在其他应用的上层”

之后
→ canDrawOverlays = true
→ 不再跳转设置
```

它与普通运行时权限的区别非常明显：

```text
CAMERA
→ App 内弹系统权限框

SYSTEM_ALERT_WINDOW
→ 跳系统设置页面
→ 用户在那里手动开启
```

## 10. 系统运行限制实验

最后用 Camera2 做了一个很直观的实验。

即使：

```text
CAMERA permission = GRANTED
```

如果 App 已经退到后台，系统仍然可能禁止访问相机。

实验中，前台可以正常打开相机；退到后台后再次尝试，Logcat 出现：

```text
CameraAccessException: CAMERA_DISABLED
Camera "0" disabled by policy
```

同时回调：

```text
camera open error = 3
```

这里说明：

> 系统不是说“你没有 CAMERA 权限”，而是在说“当前运行状态下，系统策略禁止你访问相机”。

因此：

```text
权限允许
≠
当前一定能执行
```

更完整的模型应该是：

```text
Manifest 声明正确
+
权限已经获得
+
当前前后台状态允许
+
系统策略允许
+
设备/硬件状态允许
        ↓
功能才能真正执行
```

---

# 这一目标最终应该记住什么

1. **Manifest 声明和真正获得权限是两回事。**

2. **运行时权限的基本流程是：**

```text
检查
→ 必要时解释
→ 请求
→ 处理结果
```

3. **Special permission 可能走完全不同的授权流程，例如跳系统设置页。**

4. **权限只是“资格”，不是“执行保证”。**

Android 真机环境中，系统策略、前后台状态、硬件状态都可能继续限制功能。
