# Stage 6 - 目标 2 总结：理解模拟器与真机环境之间的主要差异

## 目标

理解 Android Emulator 与真实设备之间的主要差异，并知道哪些问题适合在模拟器中验证，哪些问题必须依赖真实设备。

本阶段的真实目标设备固定为：

- 设备：Redmi K40
- 系统：Xiaomi HyperOS 1.0.10.0.TKHCNXM
- Android 版本：Android 13
- API Level：33

当前项目：

- `minSdk = 24`
- 对应最低支持 Android 7.0
- 因此 Redmi K40（Android 13 / API 33）在项目支持范围内

---

## 1. 模拟器和真机的本质区别

可以把 Android App 所处的环境理解为：

```text
你的 App
   ↓
Android Framework / 系统 API
   ↓
Android 系统
   ↓
设备硬件
```

在模拟器中：

```text
你的 App
   ↓
Android Framework
   ↓
模拟器中的 Android 系统
   ↓
虚拟硬件
   ↓
电脑提供的 CPU / GPU / 网络等资源
```

在真机中：

```text
你的 App
   ↓
Android Framework
   ↓
真实 Android 系统
   ↓
Redmi K40 的真实硬件
```

两者并不是两套完全不同的 Android。

很多上层 API 是相同的，真正容易产生差异的是底层的设备环境。

---

## 2. 模拟器适合做什么

Android Emulator 的优势是环境可控、容易复现。

可以模拟或控制：

- 屏幕尺寸和分辨率
- 网络速度
- 网络延迟
- GPS 位置
- 电池状态
- 加速度计
- 陀螺仪
- 距离传感器
- 磁场 / 指南针
- 指纹认证
- 相机
- 部分移动网络环境
- 现代 Emulator 中的 Bluetooth Classic / BLE 测试场景

例如可以主动制造弱网：

```text
高速网络
3G
EDGE
高延迟
断网
```

这对测试下面这些情况很有用：

```text
加载状态
超时处理
失败重试
弱网状态
网络恢复
```

模拟器的优势不是“它和真机完全一样”，而是：

> 它能稳定、重复地制造各种测试条件。

---

## 3. 真机必须验证的内容

模拟器虽然能覆盖很多场景，但不能完全替代 Redmi K40 的真实硬件环境。

尤其是下面这些内容：

- 真实 Bluetooth 无线环境
- 真实 NFC
- 红外发射
- USB / OTG
- 真实 Wi-Fi 芯片行为
- 真实 GPS / GNSS 接收
- 真实摄像头硬件
- 真实 CPU / GPU 性能
- 真实传感器数据
- 真实电池和功耗行为

因此：

```text
模拟器通过
≠
Redmi K40 一定通过
```

模拟器只能证明：

> App 在当前模拟环境中工作正常。

---

## 4. 不支持某项硬件能力时，不一定会崩溃

设备没有某种能力，并不代表 App 会自动崩溃。

Android API 往往会通过下面这些方式告诉应用：

```text
返回 null
返回 false
返回空结果
操作失败
```

正常处理思路应该是：

```text
App 请求某个能力
      ↓
设备是否支持？
   ↙         ↘
支持         不支持
 ↓             ↓
继续使用     禁用功能 / 给出提示
```

这不仅适用于模拟器。

真实 Android 手机本身也可能缺少某些硬件能力。

因此：

> 硬件能力应该先检测，再使用。

---

## 5. 同一个项目为什么可能模拟器正常、真机失败

实际排查时可以分成三个关口：

```text
APK 能不能安装
   ↓
App 能不能启动
   ↓
具体功能能不能正常工作
```

常见差异来源包括：

- CPU / ABI
- 权限状态
- 硬件能力
- 系统状态
- 网络环境
- 真正的外设连接状态

### ABI 示例

Native 代码需要针对具体 CPU 架构提供对应库。

例如：

```text
模拟器：x86_64
真机：arm64-v8a
```

如果 Native 库只提供了：

```text
x86_64/libxxx.so
```

那么模拟器可能运行正常，而 arm64 真机无法加载对应 Native 库。

这说明：

> Kotlin / Compose 代码可能完全没有问题，真正变化的是下面的运行设备。

## 6. Redmi K40 和 Emulator 的硬件能力对比

大致可以这样理解：

| Redmi K40 能力 | Emulator |
|---|---|
| CPU / GPU | 有虚拟 CPU / GPU，但不等价于 Snapdragon 870 / Adreno 650 |
| 屏幕 | 可以模拟尺寸和分辨率，但不等价于真实 AMOLED / 120Hz |
| 摄像头 | 可以模拟，但不等价于 K40 实际摄像头 |
| GPS | 可以模拟位置 |
| 加速度计 | 可以模拟 |
| 陀螺仪 | 可以模拟 |
| 距离传感器 | 可以模拟 |
| 指南针 | 可以模拟 |
| 指纹 | 可以模拟认证 |
| 网络 | 可以控制速度和延迟 |
| Bluetooth | 现代 Emulator 可做 Classic / BLE 测试，但不等价于真实 Bluetooth 芯片 |
| NFC | 真实硬件验证仍依赖真机 |
| 红外 | 依赖真机 |
| USB / OTG | 依赖真机 |

## 7. 新版 Emulator 与蓝牙测试

现代 Android Emulator 已经能够支持相当一部分 Bluetooth Classic / BLE 测试。

这意味着蓝牙相关测试可以分层：

```text
业务逻辑
   ↓
普通 Unit Test
   ↓
不需要 Emulator

Bluetooth API / 权限 / 状态机
   ↓
Instrumented / Integration Test
   ↓
Android Emulator

真实扫描、真实外设、真实无线环境
   ↓
Redmi K40 真机
```

可以在 Emulator 中测试的内容包括：

- 扫描到设备后的 UI 状态
- 权限拒绝后的逻辑
- 蓝牙状态变化
- 连接成功 / 失败分支
- 断开后的恢复逻辑
- BLE GATT 读写流程
- RSSI 变化相关逻辑
- 多个模拟设备之间的蓝牙交互

但 Emulator 仍然不能代替：

```text
真实 Bluetooth 芯片
真实无线距离
真实干扰
真实目标外设
Redmi K40 的实际行为
```

因此更合理的测试结构是：

```text
大量 Unit Test
      ↓
Emulator 集成测试
      ↓
少量 Redmi K40 最终真机验证
```

## 8. 当前项目的 Android 版本关系

当前项目可以理解为：

```text
minSdk 24
   ↓
最低支持 Android 7.0

Redmi K40
   ↓
Android 13 / API 33

新 Emulator
   ↓
可运行更高 Android / API 版本
```

`minSdk` 只表示：

> App 最低允许安装在哪个 Android 版本上。

它不表示项目只能按照 Android 7.0 开发。

因此当前 Redmi K40 完全处于项目支持范围内。

## 目标 2 完成后应该形成的认识

这一阶段最重要的结论是：

```text
模拟器 = 可控的测试环境
真机 = 真实的设备环境
```

模拟器适合：

- 日常开发
- 自动化测试
- 弱网和异常环境测试
- 大量重复测试
- 部分蓝牙集成测试

Redmi K40 真机适合：

- 真实硬件验证
- 真实蓝牙外设测试
- 最终性能验证
- 最终运行环境确认

最终可以把测试策略概括为：

> 平时尽量使用 Emulator 自动验证，真正依赖 Redmi K40 硬件的部分再使用真机完成最终确认。
