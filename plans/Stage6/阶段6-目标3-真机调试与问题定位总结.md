## 2. Logcat 中出现红色日志，不等于 App 出错

App 启动后，即使用户没有进行任何操作，也会立即出现大量日志。

例如：

```text
libEGL
libboost
perf_hint
BaseInputMethodService
```

其中可能包含 `E`、`W` 等级。

这些日志可能来自：

- Android Framework
- 小米 / HyperOS 系统组件
- 图形驱动
- 输入法
- 性能管理模块
- App 进程内加载的系统或厂商库

因此：

> Logcat 中出现红色 `E`，并不能直接说明自己的代码发生错误。

判断是否值得追查时，应先结合实际现象：

```text
App 是否崩溃？
功能是否异常？
日志是否对应当前问题？
```

## 5. Kotlin / Java 崩溃的最小定位方法

面对较长的 stack trace，可以先按以下顺序：

```text
1. 看异常类型
2. 看异常 Message
3. 找最靠上的自己包名
4. 点击 文件名:行号
```

本次异常：

```text
异常类型：
IllegalStateException

异常消息：
Stage 6: 这是我们故意制造的崩溃

自己的代码：
MainActivity
```

Android Studio 会把：

```text
MainActivity.kt:80
```

显示为可点击链接。

点击后可以直接跳到对应源码位置。

因此常见 Kotlin / Java 崩溃可以概括为：

```text
Logcat
→ FATAL EXCEPTION
→ Exception 类型 + Message
→ 自己代码的第一层 stack frame
→ 文件 + 行号
```

## 6. Android / Compose 调用栈不需要全部研究

Stack trace 中通常会看到大量：

```text
androidx.compose...
android.view...
```

它们主要表示：

```text
Android 收到触摸
    ↓
Compose 处理点击
    ↓
调用 onClick
    ↓
进入自己的代码
    ↓
发生异常
```

实际排查时通常优先寻找自己的包名：

```text
com.example.learnandroidfromai
```

而不是从 Android Framework 最底层一行行往上读。

编译器生成的：

```text
MainActivity$$ExternalSyntheticLambda...
```

也通常不需要作为主要问题点处理。

## 7. 真机 Native 崩溃与 LLDB

为了验证 C++ 真机调试，将矩阵函数临时改为：

```cpp
#include <cstdlib>

double runMatrixMultiply(int size) {
    std::abort();
    return 0.0;
}
```

然后不是使用普通 Run，而是：

```text
Debug App
→ 选择 Xiaomi M2012K11AC
→ LLDB 附加到真机进程
→ 点击按钮
→ C++ 执行 std::abort()
→ 产生 SIGABRT
```

Android Studio 成功自动暂停。

现场可以直接看到：

```text
Signal = SIGABRT
runMatrixMultiply(int)
matrix_compute.cpp:8
size = 1000
```

说明 LLDB 可以在真机上：

- 捕获 Native fatal signal
- 自动停在崩溃现场
- 显示 C++ 调用栈
- 定位源码文件和行号
- 查看局部变量

---

## 8. 为什么 Debug 时 App 没有立刻退出

普通运行：

```text
std::abort()
→ SIGABRT
→ 进程终止
```

Debug + LLDB 时：

```text
std::abort()
→ SIGABRT
→ LLDB 先截获 signal
→ App 进程暂停
→ 检查调用栈和变量
→ Continue
→ signal 被继续处理
→ 进程最终终止
```

所以此时手机上 App 仍然留在屏幕中，并不是它成功恢复了。

而是：

> 调试器把进程冻结在真正死亡之前。

## 9. 真机 LLDB Console

真机调试时，LLDB Console 和 Emulator 中使用方式基本一致。

常用命令：

```text
bt
```

查看当前线程调用栈。

```text
frame variable
```

查看当前 stack frame 的局部变量。

```text
p size
```

求值并打印变量。

```text
thread list
```

查看线程。

```text
register read
```

查看寄存器。

```text
disassemble
```

查看反汇编。

本质区别只是目标不同：

```text
Emulator
→ LLDB 连接模拟器进程

真机
→ LLDB 连接 Redmi K40 上的进程
```

LLDB 本身仍然是同一套 Native 调试器。

## 16. 最基本的问题定位模型

### Java / Kotlin 崩溃

```text
App 崩溃
→ Logcat
→ FATAL EXCEPTION
→ Exception 类型 / Message
→ 找自己的包名
→ 点击源码行号
```

### Native 崩溃

```text
C++ 发生 fatal signal
→ Debug + LLDB
→ SIGABRT / SIGSEGV 等
→ Call Stack
→ 找自己的 C++ frame
→ 源码行 + 现场变量
```

### 已经运行的 App

```text
App 正在运行
→ Attach Debugger
→ Dual (Java + Native)
→ Kotlin / Java / C++ 都可以继续断点调试
```
