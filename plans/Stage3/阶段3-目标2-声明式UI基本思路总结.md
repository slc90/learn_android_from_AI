# Stage 3 · 目标 2：理解声明式 UI 的基本思路

## 目标

理解 Jetpack Compose 中声明式 UI 的核心思路，并能够把它和已有的 React、WPF MVVM / Binding 经验对应起来。

本目标只讨论：

- 声明式 UI 的基本模型；
- State、UI、Event 之间的关系；
- Composable 的执行特点；
- Recomposition（重组）的基本含义；
- 为什么 Composable 不应该依赖固定执行次数和执行顺序。

暂不深入：

- `remember`；
- `mutableStateOf`；
- 状态提升；
- ViewModel；
- 生命周期状态保存。

这些内容属于 Stage 3 · 目标 3。

---

# 1. 声明式 UI 的核心

声明式 UI 最核心的思路可以概括为：

```text
UI = f(State)
```

也就是：

> 根据当前状态，描述此时界面应该是什么样。

开发者主要描述“现在应该显示什么”，而不是不断命令已有控件执行修改操作。

例如：

```kotlin
@Composable
fun Greeting(name: String) {
    Text("Hello $name")
}
```

当：

```text
name = "Alice"
```

UI 应该是：

```text
Hello Alice
```

当：

```text
name = "Bob"
```

UI 描述自然变为：

```text
Hello Bob
```

重点不是：

```text
找到 Text
→ 调用 setter
→ 修改 Text 内容
```

而是：

```text
当前数据
→ 重新描述 UI
```

---

# 2. 与 WPF Binding 的关系

WPF MVVM 中：

```xml
<TextBlock Text="{Binding Count}" />
```

同样具有明显的声明式思想。

它表达的是：

> `TextBlock.Text` 应该来自 ViewModel 的 `Count`。

而不是手动写：

```csharp
textBlock.Text = viewModel.Count.ToString();
```

所以 WPF 的：

```text
XAML + Binding
```

本身就是声明式 UI 的一种形式。

不过 WPF 和 Compose 的更新模型仍然有区别。

WPF 更接近：

```text
长期存在的控件树
        ↓
Binding Engine 持续同步属性
        ↓
控件属性发生变化
```

Compose 更接近：

```text
当前 State
    ↓
Composable 重新求值
    ↓
得到当前应该存在的 UI 描述
```

所以 WPF 常常是在同步“控件属性”，而 Compose 更强调“根据当前状态重新描述 UI”。

---

# 3. 与 React 的关系

React 和 Compose 的思想非常接近。

React：

```jsx
function Greeting({ name }) {
    return <span>Hello {name}</span>
}
```

Compose：

```kotlin
@Composable
fun Greeting(name: String) {
    Text("Hello $name")
}
```

两者都可以理解成：

```text
输入 / State
    ↓
UI 描述函数
    ↓
UI
```

因此对于熟悉 React 的开发者来说，Compose 的声明式模型并不是全新的范式。

---

# 4. 声明式 UI 不只是属性绑定

声明式 UI 不只是：

```text
某个数据
→ 某个 Text 的内容
```

整个 UI 结构本身也可以由状态决定。

例如：

```kotlin
@Composable
fun UserScreen(
    isLoading: Boolean,
    error: String?,
    userName: String?
) {
    when {
        isLoading -> {
            CircularProgressIndicator()
        }

        error != null -> {
            Text("加载失败：$error")
        }

        userName != null -> {
            Text("Hello $userName")
        }
    }
}
```

不同状态直接对应不同 UI：

```text
Loading
   ↓
Progress

Error
   ↓
Error Message

Success
   ↓
User Content
```

而不是：

```text
找到 Loading View
→ hide / show

找到 Error View
→ hide / show

找到 Content View
→ hide / show
```

所以声明式 UI 的一个重要特点是：

> 状态不仅能改变控件属性，也可以直接决定 UI 树的结构。

---

# 5. State → UI → Event → State

声明式 UI 中比较自然的数据流是：

```text
State
  ↓
 UI
  ↓
Event
  ↓
State Change
  ↺
```

例如：

```kotlin
@Composable
fun LoginScreen(
    loggedIn: Boolean,
    onLoginClick: () -> Unit
) {
    if (loggedIn) {
        Text("已登录")
    } else {
        Button(onClick = onLoginClick) {
            Text("登录")
        }
    }
}
```

这里 Button 不负责直接操作其他 UI。

它只报告：

```text
登录按钮被点击
```

外部逻辑改变状态：

```text
loggedIn = true
```

然后新的状态自然产生新的 UI：

```text
已登录
```

所以可以把思路概括成：

> 事件改变数据，数据决定界面。

而不是：

> 事件处理代码直接维护界面本身。

---

# 6. 与 WPF TwoWay Binding 的区别

WPF 中如果大量使用 TwoWay Binding，再混合：

- `INotifyPropertyChanged`；
- ViewModel setter；
- `TextChanged`；
- Converter；
- 多个属性互相依赖；

很容易形成：

```text
ViewModel 改值
→ View 更新
→ View 再把值写回 ViewModel
→ ViewModel 再修改
→ 再次触发 View 更新
```

这种关系复杂以后，可能出现循环更新或难以判断“是谁改了谁”。

React / Compose 更鼓励：

```text
State
  ↓
UI
  ↓
Event
  ↓
State
```

也就是相对清晰的单向数据流。

这并不意味着 React / Compose 不可能出现循环更新。

例如：

```text
render / composition
→ 修改 State
→ 再次 render / composition
→ 再修改 State
→ ...
```

同样可能形成无限更新。

区别主要在于：

> 声明式 UI 默认把“读取状态”和“修改状态”分得更清楚，因此循环依赖通常更容易识别。

---

# 7. Composable 是 UI 描述函数

Composable 不应该被理解成：

```text
页面创建时只执行一次的初始化函数
```

而更应该理解成：

```text
Compose 需要当前 UI 描述时
→ 执行 Composable
```

例如：

```kotlin
@Composable
fun UserCard(
    name: String,
    enabled: Boolean,
    onClick: () -> Unit
) {
    Button(
        enabled = enabled,
        onClick = onClick
    ) {
        Text(name)
    }
}
```

这个 Composable 的职责主要是：

```text
输入
├── name
├── enabled
└── onClick
      ↓
描述 UI
```

而不是在函数执行时顺便：

```text
写数据库
发网络请求
修改全局变量
手动操作其他 UI
```

---

# 8. 为什么 Composable 应尽量接近纯函数

Composable 可能因为重组而重复执行。

所以这种写法在思想上有问题：

```kotlin
@Composable
fun MyScreen() {
    sendRequest()

    Text("Hello")
}
```

如果 `MyScreen()` 再次执行：

```text
第一次组合
→ sendRequest()

重组
→ sendRequest()

再次重组
→ sendRequest()
```

因此 Composable 应尽量具有类似幂等的性质：

```text
相同输入
→ 描述相同 UI
```

而不应该依赖：

```text
这是第几次执行
之前谁执行过
之后谁一定执行
本次执行一定会最终提交
```

所以：

> Composable 更像 UI 描述函数，而不是生命周期回调或业务事件处理函数。

---

# 9. 普通局部变量会重新初始化

Composable 本质上仍然是 Kotlin 函数。

例如：

```kotlin
@Composable
fun Counter() {
    var x = 0
    Text("$x")
}
```

如果这个 Composable 因为重组再次执行：

```text
x
→ 再次初始化为 0
```

这和 React Function Component 中的普通局部变量一样。

因此：

> 普通局部变量不能天然跨重组保存。

如何保存跨重组状态属于目标 3，本目标不继续展开。

---

# 10. Recomposition（重组）

当 Compose 观察到相关状态变化后，会重新执行受影响的 Composable。

这个过程叫：

```text
Recomposition
重组
```

可以粗略理解为：

```text
State 变化
    ↓
找到受影响的 UI 描述
    ↓
重新执行相关 Composable
    ↓
更新必要的 UI
```

重要的是：

```text
Recomposition
≠ 整个 Activity 重新创建
≠ 整棵 UI 树全部销毁重建
≠ 整个屏幕所有内容重新绘制
```

Compose 可以只重新执行受影响的部分，并跳过没有必要重新计算的部分。

这和 React 中：

```text
state / props 变化
→ 重新计算相关 UI 描述
→ 最终只提交必要变化
```

的思想比较接近。

---

# 11. 为什么不能依赖固定执行次数和顺序

Compose 不把：

```text
Composable A 一定执行几次
Composable A 一定先于 B
某次执行一定最终生效
```

作为业务代码可以依赖的语义保证。

这样做的原因不是简单地说：

```text
运行结果碰巧不确定
```

而是更深一层的设计取舍。

如果框架必须保证：

```text
固定执行次数
+
固定执行顺序
```

那么运行时就会受到很强的约束。

而 Compose 希望保留：

- 跳过不需要执行的 Composable；
- 只重组局部；
- 取消已经过时的重组；
- 对复杂 UI 做更多调度和优化；
- 为未来实现保留更大的自由度。

所以更准确的理解是：

> 为了让同一套声明式执行模型适应简单 UI、复杂状态树、高频更新和各种运行时优化，Compose 不把具体执行次数和执行顺序作为语义契约。

对于简单页面，实际观察到的执行行为可能长期都很直观。

但：

> “当前实现经常这样执行”

不能等同于：

> “应用逻辑可以依赖它永远这样执行”。

# 12. 当前形成的声明式 UI 心智模型

可以把目标 2 最终压缩成：

```text
          Event
            ↑
            │
State ───→ UI
  ↑         │
  └─────────┘
```

更完整一点：

```text
State
  ↓
Composable
  ↓
UI
  ↓
User Event
  ↓
State Change
  ↓
Recomposition
  ↺
```

其中：

```text
State
→ 当前数据

Composable
→ 根据当前数据描述 UI

Event
→ 用户行为产生的事件

Recomposition
→ State 改变后重新执行相关 UI 描述
```

# 13. 与已有经验的对应

## WPF

```text
XAML + Binding
→ UI 跟随数据变化
```

已经具备明显的声明式思想。

但 WPF 通常围绕：

```text
长期存在的控件对象
+
Binding 更新属性
```

工作。

---

## React

React 与 Compose 的模型更接近：

```text
State
↓
Component / Composable
↓
UI
```

Function Component / Composable 都可能重复执行，普通局部变量也都会重新初始化。

因此有 React 背景时，Compose 的声明式 UI 基础概念通常比较容易理解。
