# 阶段 3 - 目标 6：界面结构与组件复用总结

## 目标

能够构建具有一定层次和复用性的 Jetpack Compose 界面结构。

这一目标的重点不是“把代码拆成更多函数”，而是让界面的代码结构能够对应真实的 UI 结构，并让组件拥有清晰的职责和合理的依赖。

---

# 1. Composable 与组件化

Compose 中，一个 `@Composable` 函数可以看作一个 UI 组件。

例如：

```kotlin
@Composable
fun Counter(
    count: Int,
    onIncrease: () -> Unit
) {
    Column {
        Text("计数：$count")

        Button(onClick = onIncrease) {
            Text("+1")
        }
    }
}
```

可以把整个页面理解成一棵由 Composable 组成的 UI 树：

```text
StudyScreen
├── StudyHeader
├── Counter
└── StudyActions
```

组件拆分首先是为了表达界面的真实结构，而不是单纯减少函数长度。

如果一块 UI 可以被赋予一个明确的职责，例如：

```text
Counter
StudyHeader
StudyActions
```

那么它通常就适合成为独立的 Composable。

---

# 2. 页面组件与子组件

页面级 Composable 通常负责：

- 获取页面需要的状态
- 与 ViewModel 等业务对象连接
- 组织整个页面结构
- 把数据和事件传给子组件

例如：

```kotlin
@Composable
fun StudyScreen(
    topic: String,
    onBack: () -> Unit,
    viewModel: StudyViewModel = viewModel()
) {
    Counter(
        count = viewModel.count,
        onIncrease = viewModel::increase
    )
}
```

而较小的 UI 组件通常只接收自己真正需要的数据：

```kotlin
@Composable
fun Counter(
    count: Int,
    onIncrease: () -> Unit
)
```

相比：

```kotlin
@Composable
fun Counter(
    viewModel: StudyViewModel
)
```

前一种方式依赖更少，也更容易复用。

可以把关系理解成：

```text
ViewModel
   ↓
页面 Composable
   ↓
数据 + 事件
   ↓
子 Composable
```

# 3. Slot API

Slot API 是 Compose 中非常常见的组件设计方式。

普通参数传递的是数据：

```text
String
Int
Boolean
事件回调
```

而 Slot 传递的是一块 UI：

```kotlin
@Composable () -> Unit
```

例如：

```kotlin
@Composable
fun SectionCard(
    header: @Composable () -> Unit,
    content: @Composable () -> Unit
) {
    Column {
        header()
        content()
    }
}
```

调用时：

```kotlin
SectionCard(
    header = {
        Text("学习主题")
    },
    content = {
        Text(topic)
    }
)
```

这里：

```text
SectionCard
├── header slot
└── content slot
```

组件只规定有哪些区域，而不规定这些区域必须放什么具体 UI。

Compose 自带组件中也大量使用这种设计，例如：

```kotlin
TopAppBar(
    title = { ... },
    navigationIcon = { ... },
    actions = { ... }
)
```

如果熟悉 React，可以把 Slot API 理解成类似 `children`，只是 Compose 很常使用多个具名 slot。

# 4. Modifier 与组件 API

可复用 Composable 通常会暴露：

```kotlin
modifier: Modifier = Modifier
```

例如：

```kotlin
@Composable
fun SectionCard(
    modifier: Modifier = Modifier,
    content: @Composable () -> Unit
) {
    Card(
        modifier = modifier
    ) {
        content()
    }
}
```

调用者可以决定组件在外部布局中的表现：

```kotlin
SectionCard(
    modifier = Modifier
        .fillMaxWidth()
        .padding(16.dp)
) {
    ...
}
```

可以粗略理解为：

```text
调用者传入的 Modifier
    ↓
控制组件与外部环境的关系

组件内部创建的 Modifier
    ↓
控制组件内部布局
```

Modifier 不只是样式，它还可以描述：

- 布局
- 尺寸
- 绘制
- 点击
- 滚动
- 手势
- 语义等行为

Modifier 是有顺序的，不同 Modifier 的排列顺序可能产生不同结果。

# 5. Layout Scope

一些 Compose 容器会给内部内容提供特殊的 Scope。

例如 `Row` 的 `content` 大致可以理解为：

```kotlin
content: @Composable RowScope.() -> Unit
```

因此：

```kotlin
Row {
    Text(
        "A",
        modifier = Modifier.weight(1f)
    )
}
```

这里的：

```kotlin
Modifier.weight(...)
```

来自 `RowScope` 提供的能力。

不同 Scope 可以提供不同 API，例如：

```text
RowScope
├── weight()
├── align()
└── alignBy()

BoxScope
├── align()
└── matchParentSize()
```

这些能力通常只在对应父布局中才有意义。

例如：

```kotlin
Modifier.weight(1f)
```

必须依赖父布局来解释“权重应该和谁一起分配空间”。

这种设计和 WPF 的附加属性在设计意图上有些相似：

```text
WPF
Grid.Row
Grid.Column

Compose
RowScope.weight()
BoxScope.align()
```

但实现方式不同：

- WPF 使用 DependencyProperty / Attached Property
- Compose 主要使用 Kotlin receiver scope 和扩展函数

更一般地：

```text
XXXScope
=
进入 XXX 上下文后，
可以额外使用一组只在这个上下文中有意义的 API
```

Scope 不一定只用于布局。

例如 `LazyListScope` 会提供：

```kotlin
item { ... }
items(...) { ... }
```

用于声明列表内容。

# 6. CompositionLocal

`CompositionLocal` 用于向 Composition Tree 下层隐式传播某些环境数据。

如果熟悉 React，可以把它理解成类似 React Context。

例如：

```kotlin
val LocalAccentColor = compositionLocalOf {
    Color.Blue
}
```

上层提供：

```kotlin
CompositionLocalProvider(
    LocalAccentColor provides Color.Red
) {
    HomeScreen()
}
```

深层组件可以直接读取：

```kotlin
@Composable
fun Title() {
    Text(
        text = "Hello",
        color = LocalAccentColor.current
    )
}
```

结构类似：

```text
CompositionLocalProvider
    LocalAccentColor = Red
            ↓
       HomeScreen
            ↓
          Title
            ↓
 LocalAccentColor.current
```

CompositionLocal 还支持局部覆盖：

```kotlin
CompositionLocalProvider(
    LocalAccentColor provides Color.Green
) {
    Title()
}
```

这一部分子树会看到 `Green`，离开以后仍然使用外层的值。

适合通过 CompositionLocal 传播的通常是环境级信息，例如：

- Theme
- `LocalContext`
- `LocalDensity`
- LayoutDirection
- 一些全局 UI 配置

普通页面状态和事件一般仍然优先使用参数显式传递。

Compose 本身已经大量使用 CompositionLocal，例如：

```kotlin
LocalContext.current
LocalDensity.current
MaterialTheme.colorScheme
MaterialTheme.typography
```

# 7. 组件边界与 Recomposition

组件拆分除了改善代码结构，也可能形成更清晰的 recomposition 边界。

例如：

```kotlin
@Composable
fun StudyScreen(
    topic: String,
    count: Int
) {
    Topic(topic)
    Counter(count)
}
```

当只有：

```text
count: 1 → 2
```

发生变化时，可以粗略理解为：

```text
StudyScreen
├── Topic("Compose")   ← 输入没变化，可以跳过
└── Counter(2)         ← 需要更新
```

Compose 会根据状态读取位置、输入变化以及参数稳定性等信息判断哪些 Composable 可以跳过。

但：

> 拆 Composable 本身并不是性能优化手段。

不应该为了减少 recomposition 而机械地把 UI 拆成大量小函数。

组件拆分首先应该服务于：

- 清晰的职责
- 可读性
- 可复用性
- 合理的数据依赖

更好的 recomposition 边界通常是这些设计带来的自然结果。

# 8. 本目标需要形成的整体认识

Compose 页面可以看成一棵组件树：

```text
Page
│
├── Section
│   ├── Component
│   └── Component
│
└── Section
    └── Component
```

页面顶部通常知道更多：

```text
ViewModel
业务状态
导航
页面事件
```

越往下的组件越应该只知道：

```text
我需要什么数据
我能触发什么事件
我要显示什么 UI
```

同时 Compose 提供了一些专门支持组件化的机制：

```text
Composable
    ↓
组件基本单位

Slot API
    ↓
把 UI 本身作为参数

Modifier
    ↓
控制组件在当前环境中的表现

XXXScope
    ↓
提供上下文相关能力

CompositionLocal
    ↓
向组件树下方传播环境信息

Recomposition
    ↓
根据状态依赖更新需要变化的 UI
```

# 目标 6 的判断标准

完成这一目标后，不需要记住所有 Compose API。

更重要的是面对一个页面时，能够判断：

1. 哪些部分属于页面整体结构。
2. 哪些 UI 区域值得成为独立 Composable。
3. 子组件真正需要哪些数据和事件。
4. 什么时候应该使用普通参数。
5. 什么时候适合使用 Slot API。
6. `Modifier` 应该由谁控制。
7. 为什么某些 API 只在特定 Scope 中存在。
8. 什么类型的数据适合使用 CompositionLocal。
9. 组件拆分与 recomposition 之间大致是什么关系。

最终形成的原则可以概括为：

> **按照 UI 职责划分 Composable，让页面负责组织，让子组件依赖尽可能少；利用 Slot、Modifier、Scope 和 CompositionLocal 提高组件的组合能力，而不是为了拆分本身去拆分。**
