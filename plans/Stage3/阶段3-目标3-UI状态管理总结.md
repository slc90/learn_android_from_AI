# Stage 3 · 目标 3：管理 UI 状态并让界面正确更新

## 目标

能够理解并实践 Jetpack Compose 中的 UI 状态管理，包括：

- `remember` / `rememberSaveable`；
- `mutableStateOf`；
- 状态提升（State Hoisting）；
- Single Source of Truth；
- `ViewModel` 与屏幕级状态；
- `StateFlow` 与 `collectAsStateWithLifecycle()`；
- 不可变 `UiState`；
- State / Event / Effect 的边界；
- `LaunchedEffect`；
- 局部状态与屏幕状态的生命周期差异；
- 派生状态。

本目标的核心可以概括为：

```text
State
  ↓
 UI
  ↑
Event
```

更完整一点：

```text
用户操作
   ↓
 Event
   ↓
ViewModel / 状态拥有者
   ↓
新的 State
   ↓
Compose 重组相关 UI
```

---

# 1. 什么是 UI State

如果一个值发生变化后，界面应该随之变化，那么它就是 UI State 的候选。

例如：

```kotlin
var text by remember {
    mutableStateOf("")
}
```

`text` 会影响：

```kotlin
OutlinedTextField(
    value = text,
    onValueChange = {
        text = it
    }
)

Text("当前输入：$text")
```

因此：

```text
text 改变
→ Compose 观察到状态变化
→ 相关 UI 重组
→ 新值显示出来
```

---

# 2. mutableStateOf

`mutableStateOf()` 创建一个 Compose 可以观察的可变状态。

例如：

```kotlin
mutableStateOf("")
```

其中：

```text
""
```

就是初始值。

如果写：

```kotlin
mutableStateOf("Hello")
```

那么初始状态就是：

```text
Hello
```

可以把它粗略理解成：

> 这是一个值发生变化时，可以通知 Compose 的状态容器。

---

# 3. remember

`remember` 的作用是：

> 在 Composable 重组时，继续使用之前保存的对象。

典型写法：

```kotlin
var text by remember {
    mutableStateOf("")
}
```

两者职责不同：

```text
mutableStateOf
→ 让状态变化可以被 Compose 观察

remember
→ 让这个状态对象在重组之间继续存在
```

所以它们经常一起出现，但并不是不可分割的固定组合。

---

# 4. remember 的“位置”不是代码行号

`remember` 保存的数据与 Composition 中的调用位置相关。

这不是源代码第几行，而是运行时 UI 结构中的位置。

例如：

```kotlin
@Composable
fun Screen(showText: Boolean) {
    if (showText) {
        val value = remember {
            mutableStateOf("hello")
        }

        Text(value.value)
    }
}
```

当：

```text
showText = true
```

这个 `remember` 存在于 Composition 中。

当：

```text
showText = false
```

这一支 UI 离开 Composition，对应的记忆也会被丢弃。

再次变成：

```text
showText = true
```

会重新创建：

```text
"hello"
```

如果希望状态在这个条件分支消失以后仍然保留，可以把 `remember` 提升到更高的位置。

---

# 5. Kotlin 的 by

这段：

```kotlin
var text by remember {
    mutableStateOf("")
}
```

中的 `by` 是 Kotlin 的属性委托语法，不是 Compose 特有语法。

不使用 `by` 时：

```kotlin
val textState = remember {
    mutableStateOf("")
}

textState.value = "abc"
println(textState.value)
```

使用 `by` 后：

```kotlin
var text by remember {
    mutableStateOf("")
}

text = "abc"
println(text)
```

可以把它理解成：

> 属性的 get / set 被委托给右侧对象。

---

# 6. Lambda 中的 it

例如：

```kotlin
onValueChange = {
    text = it
}
```

当一个 Kotlin Lambda 只有一个参数时，这个参数默认可以叫 `it`。

等价于：

```kotlin
onValueChange = { newText ->
    text = newText
}
```

因此：

```text
it
= 当前输入框传进来的新文本
```

---

# 7. Recomposition 与状态依赖

当 Composable 读取某个 Compose State 时，Compose 会记录这块 UI 对该状态的依赖。

可以粗略理解成：

```text
Composable 读取 State
        ↓
Compose 记录依赖
        ↓
State 发生有效变化
        ↓
相关 UI 被标记需要重组
        ↓
Recomposer 安排重组
```

因此：

```text
Recomposition
≠ Activity 重新创建
≠ 整个页面全部销毁重建
```

Compose 可以只重组受影响的部分，并跳过不需要重新执行的部分。

---

# 8. 为什么不能在 Composable 函数体里直接改 State

错误示例：

```kotlin
@Composable
fun BadExample() {
    var count by remember {
        mutableStateOf(0)
    }

    Text("$count")

    count++
}
```

逻辑会变成：

```text
执行 Composable
→ count++
→ State 变化
→ 触发重组
→ 再执行 Composable
→ 再 count++
→ ...
```

而：

```kotlin
Button(
    onClick = {
        count++
    }
) {
    Text("$count")
}
```

不会形成这个循环。

原因是：

```text
重组时
→ 只是创建 / 提供 onClick Lambda

用户真正点击时
→ Lambda 才被执行
```

---

# 9. 状态提升（State Hoisting）

如果多个 Composable 需要共享同一份状态，应该把状态提升到它们共同的上层。

例如：

```kotlin
@Composable
fun Screen() {
    var count by remember {
        mutableStateOf(0)
    }

    CounterDisplay(count)
    CounterButton(
        onClick = {
            count++
        }
    )
}
```

子组件只接收：

```text
状态
+
事件回调
```

例如：

```kotlin
@Composable
fun CounterDisplay(count: Int) {
    Text("点击次数：$count")
}

@Composable
fun CounterButton(
    onClick: () -> Unit
) {
    Button(onClick = onClick) {
        Text("增加")
    }
}
```

这和 React 中的“状态提升”非常接近。

---

# 10. Single Source of Truth

同一个事实最好只有一个权威可写来源。

例如搜索文字：

```kotlin
@Composable
fun SearchInput(
    text: String,
    onTextChange: (String) -> Unit
) {
    OutlinedTextField(
        value = text,
        onValueChange = onTextChange
    )
}
```

状态由外部持有：

```kotlin
var text by remember {
    mutableStateOf("")
}

SearchInput(
    text = text,
    onTextChange = {
        text = it
    }
)
```

此时：

```text
text
= 唯一权威来源
```

同一个事实不要同时保存多份可写副本，否则很容易出现不同步。

---

# 11. remember 与 rememberSaveable

`remember`：

```text
重组
✅ 保留

Activity 重建
❌ 通常丢失
```

例如屏幕旋转导致 Activity 重新创建时，普通 `remember` 状态会重新初始化。

`rememberSaveable`：

```kotlin
var text by rememberSaveable {
    mutableStateOf("")
}
```

可以把适合保存的轻量 UI 状态保存到 Android 的 saved state 机制中。

可以粗略理解成：

```text
remember
→ Composition 生命周期

rememberSaveable
→ Composition + 可恢复的 saved state
```

它适合轻量、可恢复的 UI 数据，不适合保存巨大或复杂对象。

---

# 12. ViewModel

当状态已经属于整个屏幕，或者和业务逻辑有关时，可以把它放到 `ViewModel`。

例如：

```kotlin
class Stage3ViewModel : ViewModel()
```

ViewModel 的角色可以理解成：

> 屏幕级状态的拥有者与事件处理者。

它和 WPF MVVM 中的 ViewModel 有明显相似之处：

```text
WPF MVVM                 Android / Compose

View                     Composable UI
ViewModel                ViewModel
绑定属性                  UiState
Command / Event           onClick / onValueChange
属性变化                  State / Flow 驱动 UI 更新
```

不同的是 Android 的 `ViewModel` 还有 Android 自己的生命周期语义，例如可以跨配置变更存活。

---

# 13. Activity 不等于页面

Activity 是 Android 平台组件，Screen / Page 是 UI 概念。

例如：

```text
MainActivity
└── Compose UI
    ├── HomeScreen
    ├── SearchScreen
    └── DetailScreen
```

用户可以在多个 Screen 之间切换，但底层仍然只有一个 Activity。

因此：

```text
Activity
→ UI 宿主

Screen / Page
→ 宿主内部当前显示的 UI 内容
```

如果一个 Activity 恰好只承载一个页面，它们在使用体验上会很像，但概念上仍然是“宿主”和“内容”的关系。

# 14. ViewModel 的 UiState

项目中创建了：

```kotlin
data class Stage3UiState(
    val text: String = "",
    val isStarted: Boolean = false,
    val isLoading: Boolean = false
)
```

它描述：

```text
当前屏幕长什么样
```

例如：

```text
text
→ 输入框显示什么

isStarted
→ 学习是否已经开始

isLoading
→ 是否显示加载 UI
```

而：

```text
Repository
API
Database
```

这些属于获取 / 计算状态的工具，不属于 UiState 本身。

---

# 15. MutableStateFlow 与 StateFlow

ViewModel 中使用：

```kotlin
private val _uiState =
    MutableStateFlow(Stage3UiState())

val uiState = _uiState.asStateFlow()
```

结构是：

```text
ViewModel 内部
MutableStateFlow
可读 + 可写
        ↓
    asStateFlow()
        ↓
外部 UI
StateFlow
只读观察
```

这样 UI 不能随便改状态。

修改状态只能通过 ViewModel 提供的方法：

```kotlin
fun onTextChange(text: String) {
    _uiState.update { oldState ->
        oldState.copy(text = text)
    }
}
```

因此形成：

```text
UI
→ 发送 Event

ViewModel
→ 修改 State

UI
← 读取新的 State
```

---

# 16. collectAsStateWithLifecycle

Compose 中通过：

```kotlin
val uiState by viewModel.uiState
    .collectAsStateWithLifecycle()
```

把 `StateFlow` 转成 Compose 可以观察的 State。

数据链是：

```text
ViewModel 修改 _uiState
        ↓
StateFlow 自动发出新值
        ↓
collectAsStateWithLifecycle() 收集
        ↓
Compose State 更新
        ↓
相关 UI 重组
```

重点是：

> Compose 并不会凭空发现普通对象变了。

需要建立明确的状态订阅关系。

为了在 Composable 中使用：

```kotlin
viewModel()
```

```toml
androidx-lifecycle-viewmodel-compose = {
```

# 18. 不可变 UiState 与 copy()

UiState 通常设计成不可变对象：

```kotlin
data class CounterUiState(
    val count: Int = 0
)
```

状态变化时，不原地修改旧对象，而是创建新状态：

```kotlin
_uiState.update { oldState ->
    oldState.copy(
        count = oldState.count + 1
    )
}
```

语义就是：

```text
旧 State
↓ Event
计算
↓
新 State
```

这和 React 中避免原地 mutate state 的思路很接近。

---

# 19. copy() 不等于深拷贝整个对象树

例如：

```kotlin
data class UiState(
    val results: List<Item>
)
```

执行：

```kotlin
old.copy(isLoading = true)
```

不会复制整个 `results` 列表内容。

它只是复制 UiState 外壳，并继续引用原来的 List：

```text
旧 UiState ──→ results ──→ 大列表
新 UiState ──→ results ──┘
```

真正可能需要复制集合结构的是：

```kotlin
old.copy(
    results = old.results + newItem
)
```

对于超大集合和高频更新，需要关注性能；普通 UI 数据一般不需要提前复杂化。

---

# 20. UiState 内部也尽量不可变

不推荐：

```kotlin
data class SearchUiState(
    val results: MutableList<String>
)
```

因为即使外层是 `val`，内部仍然可以：

```kotlin
results.add("Android")
```

这会变成：

```text
同一个 State 对象
→ 内部偷偷发生变化
```

更推荐：

```kotlin
data class SearchUiState(
    val results: List<String> = emptyList()
)
```

然后：

```kotlin
_uiState.update { old ->
    old.copy(
        results = old.results + "Android"
    )
}
```

这样状态变化始终保持：

```text
旧快照
→ 新快照
```

---

# 21. StateFlow 的自动传播

开发者主动做的是：

```kotlin
_uiState.update { ... }
```

后面的传播由框架完成：

```text
StateFlow 发出新状态
↓
collectAsStateWithLifecycle 收到
↓
Compose State 更新
↓
UI 重组
```

这里：

- `StateFlow` 属于 Kotlin Coroutines；
- `collectAsStateWithLifecycle()` 属于 AndroidX Lifecycle + Compose 的生命周期感知收集方式。

---

# 22. State down / Event up

目前形成的主要数据流是：

```text
        State ↓

ViewModel ─────────→ UI

ViewModel ←───────── UI

        Event ↑
```

也就是：

```text
UI
→ 读取状态
→ 发送事件

ViewModel
→ 处理事件
→ 修改状态
```

这是目前 Compose 屏幕状态管理中最重要的结构之一。

# 23. Stage3Screen 与 Stage3Content 的拆分

为了让 UI 本身不依赖 ViewModel，把页面拆成：

```text
Stage3Screen
→ 负责连接 ViewModel / StateFlow

Stage3Content
→ 只接收普通 State + Callback
```

例如：

```kotlin
@Composable
fun Stage3Screen(
    modifier: Modifier = Modifier,
    viewModel: Stage3ViewModel = viewModel()
) {
    val uiState by viewModel.uiState
        .collectAsStateWithLifecycle()

    Stage3Content(
        modifier = modifier,
        uiState = uiState,
        onTextChange = viewModel::onTextChange,
        onStartClick = viewModel::onStartClick,
        onLoadingClick = viewModel::onLoadingClick
    )
}
```

`Stage3Content` 不需要知道：

```text
ViewModel
StateFlow
Lifecycle
```

它只知道：

```text
给我 State
→ 我负责画 UI

用户操作
→ 我调用 Callback
```

因为 `Stage3Content` 不依赖 ViewModel，所以可以直接传假状态预览：

```kotlin
@Preview(showBackground = true)
```

因此：

> 给一份 State，就能直接得到对应 UI。

这正是声明式 UI 的优势之一。

# 25. State 可以直接决定 UI 结构

例如：

```kotlin
if (uiState.isLoading) {
    CircularProgressIndicator()
} else {
    Text("加载完成")
}
```

不是：

```text
找到 ProgressBar
→ show()

找到 Text
→ hide()
```

而是：

```text
isLoading = true
→ UI 就包含 ProgressIndicator

isLoading = false
→ UI 就包含“加载完成”
```

这再次体现：

```text
UI = f(State)
```

# 26. 派生状态

如果一个值可以从已有 State 直接算出来，通常不要再保存第二份。

例如：

```kotlin
val canStart = uiState.text.isNotBlank()
```

按钮：

```kotlin
Button(
    onClick = onStartClick,
    enabled = canStart
) {
    Text("开始学习")
}
```

这样：

```text
text = ""
→ canStart = false

text = "Android"
→ canStart = true
```

不需要在 `UiState` 里同时保存：

```text
text
+
canStart
```

否则可能出现：

```text
text = ""
canStart = true
```

这种矛盾状态。

所以：

> 能从源状态推导出来的值，尽量直接计算。

# 27. 局部状态与屏幕状态可以同时存在

用了 ViewModel 以后，并不是所有 `remember` 都应该消失。

例如：

```kotlin
var showDetails by remember {
    mutableStateOf(false)
}
```

如果它只是：

```text
某个局部说明区域是否展开
```

那么留在 Composable 中很合理。

当前页面可以同时存在：

```text
Stage3ViewModel
├── text
├── isStarted
└── isLoading

Stage3Content 本地
└── showDetails
```

选择状态位置时可以遵循：

> 把状态放在能够覆盖所需生命周期和使用范围的最低合理位置。

# 28. ViewModel 与配置变更

实践中验证了：

```text
输入 text
→ 旋转屏幕
→ Activity 重建
→ text 仍然存在
```

原因是：

```text
Activity 重建
↓
Composable 重新创建
↓
ViewModel 仍然存活
↓
StateFlow 中的 UiState 仍然存在
```

而普通：

```kotlin
remember {
    mutableStateOf(...)
}
```

通常会随着 Activity / Composition 重建而丢失。

需要注意：

> ViewModel 可以跨配置变更存活，但它本身并不等于永久存储，也不能单独解决进程死亡恢复。

进程恢复相关内容以后再学习 `SavedStateHandle`。

# 29. State / Event / Effect

可以把三者区分成：

```text
State
→ “现在是什么样？”

Event
→ “刚刚发生了什么？”

Effect
→ “因此 UI 需要额外执行一次什么动作？”
```

例如：

```text
用户点击登录按钮
→ Event

isLoading = true
→ State

登录成功
→ State / 业务结果

跳转页面一次
→ Effect

显示 Snackbar / Toast 一次
→ Effect
```

重要的是：

> Event 和 Effect 不等于“持续时间短的 State”。

关键区别在于语义。

---

# 30. 为什么 Effect 不能直接写在 Composable 函数体里

Composable 可能重复执行。

如果直接：

```kotlin
if (uiState.loginSuccess) {
    navController.navigate("home")
}
```

就可能：

```text
第一次重组
→ navigate

再次重组
→ 又 navigate
```

因此一次性副作用需要受控执行。

---

# 31. LaunchedEffect

Compose 提供：

```kotlin
LaunchedEffect(key) {
    // 副作用
}
```

可以粗略理解成：

```text
Composable 进入 Composition
→ Effect 启动

key 不变
→ 普通重组不会重新启动

key 改变
→ 旧 Effect 取消
→ 新 Effect 启动

Composable 离开 Composition
→ Effect 自动取消
```

它和 React 的：

```text
useEffect(..., [dependency])
```

在使用直觉上很相似，但具体机制不同。

---

# 32. LaunchedEffect 中运行的是 Coroutine

例如：

```kotlin
LaunchedEffect(userId) {
    delay(5000)
    loadSomething()
}
```

如果 Effect 在 `delay()` 过程中被取消：

```text
Coroutine 收到取消请求
→ 支持取消的挂起点响应取消
→ 后续代码不再继续
```

需要注意：

> Coroutine 取消是协作式的，不是强行中断任意普通代码。

如果一直执行不挂起、也不检查取消的纯计算代码，它不会立刻停下来。

---

# 33. LaunchedEffect 的 key

可以使用一个或多个 key：

```kotlin
LaunchedEffect(userId) {
    ...
}
```

也可以：

```kotlin
LaunchedEffect(userId, searchText) {
    ...
}
```

只要任意 key 发生变化，Effect 就会重新启动。

可以把 key 理解成：

> 这个 Effect 的身份由哪些值决定。

---

# 34. key 的比较是值相等语义

`LaunchedEffect` 的 key 可以粗略理解成使用 Kotlin 的：

```kotlin
oldKey == newKey
```

也就是 `equals()` 语义，而不是单纯的引用相同：

```kotlin
a === b
```

例如：

```kotlin
data class User(
    val id: Int,
    val name: String
)
```

两个不同对象：

```kotlin
User(1, "A")
User(1, "A")
```

因为内容相等，所以：

```text
key 被视为未变化
```

---

# 35. 为什么不要原地修改可变对象作为 key

假设：

```kotlin
class User(
    var name: String
)
```

第一次：

```text
oldKey ──→ user(name = "A")
```

然后：

```kotlin
user.name = "B"
```

由于 oldKey 与 newKey 都指向同一个对象：

```text
oldKey ──┐
         ├──→ user(name = "B")
newKey ──┘
```

历史上的：

```text
name = "A"
```

已经不存在于那个对象里。

因此比较时看起来仍然是同一个值。

这也是不可变状态非常重要的原因之一：

```text
旧状态 A
与
新状态 B
```

可以真正作为两个独立快照存在。
