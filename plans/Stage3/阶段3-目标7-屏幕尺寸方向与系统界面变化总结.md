# Stage 3 · 目标 7：屏幕尺寸、方向与系统界面变化总结

## 目标定位

这一目标要理解的是：

> Android App 的界面并不是永远运行在固定尺寸、固定方向、固定系统 UI 环境里。  
> Compose UI 需要能够理解“当前可用窗口有多大”“哪些区域被系统占用”“配置变化后界面和状态会发生什么”。

本阶段只学习概念与代码示例，不进行实际项目练习。

对于未来运行在**专门配发、规格受控手机**上的 App，可以将固定设备、固定方向作为产品约束，不必为了不存在的场景强行实现完整响应式布局；但仍需要理解 Android 的窗口、Insets、配置变化和状态恢复机制。

---

# 1. 屏幕方向不等于窗口尺寸

传统上可以给 Activity 指定固定方向，例如：

```xml
<activity
    android:name=".MainActivity"
    android:screenOrientation="portrait" />
```

这样可以在很多手机场景下锁定竖屏。

但“锁定方向”和“窗口尺寸不会变化”是两回事。

例如：

```text
竖屏手机
┌──────────┐
│   App    │
└──────────┘

进入分屏后

┌─────┐
│ App │
└─────┘
```

方向仍然是竖屏，但 App 实际可用宽度已经发生变化。

因此现代 Android 更强调：

> 不要只根据“手机 / 平板 / 横屏 / 竖屏”判断布局，应该根据 App 当前实际获得的窗口空间判断。

---

# 2. WindowSizeClass

`WindowSizeClass` 用来把连续变化的窗口尺寸划分成几个常用档位。

常见宽度类别包括：

```text
Compact
Medium
Expanded
Large
Extra Large
```

经典三档是：

```text
Compact
Medium
Expanded
```

这些分类和断点由 Android / Jetpack 官方提供，不是应用自己随便定义的名字。

它解决的问题是：

```text
当前窗口有多宽？
        ↓
属于哪个 Size Class？
        ↓
页面应该采用什么大结构？
```

例如：

```text
Compact
↓
单栏列表

Expanded
↓
列表 + 详情双栏
```

重要的是：

> Android 只告诉你当前属于哪个尺寸档位，具体这一档采用什么布局仍然由 App 自己决定。

可以把它理解成一种影响 UI 表达的状态。

---

# 3. WindowInsets

`WindowInsets` 描述的是：

> 当前窗口中，哪些区域正在被系统 UI 或其他系统元素占用。

常见 Insets 包括：

```kotlin
WindowInsets.statusBars
WindowInsets.navigationBars
WindowInsets.ime
WindowInsets.displayCutout
WindowInsets.systemGestures
```

分别对应：

- 状态栏；
- 导航栏；
- 软键盘；
- 刘海 / 挖孔；
- 系统手势区域。

它们不是 UI 控件，而是对占用区域的描述。

---

## 3.1 Edge-to-edge

现代 Android 越来越强调 edge-to-edge：

```text
┌──────────────────────┐
│ App 背景 + status bar│
│                      │
│       App 内容       │
│                      │
│ App 背景 + gesture   │
└──────────────────────┘
```

意思不是“系统栏消失了”，而是：

> App 可以绘制到系统栏后面。

因此真正需要解决的问题是：

- 背景可以延伸；
- 重要文字和按钮不能被状态栏、导航栏、刘海或手势区域挡住。

所以 Insets 的思想不是：

> 系统区域完全不能画。

而是：

> 整个窗口都可以是绘制空间，但某些区域正在和系统 UI 共用，重要内容需要主动避让。

---

## 3.2 常见安全区域

常见组合 Insets：

```kotlin
WindowInsets.safeDrawing
WindowInsets.safeGestures
WindowInsets.safeContent
```

例如：

```kotlin
Modifier.safeDrawingPadding()
```

表示根据当前安全绘制区域自动留出合适空间。

但不应该机械地给整个 App 最外层全部套上安全 padding，否则就会失去 edge-to-edge 的效果。

更合理的是：

```text
背景
↓
允许画到系统栏后面

重要内容
↓
根据 Insets 避让
```

---

## 3.3 IME / 软键盘

软键盘也是 Insets 的一种。

例如：

```kotlin
WindowInsets.ime
```

以及：

```kotlin
Modifier.imePadding()
```

可以让界面在软键盘弹出时为其留出空间。

---

# 4. Scaffold

`Scaffold` 是 Material 3 提供的常见页面骨架布局。

它常见的结构是：

```text
Scaffold
│
├─ topBar
├─ bottomBar
├─ floatingActionButton
└─ content
```

例如：

```kotlin
Scaffold(
    topBar = {
        TopAppBar(
            title = { Text("设备列表") }
        )
    }
) { innerPadding ->

    Column(
        Modifier.padding(innerPadding)
    ) {
        // 页面正文
    }
}
```

---

## 4.1 innerPadding

`Scaffold` 会根据：

- TopAppBar；
- BottomBar；
- 相关 WindowInsets；

计算页面正文应该避让多少空间。

结果通过：

```kotlin
innerPadding
```

交给 content。

需要注意：

> Scaffold 会计算 `innerPadding`，但不会自动把它应用到正文上。

因此正文通常要显式使用：

```kotlin
Modifier.padding(innerPadding)
```

或者 LazyColumn：

```kotlin
LazyColumn(
    contentPadding = innerPadding
)
```

---

## 4.2 Insets consumption

有时会看到：

```kotlin
LazyColumn(
    modifier = Modifier.consumeWindowInsets(innerPadding),
    contentPadding = innerPadding
)
```

两者职责不同：

```text
contentPadding
↓
真正把空间留出来

consumeWindowInsets
↓
告诉后代：
这部分 Insets 已经处理过
```

`consumeWindowInsets()` 本身并不移动 UI，它只是避免后代再次处理同一部分 Insets，从而产生重复 padding。

可以理解成：

```text
布局世界
padding / contentPadding
→ 实际留空间

Insets bookkeeping
consumeWindowInsets
→ 登记这些空间已经处理
```

---

# 5. Screen、Window 与 Constraints

这三个概念需要区分：

```text
Screen
整个物理屏幕

Window
当前 App 实际占到的区域

Constraints
某个具体 Composable 真正能用的区域
```

例如平板分屏：

```text
┌──────────────┬─────────────┐
│   你的 App   │  另一个 App │
│              │             │
└──────────────┴─────────────┘
```

物理 Screen 可能仍然很宽，但 App Window 只剩一半。

因此：

> 布局决策不应该主要依赖物理屏幕尺寸，而应该看当前 Window。

---

## 5.1 Constraints

即使整个 Window 很宽，某个内部组件实际拿到的空间仍然可能很窄。

例如：

```text
┌────────────────────────────────────┐
│             Window 1000dp          │
│                                    │
│  ┌─────────┐ ┌──────────────────┐ │
│  │ Sidebar │ │      Content     │ │
│  │ 300dp   │ │      700dp       │ │
│  └─────────┘ └──────────────────┘ │
└────────────────────────────────────┘
```

Content 内部某张 Card 真正关心的是自己获得的 Constraints。

Compose 布局的基本过程可以理解为：

```text
父组件
   ↓
给子组件 Constraints

子组件
   ↓
在 Constraints 范围内测量自己

子组件
   ↓
返回最终尺寸

父组件
   ↓
决定放在哪里
```

这和很多桌面 UI 框架的 Layout 思路非常接近。

---

## 5.2 BoxWithConstraints

局部组件可以通过类似：

```kotlin
BoxWithConstraints {
    if (maxWidth < 400.dp) {
        Column {
            // 窄布局
        }
    } else {
        Row {
            // 宽布局
        }
    }
}
```

根据自己真正拿到的宽度决定局部布局。

因此可以分成两层：

```text
整个页面的大结构
↓
Window / WindowSizeClass

局部组件自己的结构
↓
Constraints
```

# 6. Configuration

Android 里的“配置”不是某个配置文件，而是运行时的：

```kotlin
Configuration
```

对象。

可以把它想成当前 Android 运行环境的一张快照：

```text
Configuration
├─ orientation
├─ screenWidthDp
├─ screenHeightDp
├─ smallestScreenWidthDp
├─ densityDpi
├─ fontScale
├─ locales
├─ uiMode
└─ ...
```

例如屏幕旋转可能导致：

```text
旧：
orientation = PORTRAIT
screenWidthDp = 412
screenHeightDp = 892

新：
orientation = LANDSCAPE
screenWidthDp = 892
screenHeightDp = 412
```

除了旋转，还有很多 Configuration Change：

- 窗口尺寸变化；
- 深色 / 浅色模式；
- 系统语言变化；
- 字体缩放；
- density 等。

---

# 7. Configuration Change 与 Activity 重建

默认情况下，很多 Configuration Change 会让 Activity 被销毁再创建。

典型流程：

```text
旧 Activity

onPause()
↓
onStop()
↓
onDestroy()

新 Activity

onCreate()
↓
onStart()
↓
onResume()
```

这不是简单的“原 Activity 改了几个属性”，而是：

> 旧 Activity 实例被销毁，新 Activity 实例重新创建。

这样可以让界面、资源和上下文重新基于新 Configuration 建立。

---

# 8. remember、rememberSaveable 与 ViewModel

配置变化导致 Activity 重建后：

```kotlin
remember
```

保存的状态会随旧 Composition 一起消失。

例如：

```kotlin
var count by remember {
    mutableStateOf(0)
}
```

Activity 重建后可能重新变成：

```text
count = 0
```

---

## 8.1 rememberSaveable

```kotlin
var count by rememberSaveable {
    mutableStateOf(0)
}
```

适合保存小型 UI 状态。

可以跨：

```text
recomposition
+
Activity recreation
```

恢复。

例如：

```text
某块 UI 是否展开
当前 tab
文本输入内容
临时选择
```

---

## 8.2 ViewModel

ViewModel 可以跨 Configuration Change 保持。

典型关系：

```text
旧 Activity
  ✕ 销毁

ViewModel
  ✓ 保留

新 Activity
  ↓
重新连接原 ViewModel
```

适合：

- 页面业务状态；
- 设备数据；
- 加载状态；
- 网络 / Repository 相关业务数据。

不要仅仅因为“想跨旋转”就把所有东西都塞进 ViewModel。

状态应该按职责放置。

---

# 9. onConfigurationChanged()

可以在 Manifest 中声明某些配置变化由 Activity 自己处理：

```xml
<activity
    android:name=".MainActivity"
    android:configChanges="orientation|screenSize" />
```

然后：

```kotlin
override fun onConfigurationChanged(newConfig: Configuration) {
    super.onConfigurationChanged(newConfig)
}
```

这时：

```text
Configuration 改变
↓
Activity 不重建
↓
onConfigurationChanged()
```

但需要注意：

```text
configChanges
≠ 禁止配置变化
```

它只是表示：

> 变化仍然发生，但 Activity 不因为这些变化而自动重建，我自己负责处理。

对于纯 Compose UI，读取：

```kotlin
LocalConfiguration.current
```

的 Composable 可以随着新配置重新组合。

---

# 10. 为什么不能把 configChanges 当成状态保存方案

即使处理了 Configuration Change：

```text
Activity 仍然可能因为其他原因被销毁
甚至整个进程可能被系统杀掉
```

因此：

```text
configChanges
```

不能替代：

```text
rememberSaveable
ViewModel
持久化
```

状态生命周期仍然应该正常设计。

---

# 11. 对未来固定设备 App 的实际结论

未来 App 很可能运行在：

```text
专门配发的手机
+
固定设备型号
+
固定屏幕方向
+
固定主要使用场景
```

因此没有必要为了通用 Android App 的全部使用环境而实现复杂 adaptive layout。

可以明确把：

```text
设备规格
方向
窗口范围
```

作为产品约束。

但仍然值得保留这些能力和意识：

- 正确处理 WindowInsets；
- 正确处理状态栏 / 导航栏 / IME；
- 正确理解 Activity recreation；
- UI 状态不要依赖 Activity 永远存在；
- 正确区分 remember / rememberSaveable / ViewModel；
- 理解 Compose 的 Constraints 布局模型。
