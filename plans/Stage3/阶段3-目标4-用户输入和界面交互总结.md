# Stage 3 · 目标 4：处理用户输入和各种界面交互

## 目标

能够理解并实践 Jetpack Compose 中常见的用户输入和界面交互，包括：

- 文本输入；
- 点击与选择；
- 开关类交互；
- 根据当前状态决定操作是否可用；
- 用户操作后的即时界面反馈；
- 使用组件自身的交互 API；
- 使用 `Modifier` 为普通组件增加交互能力；
- 理解交互事件与 UI State 之间的关系。

本目标不要求记住大量具体 API。重点是建立一套通用的交互模型，并能够把用户操作接入前一目标学习过的状态管理流程。

---

# 1. 用户交互的基本闭环

一个常见的界面交互可以概括为：

```text
用户意图
   ↓
界面接受操作
   ↓
产生 Event
   ↓
应用处理 Event
   ↓
State 改变
   ↓
UI 更新并给出反馈
```

它与目标 3 的状态模型正好衔接：

```text
        State
          ↓
用户 → UI
      ↑   ↓
      Event
```

目标 3 主要关注：

```text
Event → State → UI
```

目标 4 则把用户这一端也接了进来：

```text
用户操作 → Event → State → UI 反馈
```

---

# 2. UI State 与 Event 在交互中的两个方向

Compose 中很多交互组件都有类似的结构。

例如：

```kotlin
OutlinedTextField(
    value = uiState.text,
    onValueChange = onTextChange
)
```

可以理解成两个方向：

```text
value           State → UI
onValueChange   UI → Event
```

`Switch` 也是一样：

```kotlin
Switch(
    checked = uiState.isReviewMode,
    onCheckedChange = onReviewModeChange
)
```

对应：

```text
checked           State → UI
onCheckedChange   UI → Event
```

因此，不必把 `TextField`、`Switch`、`Checkbox` 等组件分别理解成完全不同的机制。

它们通常都符合：

```text
当前值进入组件
        ↓
组件显示当前状态

用户进行操作
        ↓
组件通过回调报告事件
```

---

# 3. Event 应尽量表达“用户意图”

按钮的底层事实是：

```text
用户点击了一块区域
```

但应用真正关心的通常不是“发生了一次点击”，而是：

```text
用户想提交
用户想开始学习
用户想删除
用户想切换模式
```

因此，相比把大量逻辑直接写进：

```kotlin
onClick = {
    // 很多处理代码
}
```

更常见的写法是让 UI 暴露有意义的事件：

```kotlin
Button(
    onClick = onStartClick
) {
    Text("开始学习")
}
```

这样 Composable 表达的是：

```text
这里存在一个“开始学习”的用户意图
```

而事件的实际处理可以交给状态拥有者，例如 `ViewModel`。

这和目标 3 中的状态提升是同一套思路。

---

# 4. 组件自身的交互 API

Compose 的高层组件通常已经带有相应的交互入口。

例如：

```kotlin
Button(
    onClick = onStartClick
)
```

```kotlin
OutlinedTextField(
    value = uiState.text,
    onValueChange = onTextChange
)
```

```kotlin
Switch(
    checked = uiState.isReviewMode,
    onCheckedChange = onReviewModeChange
)
```

这些组件已经处理了大量底层输入细节。

因此，在普通界面开发中，优先使用组件提供的高层交互 API 即可。

---

# 5. Modifier 可以给普通 UI 增加交互能力

并不是所有 Composable 天生都是交互组件。

例如普通 `Text`：

```kotlin
Text("展开说明")
```

可以通过：

```kotlin
Text(
    text = "展开说明",
    modifier = Modifier.clickable {
        // 处理点击
    }
)
```

增加点击能力。

可以把它理解成：

```text
Composable
    +
Modifier
    ↓
附加布局、绘制、交互等能力
```

因此：

```text
Button(onClick)
```

表示：

> 这个组件本身就是按钮。

而：

```text
Text + Modifier.clickable
```

表示：

> 给一个普通组件额外增加点击行为。

---

# 6. Modifier 的顺序会影响交互区域

实践中比较了：

```kotlin
Modifier
    .clickable { ... }
    .padding(16.dp)
```

和：

```kotlin
Modifier
    .padding(16.dp)
    .clickable { ... }
```

两者的点击范围不同。

可以粗略理解为：

```text
clickable(padding(Content))
```

与：

```text
padding(clickable(Content))
```

不是同一种结构。

前一种情况下，`padding` 所占的区域也位于可点击范围内，因此点击区域更大。

这说明 Modifier 并不是一组互不相关的配置项，而是按顺序作用的一条链。

以后同时使用：

- `padding`
- `background`
- `clip`
- `clickable`

等 Modifier 时，都应该意识到顺序可能影响最终布局、绘制和交互效果。

---

# 7. 当前状态决定“现在能不能操作”

交互不只是响应用户动作，还需要根据当前 State 决定哪些操作有效。

例如：

```kotlin
val canStart = uiState.text.isNotBlank()
```

然后：

```kotlin
Button(
    onClick = onStartClick,
    enabled = canStart
) {
    Text("开始学习")
}
```

这里形成了：

```text
uiState.text
    ↓
canStart
    ↓
Button.enabled
```

也就是说：

> 当前 State 不只决定“界面显示什么”，也决定“用户现在能做什么”。

这是交互设计中非常常见的一部分。

---

# 8. 用户操作后应该得到明确反馈

完整交互不是：

```text
用户操作 → 执行代码
```

而应该形成：

```text
用户操作
   ↓
应用处理
   ↓
用户能够观察到结果
```

例如：

```kotlin
Text(
    if (uiState.isReviewMode) {
        "当前模式：复习"
    } else {
        "当前模式：学习"
    }
)
```

当用户切换 `Switch` 后：

```text
Switch
   ↓
onReviewModeChange
   ↓
UiState.isReviewMode 改变
   ↓
Text 更新
```

这就是一次完整的交互反馈。

反馈以后还可能表现为：

- 文本变化；
- 控件选中状态变化；
- 按钮变为可用 / 不可用；
- Loading；
- 成功状态；
- 错误提示；
- 页面变化。

这些具体形式不同，但基本模型相同。

# 9. 本目标实践：学习设置

本目标最终使用了一个简单的“学习设置”界面来串起这些内容。

大致结构：

```text
学习主题：[ Android          ]

复习模式：        [Switch]

[开始学习]

当前模式：复习
```

其中：

### 文本输入

```kotlin
OutlinedTextField(
    value = uiState.text,
    onValueChange = onTextChange
)
```

### 模式选择

`UiState` 中增加：

```kotlin
val isReviewMode: Boolean = false
```

`ViewModel` 处理事件：

```kotlin
fun onReviewModeChange(checked: Boolean) {
    _uiState.update { oldState ->
        oldState.copy(
            isReviewMode = checked
        )
    }
}
```

UI：

```kotlin
Switch(
    checked = uiState.isReviewMode,
    onCheckedChange = onReviewModeChange
)
```

### 操作是否可用

```kotlin
val canStart = uiState.text.isNotBlank()
```

```kotlin
Button(
    onClick = onStartClick,
    enabled = canStart
) {
    Text("开始学习")
}
```

### 即时反馈

```kotlin
Text(
    if (uiState.isReviewMode) {
        "当前模式：复习"
    } else {
        "当前模式：学习"
    }
)
```

整个流程可以概括成：

```text
输入学习主题
      +
选择学习模式
      ↓
UiState 更新
      ↓
界面立即反映当前状态
      ↓
根据状态决定是否允许开始
      ↓
用户点击开始
```

这个例子已经包含了普通应用界面中最常见的一套交互闭环。

# 10. 焦点和软键盘

本目标中还简单接触了输入框相关的：

- `KeyboardOptions`
- `KeyboardActions`
- `ImeAction`
- `FocusManager`

例如：

```kotlin
keyboardOptions = KeyboardOptions(
    imeAction = ImeAction.Done
)
```

以及：

```kotlin
keyboardActions = KeyboardActions(
    onDone = {
        focusManager.clearFocus()
    }
)
```

它们分别涉及：

```text
KeyboardOptions
→ 配置输入法希望如何表现

KeyboardActions
→ 响应输入法动作

FocusManager
→ 管理 Compose 焦点
```

这些属于具体输入场景中的工具，不是目标 4 的核心主线。

本次实践中模拟器的软键盘显示存在环境问题，因此没有继续深入排查；这不影响对交互模型本身的理解。

# 11. 本目标真正需要掌握的东西

不需要记住每一种交互组件的 API。

更重要的是看到一个界面时，能够判断：

```text
用户现在能做什么？
        ↓
这个动作表达什么意图？
        ↓
对应什么 Event？
        ↓
谁处理这个 Event？
        ↓
State 如何改变？
        ↓
UI 如何反馈？
```

最终可以压缩成：

```text
State
  ↓
决定 UI 显示什么
以及当前允许什么操作
  ↓
用户交互
  ↓
Event
  ↓
状态拥有者处理
  ↓
新的 State
  ↓
新的 UI
```

这套模型并不是 Compose 独有的。

Compose 的特点主要在于：

- UI 本身由 State 描述；
- 交互通常通过回调向外报告；
- State 改变后重新驱动 UI；
- `Modifier` 可以组合式地为 UI 增加交互等能力。

# 12. 阶段结论

完成目标 4 后，已经可以把目标 3 和目标 4 连成一条完整主线：

```text
用户
 ↓
Interaction
 ↓
Event
 ↓
ViewModel / 状态拥有者
 ↓
State
 ↓
Compose UI
 ↓
用户看到反馈
```

到这里，已经不只是“会写 Button 和 TextField”，而是能够理解 Compose 界面中用户操作、事件、状态和界面更新之间的完整关系。

后续遇到新的交互组件时，优先把它放回这条链里理解，而不是单独记忆 API。
