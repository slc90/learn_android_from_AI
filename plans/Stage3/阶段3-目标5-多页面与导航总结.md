# 阶段3・目标5：多页面与 Navigation 3 总结

## 1. 这一节学到了什么

这一节的核心目标，是把应用从“单页面 UI”推进到“多个页面之间可以导航，并且每个页面拥有自己的状态与生命周期”。

最终形成的基本结构：

```text
Stage3App
│
├─ rememberNavBackStack(...)
│
├─ SetupRoute
│  ├─ SetupScreen
│  └─ SetupViewModel
│
└─ StudyRoute(topic)
   ├─ StudyScreen
   └─ StudyViewModel
```

---

## 2. Navigation 3 的最小模型

Navigation 3 可以先理解成三部分：

```text
NavKey
  ↓
backStack
  ↓
NavDisplay
```

### NavKey

`NavKey` 表示“导航到哪个页面”。

没有参数的页面可以使用：

```kotlin
@Serializable
data object SetupRoute : NavKey
```

需要携带参数时，可以使用 `data class`：

```kotlin
@Serializable
data class StudyRoute(
    val topic: String
) : NavKey
```

经验规则：

```text
无参数页面 → data object
有参数页面 → data class
```

---

## 3. backStack 是导航状态

创建导航栈：

```kotlin
val backStack = rememberNavBackStack(SetupRoute)
```

前进到 Study：

```kotlin
backStack.add(
    StudyRoute(topic = "Android")
)
```

此时：

```text
[SetupRoute, StudyRoute("Android")]
```

返回：

```kotlin
backStack.removeLastOrNull()
```

变回：

```text
[SetupRoute]
```

Navigation 3 的关键思想仍然是声明式：

```text
backStack 状态变化
        ↓
NavDisplay 观察到变化
        ↓
显示新的栈顶页面
```

所以 `backStack.add(...)` 并不是直接调用某个 `Screen()`。

---

## 4. NavDisplay 负责把 Route 映射成页面

```kotlin
NavDisplay(
    backStack = backStack,
    onBack = {
        backStack.removeLastOrNull()
    },
    entryProvider = entryProvider {
        entry<SetupRoute> {
            SetupScreen(...)
        }

        entry<StudyRoute> { route ->
            StudyScreen(
                topic = route.topic
            )
        }
    }
)
```

其中：

```kotlin
entry<StudyRoute> { route ->
```

这里的 `route` 就是实际加入 back stack 的那个 `StudyRoute` 实例。

例如：

```kotlin
backStack.add(StudyRoute("Android"))
```

那么：

```kotlin
route.topic == "Android"
```

---

## 5. “导航图”与“back stack”不是一回事

应用允许的页面关系可以是网状的：

```text
      B ───→ D
     ↗       ↑
A ──         │
     ↘       │
      C ─────┘
```

它描述的是：

```text
哪些页面可以跳到哪些页面
```

但用户一次真实运行只会走一条路径。

例如：

```text
A → B → D
```

那么 back stack 是：

```text
[A, B, D]
```

另一轮可能是：

```text
A → C → D
```

那么：

```text
[A, C, D]
```

所以：

```text
静态导航关系
= 所有可能路径

back stack
= 本次实际走过的路径
```

back stack 本身始终是线性的。

---

## 6. Screen 不应该直接操作 backStack

页面最好只表达“用户做了什么”，而不是自己知道 Navigation 3 的具体实现。

例如：

```kotlin
@Composable
fun SetupScreen(
    onStartStudy: (String) -> Unit,
    viewModel: SetupViewModel = viewModel()
) {
    Button(
        onClick = {
            onStartStudy(viewModel.text)
        }
    ) {
        Text("开始学习")
    }
}
```

真正导航放在上层：

```kotlin
entry<SetupRoute> {
    SetupScreen(
        onStartStudy = { topic ->
            backStack.add(
                StudyRoute(topic)
            )
        }
    )
}
```

职责变成：

```text
Screen
→ 发出语义事件

Stage3App
→ 决定这个事件对应怎样的导航
```

这样 Screen 不依赖 Navigation 3，本身也更容易复用。

---

## 7. 每个页面使用独立 ViewModel

一开始直接在 Screen 中调用：

```kotlin
viewModel<Stage3ViewModel>()
```

如果没有额外配置，通常会使用外层 Activity 提供的 `ViewModelStoreOwner`，多个页面可能因此取得同一个 Activity 级 ViewModel。

为了让 ViewModel 跟随 NavEntry，需要给 Navigation 3 加 ViewModelStore decorator。

依赖：

```kotlin
implementation(libs.androidx.lifecycle.viewmodel.navigation3)
```

然后：

```kotlin
NavDisplay(
    backStack = backStack,
    entryDecorators = listOf(
        rememberSaveableStateHolderNavEntryDecorator(),
        rememberViewModelStoreNavEntryDecorator()
    ),
    ...
)
```

此时结构变成：

```text
SetupRoute NavEntry
└─ ViewModelStore
   └─ SetupViewModel

StudyRoute NavEntry
└─ ViewModelStore
   └─ StudyViewModel
```

例如：

```kotlin
class SetupViewModel : ViewModel() {
    var text by mutableStateOf("")
        private set

    fun onTextChange(value: String) {
        text = value
    }
}
```

```kotlin
class StudyViewModel : ViewModel() {
    var count by mutableIntStateOf(0)
        private set

    fun increase() {
        count++
    }
}
```

这样两页的状态真正分开了。

---

## 8. NavEntry 与 ViewModel 生命周期

这是这一节很重要的一点。

进入 Study：

```text
[SetupRoute, StudyRoute]
```

此时：

```text
SetupViewModel 存活
StudyViewModel 存活
```

从 Study 返回：

```text
[SetupRoute, StudyRoute]
          ↓ pop
[SetupRoute]
```

于是：

```text
StudyRoute 被移出栈
→ 对应 ViewModelStore 被清理
→ StudyViewModel.onCleared()
```

而 SetupRoute 仍然在栈里，因此：

```text
SetupViewModel 继续存活
```

所以实验结果是：

```text
Setup 输入内容
→ 返回后仍然存在

Study count
→ 返回后 StudyViewModel 被销毁
→ 再次进入 Study 时重新从 0 开始
```

这说明 ViewModel 的生命周期已经从：

```text
Activity 级
```

变成：

```text
NavEntry 级
```

## 9. 页面返回按钮与系统返回统一

系统返回已经通过：

```kotlin
onBack = {
    backStack.removeLastOrNull()
}
```

处理。

页面上的返回按钮也应该走同一逻辑。

可以先统一一个函数：

```kotlin
val navigateBack: () -> Unit = {
    backStack.removeLastOrNull()
}
```

然后：

```kotlin
NavDisplay(
    onBack = navigateBack,
    ...
)
```

Study 页面：

```kotlin
StudyScreen(
    topic = route.topic,
    onBack = navigateBack
)
```

页面内部：

```kotlin
Button(
    onClick = onBack
) {
    Text("返回")
}
```

于是：

```text
系统返回
       ┐
       ├→ navigateBack()
页面返回┘
          ↓
backStack.removeLastOrNull()
```

页面本身仍然只知道：

```text
用户想返回
```

而不知道 Navigation 3 的实现细节。

## 10. rememberNavBackStack 不是全局单例

```kotlin
val backStack = rememberNavBackStack(...)
```

得到的是当前 Composition 调用位置拥有的状态，不是全局对象。

例如：

```kotlin
@Composable
fun A() {
    val backStack = rememberNavBackStack(RouteA)
}
```

和：

```kotlin
@Composable
fun B() {
    val backStack = rememberNavBackStack(RouteB)
}
```

会得到两个独立 back stack。

现在整个 Stage3 共用同一个导航栈，是因为只在 `Stage3App` 创建一次：

```text
Stage3App
└─ backStack
   ├─ NavDisplay 使用它
   ├─ Setup 导航回调使用它
   └─ Study 返回回调使用它
```

因此：

```text
共享来自“同一个实例被向下使用”
而不是 rememberNavBackStack 是全局的
```

## 11. Activity 重建与导航状态恢复

`rememberNavBackStack(...)` 不只是普通 `remember`。

当 Route 是可保存的 `NavKey` 时，导航栈可以在 Activity 重建时恢复。

例如原本：

```text
[SetupRoute, StudyRoute("Android")]
```

屏幕旋转导致 Activity 重建后，仍然可以恢复成：

```text
[SetupRoute, StudyRoute("Android")]
```

因此用户仍然处于 Study 页面。

### ViewModel 要区分两种情况

普通配置变化，例如旋转：

```text
Activity 重建
→ NavEntry 仍然恢复
→ 对应 ViewModel 状态继续保留
```

因此：

```text
Study count = 5
↓
旋转
↓
Study count 仍然 = 5
```

但是如果整个进程被系统杀死：

```text
进程死亡
→ ViewModel 实例全部消失
```

之后重新恢复时：

```text
Navigation back stack
→ 可以恢复

ViewModel 内普通内存状态
→ 不会自动恢复
```

如果某些状态需要跨进程死亡恢复，需要另外使用：

```text
SavedStateHandle
rememberSaveable
持久化存储
```

## 12. 这一节最终建立的职责边界

可以把现在的架构压缩成：

```text
UI
→ 展示状态
→ 发出用户事件

ViewModel
→ 管理页面自己的状态

Route / NavKey
→ 描述要去哪个页面，以及必要导航参数

Stage3App
→ 持有 backStack
→ 决定页面之间如何导航

NavDisplay
→ 根据 backStack 显示当前页面

NavEntry
→ 提供页面级生命周期与 ViewModel scope
```

最终数据与事件流大致是：

```text
用户点击
   ↓
Screen 发出事件
   ↓
导航层修改 backStack
   ↓
NavDisplay 显示新的 NavEntry
   ↓
页面获得自己的 ViewModel
```

返回时则反过来：

```text
返回事件
   ↓
backStack pop
   ↓
NavEntry 被移除
   ↓
对应页面 ViewModel 被清理
   ↓
显示前一个页面
```

---

## 13. 本节一句话总结

> Navigation 3 的核心不是“调用某个跳转函数去打开页面”，而是维护一份 back stack 状态；NavDisplay 根据它显示页面，而每个 NavEntry 又可以拥有自己独立的 ViewModel 与生命周期。
