# Stage 5 · 目标 1：理解 C++ 在 Android 应用中的定位与适用场景

## 这一节的核心

在 Android 开发里，C++ 通常不是用来取代 Kotlin 写整个 App 的。

更合适的理解是：

> **Android App 的主体仍然由 Kotlin / Android Framework / Jetpack Compose 负责，C++ 作为 Native 层的一块能力，被嵌入应用中处理更适合它的任务。**

---

## C++ 在 Android 里的位置

可以先用这个最小模型理解：

```text
Android App
│
├─ Kotlin / Compose
│   ├─ UI
│   ├─ 生命周期
│   ├─ 权限
│   ├─ 数据库 / 网络
│   └─ 大部分业务逻辑
│
└─ C++ Native 模块
    ├─ 计算密集型任务
    ├─ 已有 C / C++ 算法
    └─ 第三方 C / C++ 库
```

所以：

- Kotlin / Android 层主要负责“这个 App 是什么、怎么和系统与用户交互”
- C++ 层主要负责“某些更适合 Native 实现的能力”

---

## 典型适用场景

C++ 在 Android 中常见于这些方向：

- 复用已有的 C / C++ 代码或成熟库
- 数值计算、矩阵运算
- 图像处理
- 音视频处理
- 信号处理
- 游戏引擎
- 其他计算密集、低延迟或已有 Native 生态的功能

这一阶段后面要使用的 Eigen，就是很典型的例子。

大致调用关系可以先理解成：

```text
Compose 界面
    ↓
Kotlin 收集参数
    ↓
C++ + Eigen 执行矩阵计算
    ↓
结果返回 Kotlin
    ↓
Compose 显示结果
```

---

## 哪些东西通常不属于 C++ 的主战场

下面这些仍然更适合放在 Kotlin / Android 层：

- Compose UI
- Activity
- 页面导航
- 生命周期处理
- 权限申请
- Room 数据库
- 普通网络请求
- 一般业务逻辑

不能因为“C++ 性能高”就默认把这些逻辑搬过去。

---

## 一个容易误解的点

> **使用 C++ 不等于整个 App 会自动变快。**

引入 Native 层本身会增加：

- Kotlin 与 C++ 之间的调用边界
- Native 构建流程
- 调试复杂度
- 维护成本

所以 C++ 是一种有明确用途的工具，而不是 Android 开发中的默认选择。

---

## 目标 1 和目标 10 的区别

这两个目标容易混在一起。

### 目标 1

关注的是：

> **C++ 在 Android 里通常适合干什么？**

现在只需要建立定位和场景认识。

例如：

> 矩阵计算是 C++ 的典型候选场景。

### 目标 10

关注的是：

> **面对一个具体功能，综合性能收益、调用成本、维护成本后，到底值不值得真的放进 C++？**

例如：

> 一个 10×10 的矩阵，每秒只算一次，还有没有必要跨 Native 边界交给 C++？

这是后面真正的工程判断问题。

---

## 现在先记住

1. **Android App 的主体仍然是 Kotlin / Android Framework。**
2. **C++ 是嵌入 App 的 Native 能力层，不是另一个独立 App。**
3. **它最常见的价值是复用 C / C++ 生态，以及承担适合 Native 的计算任务。**
4. **不是所有逻辑都值得搬到 C++；具体值不值得，是目标 10 再解决的问题。**
