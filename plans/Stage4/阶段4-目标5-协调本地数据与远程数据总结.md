# Stage 4 · 目标 5：协调本地数据与远程数据

## 目标

理解 Android 应用中本地数据与远程数据如何协调，以及 Repository 在这个过程中的职责边界。

这一节重点是建立设计判断，不做具体实践代码。

---

## 1. 本地数据与远程数据的核心问题

当一个 App 同时存在：

- 本地数据，例如 Room；
- 远程数据，例如网络 API；

真正需要先决定的并不是 API 怎么写，而是：

> App 到底应该相信哪一份数据？

这本质上是一个数据所有权和同步策略的问题。

---

## 2. 一个常见的数据流模型

一个比较清晰的组织方式是：

```text
                 ┌→ Network
                 │
UI ← ViewModel ← Repository
                 │
                 └→ Room
```

更具体地看，常见的数据流是：

```text
Network
   ↓
Repository
   ↓
Room
   ↓
Flow
   ↓
ViewModel
   ↓
UI
```

这里最重要的一点是：

> UI 不要同时直接依赖 Room 和 Network 两套数据源。

否则很容易出现：

- 两边数据不一致；
- UI 不知道应该显示哪一份；
- 网络结果和本地 Flow 相互覆盖；
- 状态变化难以推理。

---

## 3. Source of Truth

一种很常见的设计是：

> Room 作为 App 上层主要读取的数据来源，Network 负责让 Room 变新。

于是可以把两种操作分开：

```text
读取数据
≠
刷新数据
```

例如：

```text
observeData()
    ↓
Room
    ↓
Flow
    ↓
UI
```

而刷新则是：

```text
refresh()
    ↓
Network
    ↓
写入 Room
    ↓
Room Flow 发出新数据
    ↓
UI 更新
```

这样 UI 的读取路径始终保持稳定。

---

## 4. 本地数据到底是什么

设计同步策略前，要先判断本地数据的性质。

### 纯缓存

例如：

- 新闻；
- 天气；
- 商品目录；
- 服务器生成的数据。

这种情况下，远程数据通常是真正的数据来源，本地只是副本。

可以简单理解为：

```text
Network
   ↓
Room
```

远程数据回来以后，可以直接更新或覆盖本地缓存。

---

### 用户真实数据

例如：

- 用户离线编辑的笔记；
- 尚未上传的表单；
- 本地创建但还没同步的记录。

这时候本地数据不能再当成“可以随便覆盖的缓存”。

可能需要记录：

```text
是否被本地修改
是否已同步
最后修改时间
```

例如：

```kotlin
data class NoteEntity(
    val id: Long,
    val text: String,
    val isDirty: Boolean,
)
```

其中：

```text
isDirty = true
```

可以表示：

> 这条数据已经在本地修改，但还没有成功同步到服务器。

这时 Room 承载的是用户当前真实状态，而不只是缓存。

---

## 5. 同步首先是设计问题

本地和远程如何协调，没有一套适用于所有业务的固定答案。

真正要先确定的是：

```text
谁是 source of truth？
本地只是缓存，还是用户真实数据？
远程回来后是覆盖、合并，还是保留本地修改？
失败以后保留什么状态？
```

所以：

> 本地数据与远程数据的协调，本质上首先是数据所有权和同步策略的设计问题。

具体 API 和实现方式是在这些规则确定以后才有意义。

---

# Repository 的边界

## 6. Repository 负责什么

Repository 的主要职责可以理解为：

> 隐藏具体数据来源，并协调数据访问。

它比较适合负责：

- 从哪里取数据；
- 数据保存到哪里；
- 本地和远程怎么协调；
- 缓存怎么处理；
- 数据源失败以后怎么降级；
- 向上层隐藏 Room、Retrofit、文件系统等具体实现。

例如：

```kotlin
articleRepository.getArticles()
articleRepository.refreshArticles()
articleRepository.saveArticle()
```

上层不需要知道这些操作内部到底用了：

```text
Room
Network
File
或者多个数据源组合
```

---

## 7. Repository 不应该负责所有业务逻辑

Repository 很容易被误用成：

```text
所有不知道放哪里的代码
        ↓
Repository
```

最后变成：

```text
Repository
├─ 网络请求
├─ 数据库
├─ 缓存
├─ 用户权限判断
├─ 价格计算
├─ 订单规则
├─ 页面流程
└─ 大量业务判断
```

这样 Repository 就失去了清晰的职责边界。

---

## 8. 数据访问规则和业务规则的区别

可以这样区分：

```text
Repository
关注：
数据从哪来
怎么存
怎么同步
怎么读取
```

而业务逻辑关注的是：

```text
拿到这些数据以后
按照什么产品规则做决定
```

例如：

```kotlin
val user = userRepository.getUser()
val orders = orderRepository.getOrders()
```

Repository 负责提供 `user` 和 `orders`。

但是：

```text
这个用户是否满足优惠券领取条件？
```

这通常属于业务规则，而不是 Repository 的天然职责。

---

## 9. 最终记住

这一节最重要的几个结论：

1. 本地和远程数据如何协调，首先是设计问题，而不是 API 问题。
2. UI 最好不要同时直接依赖多套数据源。
3. 要先明确谁是 source of truth。
4. 本地是缓存还是用户真实数据，会直接影响同步策略。
5. Repository 负责隐藏和协调数据源。
6. Repository 不应该承包整个业务逻辑。

最简洁的一句话可以记成：

> Repository 隐藏数据来源，不负责承包整个业务。
