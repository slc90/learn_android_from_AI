# Stage 4 目标 1 总结：Android 应用中的数据组织与流动

## 这一目标要解决什么

Stage 4 开始，我们从“把界面做出来”转向：

- 数据从哪里来？
- 谁负责管理数据？
- 页面状态由谁产生？
- 用户操作后，数据怎样回到 UI？

目标 1 的作用主要是建立后面整个 Stage 4 的“总地图”。

---

## 1. 应用数据和界面状态不是一回事

### 应用数据

应用真正关心的数据，本身不依赖某个页面是否存在。

例如：

```kotlin
data class Todo(
    val id: Int,
    val title: String,
    val completed: Boolean
)
```

即使当前没有界面显示它，这条 Todo 仍然有意义，也可能保存在数据库中。

### 界面状态（UI State）

为了让某个页面正确显示而整理出来的数据。

例如：

```kotlin
data class TodoScreenState(
    val todos: List<Todo>,
    val isLoading: Boolean,
    val selectedTodoId: Int?,
    val errorMessage: String?
)
```

其中：

- `todos` 可能来自应用数据；
- `isLoading`、`selectedTodoId`、`errorMessage` 更偏向当前页面的显示需要。

简单 App 中，两者可能非常接近；复杂后就会明显分开。

---

## 2. 单向数据流

核心方向：

```text
状态 / 数据
    ↓
   UI
    │
    │ 用户操作
    ↓
业务处理
```

更完整一点：

```text
数据源 → Repository → ViewModel → UI State → Compose UI
  ↑                                        │
  └──────────── 用户操作 / 事件 ────────────┘
```

可以记成一句话：

> 状态向 UI 流，事件从 UI 往回传。

---

## 3. 数据源（Data Source）

数据实际来自哪里，例如：

```text
数据库
网络服务器
本地文件
```

数据源负责真正的读写。

---

## 4. Repository

Repository 位于具体数据来源和应用其他部分之间。

它的主要意义是：

> 上层只需要向 Repository 要数据，不必知道数据到底来自数据库、网络还是其他地方。

例如：

```text
数据库
  ↓
TodoRepository
  ↓
List<Todo>
```

当多个页面都需要相同数据时，Repository 尤其有价值：

```text
                 ┌→ TodoListViewModel
TodoRepository ──┤
                 └→ TodoDetailViewModel
```

Repository 主要关注“数据本身”，而不是某个具体页面应该怎么显示。

---

## 5. ViewModel

可以先理解成：

> 页面背后的状态管理者。

典型职责：

```text
Repository 提供应用数据
        ↓
ViewModel 获取、组合、转换
        ↓
产生 UI State
        ↓
Compose 显示
```

ViewModel 关心的是：

- 当前页面需要哪些数据；
- 页面现在是什么状态；
- 用户事件到来后应该触发什么处理。

---

## 6. Compose UI

Compose UI 主要做两件事：

1. 根据 UI State 显示界面；
2. 把用户操作表达成事件，交给 ViewModel。

例如：

```kotlin
onClick = {
    viewModel.completeTodo(todo.id)
}
```

UI 不应该自己直接承担数据库读写等职责。

---

## 7. 数据变化后，UI 可以自动更新吗？

可以，但前提是先把“可观察的数据流”接好。

例如 Repository 暴露：

```kotlin
val todos: Flow<List<Todo>>
```

ViewModel 持续观察它，再产生新的 `uiState`。

Compose 再观察 ViewModel 中的状态：

```kotlin
val state by viewModel.uiState.collectAsState()
```

于是链路可以变成：

```text
Repository 数据变化
        ↓
ViewModel 收到新数据
        ↓
UI State 更新
        ↓
Compose 自动重组
```

所以不是“隔空自动感应”，而是：

> 开发者负责建立监听关系；关系接好以后，变化可以自动传播。

---

## 8. Repository 和 ViewModel 为什么要分开

最简单的区分：

```text
Repository
关注：数据本身

ViewModel
关注：这个页面怎么使用这些数据

Compose
关注：把状态画出来
```

例如：

Repository 可以负责：

```text
读取 Todo
保存 Todo
删除 Todo
修改 completed
```

ViewModel 可以负责：

```text
当前是否加载中
页面应该显示哪些 Todo
发生错误时显示什么
用户点击后该触发什么操作
```

不要让“数据怎么取得”和“页面怎么表现”粘死在一起。

---

## 9. 分层不是越多越好

这套结构：

```text
数据源
  ↓
Repository
  ↓
ViewModel
  ↓
UI State
  ↓
Compose
```

是方向，不是要求每个小功能都机械地凑齐所有层。

例如单纯的计数器：

```text
点按钮 → 数字 +1 → UI 更新
```

可能根本不需要 Repository。

真正值得拆层，通常是因为：

- 有数据库、网络、文件等真实数据来源；
- 数据来源不止一个；
- 多个页面需要共享同一批数据；
- 页面状态和数据访问开始变复杂。

判断标准不是“标准架构有几层”，而是：

> 这个职责有没有复杂到值得单独隔开。

---

## 10. 目标 1 最终要留下的心智模型

```text
           数据向 UI 流动
                  ↓

数据源 → Repository → ViewModel → UI State → Compose
                                      ↑
                                      │
              用户事件 ───────────────┘
```

现在先记住三件事：

1. **数据要有明确来源。**
2. **状态向下流，事件向上走。**
3. **数据访问和页面表现尽量不要粘死。**

---

## 11. 为什么目标 1 暂时不单独实践

目标 1 更像 Stage 4 的总地图。

后面的目标会逐步把这条链中的各个部分真正写出来：

```text
目标 2  本地数据保存与读取
          ↓
目标 3  本地数据库
          ↓
目标 4  网络数据
          ↓
目标 5  本地与远程数据协调
          ↓
目标 6  异步处理
          ↓
目标 7  UI / 业务逻辑 / 数据访问分离
          ↓
目标 8~9  加载、失败、重试、恢复等真实状态
          ↓
目标 10  串成完整的数据驱动 App
```

所以现在不必为了目标 1 单独造一个假的完整架构 Demo。

等后面第一次真正把：

```text
本地数据 → Repository → ViewModel → UI State → Compose
```

跑通时，目标 1 就从“理解了”变成“实际用过了”。
