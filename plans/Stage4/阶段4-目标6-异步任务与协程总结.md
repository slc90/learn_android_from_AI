# Stage 4 · 目标 6：异步任务在业务逻辑中的基本处理方式

## 目标

理解 Android / Kotlin 中业务层常见异步任务的基本处理方式，包括：

- `suspend`
- `CoroutineScope` / `viewModelScope`
- `launch` / `async` / `await`
- `Dispatcher`
- `withContext`
- 挂起与阻塞的区别
- 结构化并发
- 取消与异常传播
- `supervisorScope` / `SupervisorJob`
- Repository 的 main-safe 思路
- `Flow` / `StateFlow` / `SharedFlow`

---

## 1. 协程的核心直觉

协程不是“新开一个线程”。

它更准确的作用是：

> 让一段异步逻辑可以在执行过程中挂起，等结果准备好以后再继续执行，而不必一直占住当前线程。

关键区别：

```text
suspend
→ 协程暂停
→ 当前线程可以去干别的事

block
→ 当前线程被卡住
→ 只能原地等待
```

因此：

```kotlin
suspend fun loadData()
```

只表示这个函数**允许挂起**。

它并不意味着：

- 自动切到后台线程
- 自动变成并发任务
- 函数内部的阻塞调用自动安全

---

## 2. CoroutineScope 与 viewModelScope

`CoroutineScope` 可以理解为：

> “这些协程任务属于谁，由谁管理生命周期。”

Android 中常见：

```kotlin
viewModelScope.launch {
    repository.refresh()
}
```

表示：

> 启动一个属于当前 `ViewModel` 的协程任务。

当 `ViewModel` 生命周期结束时，对应任务会被取消。

这体现了 Kotlin 协程的**结构化并发**思想：

```text
Scope
├── Coroutine A
├── Coroutine B
└── Coroutine C
```

子任务不会变成无人管理的后台任务。

---

## 3. launch 与 async

### launch

```kotlin
viewModelScope.launch {
    repository.refresh()
}
```

用于：

> 启动一个不需要返回业务结果的协程任务。

返回：

```text
Job
```

---

### async

```kotlin
val result = async {
    repository.loadUser()
}
```

用于：

> 启动一个会产生结果的并发任务。

返回：

```text
Deferred<T>
```

通过：

```kotlin
val user = result.await()
```

取得结果。

可以粗略类比 C#：

```text
Kotlin Deferred<T>
≈ C# Task<T>
```

需要注意：

```kotlin
async { ... }
```

默认在调用 `async` 时就开始执行。

不是等到 `await()` 才开始。

---

## 4. async 不等于后台线程

例如：

```kotlin
viewModelScope.launch {
    val result = async {
        loadData()
    }
}
```

这个 `async` 默认继承父协程上下文。

因此如果父协程在 Main：

```text
viewModelScope
→ Main

async
→ 默认仍然 Main
```

`async` 解决的是：

> 是否启动一个新的并发协程。

不是：

> 是否切换线程。

---

## 5. 挂起点与线程占用

协程只有在真正能够挂起的地方，才会把当前线程让出来。

例如：

```kotlin
delay(1000)
```

属于挂起：

```text
协程暂停
线程释放
```

而：

```kotlin
Thread.sleep(1000)
```

属于阻塞：

```text
线程停在那里等 1 秒
```

所以即使写在：

```kotlin
suspend fun foo()
```

里面：

```kotlin
Thread.sleep(...)
```

依然会阻塞线程。

`suspend` 修饰符本身不会把阻塞 API 变成非阻塞 API。

---

## 6. Dispatcher 与 withContext

常见 Dispatcher：

```text
Dispatchers.Main
→ UI / 主线程相关任务

Dispatchers.IO
→ 阻塞型 I/O

Dispatchers.Default
→ CPU 密集型计算
```

使用：

```kotlin
suspend fun loadFile(): Data =
    withContext(Dispatchers.IO) {
        blockingReadFile()
    }
```

`withContext` 可以理解为：

> 当前协程暂时去另一个执行上下文完成一段工作，结束后再回来继续。

它不是为了制造并发，而是为了切换执行环境。

---

## 7. main-safe

业务层一个很重要的设计原则：

> 一个 `suspend` 函数如果允许从 Main 调用，就应该自己保证不会长时间阻塞 Main。

例如 Repository 内部使用阻塞文件 API：

```kotlin
suspend fun loadUser(): User =
    withContext(Dispatchers.IO) {
        blockingLoadUser()
    }
```

这样 ViewModel 只需要：

```kotlin
viewModelScope.launch {
    val user = repository.loadUser()
}
```

不需要知道 Repository 内部到底用了：

- 网络
- Room
- 文件
- 阻塞 API
- 哪个 Dispatcher

也就是说：

```text
ViewModel
→ 决定什么时候做

Repository
→ 决定具体怎么做
```

---

## 8. 结构化并发与异常传播

普通父子协程关系中：

```text
父协程
├── 子协程 A
└── 子协程 B
```

一个子协程发生异常时，通常会向上传播，并导致同一任务结构中的其他子协程被取消。

这种行为适合：

> 多个子任务共同构成一个整体操作，一个失败则整个操作失败。

---

## 9. supervisorScope / SupervisorJob

如果多个子任务属于同一范围，但不希望一个失败导致其他兄弟任务一起被取消，可以使用 supervision。

### supervisorScope

```kotlin
supervisorScope {
    launch { taskA() }
    launch { taskB() }
}
```

适合：

> 某一次局部操作中的失败隔离。

---

### SupervisorJob

```kotlin
CoroutineScope(
    SupervisorJob() + Dispatchers.Main
)
```

适合：

> 构造一个长期存在的、对子任务失败进行隔离的 Scope。

可以简单理解：

```text
coroutineScope
→ 同一个整体，兄弟任务容易互相影响

supervisorScope
→ 同属一组，但一个失败不会自动连坐兄弟
```

---

## 10. launch 与 async 的异常差异

### launch

`launch` 中未捕获的异常会作为协程异常向上传播 / 报告。

### async

`async` 会把异常保存在 `Deferred` 中。

```kotlin
val deferred = async {
    loadData()
}
```

真正：

```kotlin
deferred.await()
```

时会把异常重新抛出来。

因此：

> 如果根本不准备 `await()` 一个结果，通常就不应该使用 `async`。

没有返回值需求时，更适合：

```kotlin
launch
```

---

## 11. 取消不是普通失败

Kotlin 协程取消通常通过：

```text
CancellationException
```

传播。

这和 C# 中：

```text
OperationCanceledException
TaskCanceledException
```

思路非常接近。

因此不要把取消误当成业务错误：

```kotlin
try {
    repository.loadData()
} catch (e: CancellationException) {
    throw e
} catch (e: Exception) {
    uiState = UiState.Error
}
```

原则：

```text
CancellationException
→ 取消信号
→ 一般继续抛出

普通 Exception
→ 业务失败
→ 可以转换成 UI Error
```

协程取消也是**协作式取消**，不是强制杀线程。

# Flow

## 12. Flow：持续的异步结果

可以先这样区分：

```text
suspend
→ 一次异步结果

Flow
→ 一串随时间持续到来的异步结果
```

例如：

```kotlin
fun observeUsers(): Flow<List<User>>
```

可能持续产生：

```text
[A]

[A, B]

[A, B, C]
```

接收数据：

```kotlin
flow.collect { value ->
    ...
}
```

`collect` 本身是挂起操作。

---

## 13. Cold Flow

普通 `Flow` 默认是 cold。

含义：

> 创建 Flow 本身不会开始执行；只有出现 collector 时，上游生产逻辑才真正开始。

例如：

```kotlin
val numbers = flow {
    emit(1)
    emit(2)
}
```

这里只是创建了一份“如何产生数据”的描述。

直到：

```kotlin
numbers.collect { ... }
```

才开始真正执行。

而且不同 collector 通常会分别重新执行一次上游逻辑：

```text
Collector A
→ Flow 执行 A

Collector B
→ Flow 执行 B
```

因此两次订阅之间，外部数据源可能已经变化。

---

## 14. StateFlow

`StateFlow` 是 hot flow。

它可以理解为：

> 一个支持多人订阅的响应式变量。

例如：

```kotlin
val count = MutableStateFlow(0)
```

它始终保存一个当前值：

```text
current = 0
```

之后：

```kotlin
count.value = 1
```

所有正在订阅的人都能收到 `1`。

新的订阅者加入时，也会立刻拿到**当前最新值**。

因此：

```text
StateFlow
→ 表示“现在是什么”
→ 永远有当前状态
```

---

## 15. SharedFlow

`SharedFlow` 同样是 hot flow，也支持多个订阅者。

但它更像：

> 一个广播频道。

例如：

```kotlin
val events = MutableSharedFlow<UiEvent>()

events.emit(UiEvent.Saved)
```

正在订阅的多个 collector 都可以收到该事件。

它不是“某个人收到后把事件 Pop 掉”。

默认情况下，一个事件发出后就不再作为“当前值”长期保存。

因此：

```text
SharedFlow
→ 表示“刚刚发生了什么”
```

---

## 16. replay

`SharedFlow` 可以配置：

```kotlin
MutableSharedFlow<Event>(
    replay = 2
)
```

表示保存最近两条事件，用于给后来加入的订阅者重放。

```text
曾经发出：

A
B
C

replay = 2

新订阅者
→ B
→ C
```

默认：

```text
replay = 0
```

时，更接近：

> 事件发出去，当时没人听就过去了。

---

## 17. StateFlow 与 SharedFlow 的真正区别

区别不是：

> 能不能多人订阅。

两者都可以。

真正区别是语义：

```text
StateFlow
→ State
→ 当前状态是什么

SharedFlow
→ Event / Stream
→ 发生了什么
```

### StateFlow

适合：

```text
当前页面状态
当前用户
当前加载状态
当前选中项
```

### SharedFlow

适合：

```text
保存成功
弹 Snackbar
一次导航通知
某次业务事件
```

---

## 18. 为什么不建议用 StateFlow 模拟事件

技术上可以：

```kotlin
val event = MutableStateFlow<UiEvent?>(null)
```

但会有两个问题。

### 问题 1：新订阅者会收到旧事件

```text
当前 StateFlow = Saved

UI 重建
→ 新 collector
→ 又收到 Saved
```

这样可能导致“保存成功”提示重复出现。

### 问题 2：相同值可能被合并

`StateFlow` 面向状态：

```text
状态还是 20℃
→ 没变化
```

所以相等值不会被当成新的状态变化。

但对于事件：

```text
Save
Save
```

明明可能是两次独立操作。

因此事件场景更适合 `SharedFlow`。

# 最终心智模型

整个目标 6 可以压缩成：

```text
一次异步结果
→ suspend

持续异步结果
→ Flow

当前共享状态
→ StateFlow

共享事件广播
→ SharedFlow
```

协程任务本身：

```text
viewModelScope
→ 管生命周期

launch
→ 启动不返回业务结果的任务

async + await
→ 并发执行并取得结果

withContext
→ 切换执行上下文

CancellationException
→ 取消信号，不当作普通失败
```

最后再记住一个最重要的原则：

> 协程不是为了“自动开后台线程”，而是为了让异步任务能够以结构化、可取消、可挂起的方式组织起来。

---

## 与已有经验的类比

如果有 C# / WPF / Reactive 编程经验，可以粗略这样对应：

```text
Kotlin suspend
≈ C# async 方法的一次异步结果

Deferred<T>
≈ Task<T>

CancellationException
≈ OperationCanceledException / TaskCanceledException

Flow<T>
≈ IAsyncEnumerable<T> / 响应式数据流

StateFlow
≈ 可观察的“当前状态变量”

SharedFlow
≈ 多订阅者事件广播
```

这些只是帮助建立直觉，不代表 API 或运行机制完全等价。
