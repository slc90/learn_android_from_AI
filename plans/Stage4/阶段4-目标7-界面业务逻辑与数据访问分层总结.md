# Stage 4 · 目标 7：界面、业务逻辑与数据访问分层总结

## 目标

这一阶段的目标不是引入更多功能，而是把已经存在的 Todo 功能重新整理，让：

- UI 只负责显示状态和接收用户操作。
- ViewModel 负责界面状态和业务动作。
- Repository 负责数据访问。
- Retrofit / DTO / Request 等网络细节限制在数据层内部。
- 应用级依赖集中组装，而不是由各模块自行创建。

---

## 一、重构前的问题

最开始的调用链虽然已经有：

```text
MainActivity
    ↓
TodoViewModel
    ↓
TodoRepository
    ↓
Retrofit
```

但边界并不干净。

主要问题有：

- `TodoViewModel` 直接处理 `Response<T>`、HTTP 状态码。
- `TodoDto` 直接进入 `TodoUiState`。
- `CreateTodoRequest` 出现在 `TodoViewModel`。
- `TodoViewModel` 自己创建 `TodoRepository`。
- `TodoRepository` 自己直接访问 `RetrofitClient.todoApi`。
- Todo 的具体 UI 全部堆在 `MainActivity` 中。
- 依赖创建逻辑分散在各处。

---

## 二、引入应用内部模型 Todo

新增：

```text
model/Todo.kt
```

示例：

```kotlin
data class Todo(
    val userId: Int,
    val id: Int,
    val title: String,
    val completed: Boolean
)
```

这里要区分三个概念：

```text
TodoDto      = 网络返回的数据结构
Todo         = 应用内部的数据模型
TodoUiState  = 当前界面的状态
```

虽然 `TodoDto` 和 `Todo` 当前字段可能完全一样，但职责不同。

---

## 三、把 TodoDto 限制在数据层

Repository 负责把：

```text
TodoDto
   ↓
Todo
```

转换掉。

例如：

```kotlin
private fun TodoDto.toTodo(): Todo {
    return Todo(
        userId = userId,
        id = id,
        title = title,
        completed = completed
    )
}
```

这样 `TodoViewModel` 不再依赖：

```kotlin
TodoDto
Response<T>
HTTP 状态码
```

而只接触：

```kotlin
Todo
List<Todo>
```

---

## 四、CreateTodoRequest 也留在数据层

原先 ViewModel 中会创建：

```kotlin
CreateTodoRequest(...)
```

这依然属于网络协议细节。

重构后，ViewModel 只传应用能理解的参数：

```kotlin
repository.createTodo(
    userId = 1,
    title = "...",
    completed = false
)
```

由 Repository 内部创建：

```kotlin
CreateTodoRequest(...)
```

因此：

```text
ViewModel
    ↓ 普通业务参数
Repository
    ↓ CreateTodoRequest
TodoApiService
```

---

## 五、把 Todo UI 从 MainActivity 拆出来

新增：

```text
ui/todo/TodoScreen.kt
```

`TodoScreen` 不直接持有 `TodoViewModel`，而只接收：

```kotlin
TodoUiState
onLoadTodo
onCreateTodo
onLoadTodosByUser
```

例如：

```kotlin
@Composable
fun TodoScreen(
    uiState: TodoUiState,
    onLoadTodo: (Int) -> Unit,
    onCreateTodo: () -> Unit,
    onLoadTodosByUser: (Int) -> Unit,
    modifier: Modifier = Modifier
)
```

这样：

```text
TodoScreen
```

只知道：

- 当前状态是什么。
- 用户触发了什么操作。

它不知道：

- Retrofit。
- Repository。
- 网络协议。
- 数据到底从哪里来。

---

## 六、ViewModel 不再自己创建 Repository

原先：

```kotlin
private val repository = TodoRepository()
```

改为构造函数注入：

```kotlin
class TodoViewModel(
    private val repository: TodoRepository
) : ViewModel()
```

含义是：

> ViewModel 只声明“我需要一个 Repository”，但不负责创建它。

这就是最基础的依赖注入。

---

## 七、Repository 接口与具体实现分离

把 Repository 拆成：

```text
TodoRepository           ← 接口
NetworkTodoRepository    ← 网络实现
```

接口：

```kotlin
interface TodoRepository {
    suspend fun getTodo(id: Int): Todo

    suspend fun createTodo(
        userId: Int,
        title: String,
        completed: Boolean
    ): Todo

    suspend fun getTodosByUser(
        userId: Int
    ): List<Todo>
}
```

实现：

```kotlin
class NetworkTodoRepository(
    private val api: TodoApiService
) : TodoRepository
```

这样 `TodoViewModel` 只依赖：

```text
TodoRepository
```

而不依赖具体实现。

未来可以替换为：

```text
NetworkTodoRepository
FakeTodoRepository
CachedTodoRepository
RoomTodoRepository
```

而 ViewModel 不需要修改。

---

## 八、TodoApiService 也通过构造函数传入

原先 `NetworkTodoRepository` 内部直接使用：

```kotlin
RetrofitClient.todoApi
```

重构后：

```kotlin
class NetworkTodoRepository(
    private val api: TodoApiService
)
```

内部只调用：

```kotlin
api.getTodo(...)
api.createTodo(...)
api.getTodosByUser(...)
```

因此 Repository 只知道：

> 我有一个可以访问 Todo API 的对象。

而不知道这个对象是如何创建出来的。

---

## 九、用 AppContainer 集中组装依赖

新增：

```text
AppContainer.kt
```

示例：

```kotlin
class AppContainer {

    val todoRepository: TodoRepository =
        NetworkTodoRepository(
            RetrofitClient.todoApi
        )
}
```

它的职责是：

> 决定具体实现如何组合。

也就是所谓的依赖组装点。

---

## 十、让 AppContainer 跟随 Application 生命周期

新增：

```text
LearnAndroidApplication.kt
```

```kotlin
class LearnAndroidApplication : Application() {

    val appContainer by lazy {
        AppContainer()
    }
}
```

并在 `AndroidManifest.xml` 的 `<application>` 中加入：

```xml
android:name=".LearnAndroidApplication"
```

这样依赖关系的生命周期大致变成：

```text
Application
    ↓
AppContainer
    ↓
Repository
    ↓
ViewModel
    ↓
Screen
```

`AppContainer` 属于整个应用，而不是某个 Activity。

---

## 十一、ViewModelFactory 的作用

因为 `TodoViewModel` 不再是无参构造：

```kotlin
TodoViewModel(repository)
```

Android 默认无法直接创建它，因此需要：

```text
TodoViewModelFactory
```

由 Factory 负责：

```text
Android 要 TodoViewModel
        ↓
Factory
        ↓
TodoViewModel(repository)
```

它本质上只是负责把依赖传进去。

## 十三、最终依赖方向

可以把整条链路理解为：

```text
LearnAndroidApplication
        ↓
   AppContainer
        ↓
NetworkTodoRepository
        ↑
 TodoRepository
        ↓
   TodoViewModel
        ↓
   TodoUiState
        ↓
   TodoScreen
```

网络侧：

```text
TodoApiService
CreateTodoRequest
TodoDto
        ↓
NetworkTodoRepository
        ↓
Todo
```

UI 侧：

```text
Todo
   ↓
TodoViewModel
   ↓
TodoUiState
   ↓
TodoScreen
```

## 十四、这一阶段真正掌握的东西

这次重构最重要的不是“多建了几个文件”，而是把职责真正拆开：

- UI 不直接访问数据源。
- ViewModel 不处理 Retrofit / HTTP / DTO。
- Repository 不知道 UI。
- 网络 DTO 不直接进入 UI。
- ViewModel 不自己创建 Repository。
- Repository 不自己决定 API 从哪里来。
- 具体实现集中在 AppContainer 中组装。

可以把原则压缩成一句话：

> 每一层只知道自己需要知道的东西，具体实现尽量留在边界之外。

---

## 十五、和 WPF / MVVM 的对应关系

这套结构已经很接近熟悉的 MVVM：

```text
WPF                     Android / Compose

View                    TodoScreen
ViewModel               TodoViewModel
Model                   Todo
Service / Repository    TodoRepository
数据源                   Retrofit / Room
App                     Application
```

Compose 和传统 WPF 最大的感觉差异之一是：

```text
UiState
   ↓
Composable
   ↓
用户事件
   ↓
ViewModel
```

也就是：

> 状态向下流，事件向上走。
