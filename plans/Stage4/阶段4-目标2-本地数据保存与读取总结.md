# Stage 4 目标 2 总结：保存并读取应用本地数据

## 这一目标要解决什么

目标 1 建立了应用中的数据流动模型：

```text
数据源 → Repository / 数据访问层 → ViewModel → UI State → Compose
```

目标 2 开始真正引入“本地数据源”。

这一目标主要解决：

- App 关闭甚至进程被杀死后，数据怎样继续存在；
- 少量配置数据怎样保存；
- 普通文件怎样保存和读取；
- 本地持久化数据怎样重新进入 ViewModel 和 UI。

---

## 1. 内存状态和持久化数据不是一回事

例如：

```kotlin
var showStudyTip = false
```

如果它只存在于内存中：

```text
App 运行
  ↓
showStudyTip = false
  ↓
进程死亡
  ↓
数据消失
```

如果把它写入设备存储：

```text
App
 ↓
写入本地存储
 ↓
进程死亡
 ↓
重新启动
 ↓
再次读取
 ↓
仍然得到原来的值
```

这就是持久化。

---

## 2. 本目标接触的两种本地存储

我们实际练习了两种方式：

```text
本地数据
   │
   ├─ 少量设置、小状态
   │       ↓
   │   Preferences DataStore
   │
   └─ 一份真正的文件
           ↓
      App 专属文件
```

例如：

```text
showStudyTip = false
```

适合 DataStore。

而：

```text
study_note.txt
```

这种完整文件，更适合直接使用文件 API。

大量结构化记录暂时不属于目标 2：

```text
Todo 1
Todo 2
Todo 3
...
```

这类数据会在目标 3 使用 Room 数据库处理。

---

## 3. Preferences DataStore

我们创建了：

```kotlin
val Context.dataStore: DataStore<Preferences> by preferencesDataStore(
    name = "settings"
)
```

这里：

```text
dataStore
```

是 Kotlin 中扩展属性的名字。

而：

```text
settings
```

是这一份 DataStore 的持久化存储名称。

最终设备上可以看到类似：

```text
/data/user/0/com.example.learnandroidfromai/files/datastore/
    settings.preferences_pb
```

其中：

```text
settings
        ↓
settings.preferences_pb
```

Preferences DataStore 底层保存的不是普通文本，而是 protobuf 格式的数据。

---

## 4. Preferences 是什么

`Preferences` 可以理解成：

> 一份类型安全的键值数据集合。

例如：

```text
Preferences
├─ show_study_tip → false
├─ font_size      → 18
└─ user_name      → "abc"
```

因此：

```kotlin
DataStore<Preferences>
```

可以理解成：

> 这份 DataStore 保存的是一整组 Preferences 数据。

---

## 5. Preferences 的 Key

Preferences 的 key 不是普通字符串。

例如：

```kotlin
private val SHOW_STUDY_TIP =
    booleanPreferencesKey("show_study_tip")
```

这里：

```text
"show_study_tip"
```

只是 key 的名字。

而：

```kotlin
SHOW_STUDY_TIP
```

实际上是：

```kotlin
Preferences.Key<Boolean>
```

它同时表达：

```text
名字：show_study_tip
类型：Boolean
```

所以读写时使用：

```kotlin
preferences[SHOW_STUDY_TIP]
```

而不是：

```kotlin
preferences["show_study_tip"]
```

类似地：

```kotlin
stringPreferencesKey("user_name")
intPreferencesKey("font_size")
booleanPreferencesKey("show_study_tip")
```

可以创建不同类型的 Key。

---

## 6. DataStore 写入

我们使用：

```kotlin
suspend fun setShowStudyTip(value: Boolean) {
    context.dataStore.edit { preferences ->
        preferences[SHOW_STUDY_TIP] = value
    }
}
```

数据流向：

```text
Boolean
   ↓
DataStore.edit
   ↓
Preferences
   ↓
settings.preferences_pb
```

例如：

```kotlin
setShowStudyTip(false)
```

最终保存：

```text
show_study_tip = false
```

---

## 7. DataStore 读取

DataStore 的：

```kotlin
context.dataStore.data
```

返回的是：

```kotlin
Flow<Preferences>
```

也就是说，它不是“读取一次就结束”，而是一条持续的数据流。

我们再通过：

```kotlin
val showStudyTip: Flow<Boolean> =
    context.dataStore.data.map { preferences ->
        preferences[SHOW_STUDY_TIP] ?: true
    }
```

把：

```text
Flow<Preferences>
```

转换成：

```text
Flow<Boolean>
```

其中：

```kotlin
?: true
```

表示：

```text
已经保存过
    ↓
使用保存值

从未保存过
    ↓
默认 true
```

---

## 8. DataStore → ViewModel → Compose

ViewModel 中持续收集：

```kotlin
settingsDataStore.showStudyTip.collect { value ->
    _uiState.update { oldState ->
        oldState.copy(
            showStudyTip = value
        )
    }
}
```

于是：

```text
DataStore
   ↓
Flow<Boolean>
   ↓
collect
   ↓
ViewModel
   ↓
UI State
   ↓
Compose
```

Compose 中：

```kotlin
Switch(
    checked = settingsUiState.showStudyTip,
    onCheckedChange = settingsViewModel::setShowStudyTip
)
```

形成完整循环：

```text
DataStore
   ↓
Flow
   ↓
ViewModel
   ↓
UI State
   ↓
Switch
   │
   │ 用户操作
   ↓
ViewModel
   ↓
DataStore
```

---

## 9. 为什么写 DataStore 后不用手动修改 UI State

我们保存时只做：

```kotlin
settingsDataStore.setShowStudyTip(value)
```

没有同时：

```kotlin
_uiState.update { ... }
```

仍然可以更新 UI。

原因是：

```text
DataStore 写入新值
        ↓
DataStore 的 Flow 发出新数据
        ↓
ViewModel collect 收到
        ↓
_uiState 更新
        ↓
Compose 重组
```

所以 UI State 的数据来源仍然保持统一：

```text
DataStore → Flow → ViewModel
```

而不是同时存在两套状态更新路径。

## 10. 验证 DataStore 持久化

实践中进行了：

```text
Switch 设为 false
        ↓
停止 App
        ↓
进程结束
        ↓
重新运行 App
        ↓
Switch 仍然为 false
```

这证明：

```text
showStudyTip
```

已经不是只存在 ViewModel 或 Compose 内存中的状态，而是真正保存到了设备存储。

也通过 Device Explorer 找到了：

```text
files/datastore/settings.preferences_pb
```

## 11. App 专属普通文件

除了 DataStore，我们还练习了直接保存文件。

例如：

```kotlin
private val file = File(
    context.filesDir,
    "study_note.txt"
)
```

其中：

```kotlin
context.filesDir
```

对应 App 自己的内部文件目录，例如：

```text
/data/user/0/com.example.learnandroidfromai/files/
```

因此最终文件是：

```text
/data/user/0/com.example.learnandroidfromai/files/study_note.txt
```

这是应用自己的私有文件。

---

## 12. 普通文件写入和读取

写入：

```kotlin
file.writeText(text)
```

读取：

```kotlin
file.readText()
```

例如保存：

```text
今天学习 Android 文件读写
```

文件中就真正保存普通文本：

```text
今天学习 Android 文件读写
```

和 DataStore 的：

```text
settings.preferences_pb
```

不同，`study_note.txt` 可以直接作为普通文本查看。

---

## 13. 文件 I/O 不应该直接堵塞主线程

文件读写属于 I/O 操作。

因此我们使用：

```kotlin
suspend fun save(text: String) {
    withContext(Dispatchers.IO) {
        file.writeText(text)
    }
}
```

以及：

```kotlin
suspend fun read(): String {
    return withContext(Dispatchers.IO) {
        if (file.exists()) {
            file.readText()
        } else {
            ""
        }
    }
}
```

这里：

```kotlin
suspend
```

表示函数可以挂起。

真正把文件工作切到适合 I/O 的线程执行的是：

```kotlin
withContext(Dispatchers.IO)
```

可以理解成：

```text
ViewModel 协程
     ↓
Dispatchers.IO
     ↓
磁盘文件读写
     ↓
完成后返回结果
```

---

## 14. 普通文件和 DataStore 的重要区别

普通文件默认不会提供：

```kotlin
Flow<String>
```

因此写入文件后：

```text
文件内容变了
```

并不意味着：

```text
ViewModel 自动知道了
```

例如：

```text
保存文件
   ↓
study_note.txt 已更新
   ↓
UI 不会自动变化
```

需要显式读取：

```text
点击读取
   ↓
fileStore.read()
   ↓
得到 String
   ↓
更新 UI State
   ↓
Compose 重组
```

---

## 15. 保存后怎样立即刷新 UI

如果保存成功后已经知道保存的内容：

```kotlin
fun save() {
    viewModelScope.launch {
        val text = _uiState.value.inputText

        fileStore.save(text)

        _uiState.update {
            it.copy(savedText = text)
        }
    }
}
```

没有必要一定再次从文件读取。

流程：

```text
输入内容
   ↓
保存成功
   ↓
直接更新 UI State
   ↓
Compose 重组
```

如果保存过程中还会对数据进行转换，才可能有必要重新读取最终结果。

---

## 16. 普通 File 能不能做成 Flow

可以。

例如自己维护：

```kotlin
private val _text = MutableStateFlow("")
val text = _text.asStateFlow()
```

写入之后：

```kotlin
file.writeText(text)
_text.value = text
```

于是也可以形成：

```text
保存文件
   ↓
更新 StateFlow
   ↓
ViewModel collect
   ↓
UI 自动更新
```

但这里需要注意：

> 这个 Flow 观察的是我们自己管理的状态，并不是文件系统天然提供的 Flow。

如果有人绕过这个类直接修改磁盘文件：

```text
study_note.txt 被外部修改
```

`MutableStateFlow` 本身并不会自动知道。

如果真正需要观察文件系统变化，可以进一步使用：

```text
FileObserver
    ↓
callbackFlow
    ↓
Flow
```

这属于更深入的文件监听机制，目前不需要展开。

---

## 17. DataStore 和普通文件的区别

可以先形成这个心智模型：

```text
Preferences DataStore
─────────────────────
适合：
少量设置、小状态

例子：
showStudyTip
fontSize
userName

特点：
键值形式
自带 Flow
负责持久化格式
适合响应式数据流
```

而：

```text
普通应用专属文件
─────────────────────
适合：
真正具有“文件”含义的数据

例子：
study_note.txt
config.json
缓存文件

特点：
内容格式自己决定
主动读写
默认没有 Flow
可以直接操作文件
```

---

## 18. DataStore 不只有 Preferences

DataStore 本身是：

```kotlin
DataStore<T>
```

我们当前使用的是：

```kotlin
DataStore<Preferences>
```

也就是 Preferences DataStore。

还可以存在：

```text
DataStore<自定义类型>
```

例如 Proto DataStore。

所以：

```text
DataStore
   │
   ├─ Preferences DataStore
   │      ↓
   │   key-value
   │
   └─ 类型化 DataStore
          ↓
       自定义数据结构
```

目标 2 只需要掌握 Preferences DataStore 即可，Proto DataStore 暂时不深入。

---

## 19. 目标 2 最终留下的心智模型

本地持久化首先要判断：

```text
我要保存什么？
      │
      ├─ 少量设置、小状态
      │       ↓
      │    DataStore
      │
      ├─ 一份真正的文件
      │       ↓
      │    File
      │
      └─ 大量结构化记录
              ↓
            Room
          （目标 3）
```

其中 DataStore 的典型数据流：

```text
磁盘
 ↓
DataStore
 ↓
Flow
 ↓
ViewModel
 ↓
UI State
 ↓
Compose
```

普通文件则更像：

```text
磁盘文件
   ↑ ↓
FileStore
   ↑ ↓
ViewModel
   ↑ ↓
Compose
```

普通文件默认不会主动通知上层变化。

---

## 20. 现在需要记住的几件事

1. **ViewModel 状态和磁盘持久化不是一回事。**
2. **DataStore 适合少量配置、小状态，并天然提供 Flow。**
3. **普通 File 适合真正的文件内容，默认需要主动读写。**
4. **文件 I/O 不应该直接长时间阻塞主线程。**
5. **大量结构化数据不应该硬塞进 DataStore 或文本文件，下一目标交给 Room。**
