# 阶段 1 - 目标 3：完成项目的构建与运行

## 目标

能够理解并完成 Android 项目的基本构建与运行流程：

```text
源码 / 资源 / Manifest / Gradle 配置
                ↓
              Build
                ↓
              APK
                ↓
              adb
                ↓
          安装到模拟器
                ↓
          启动 MainActivity
                ↓
             App 运行
```

---

## 1. Build 是什么

Build 的作用不是单纯“编译 Kotlin”，而是把项目中的代码、资源、Manifest、依赖和构建配置等内容加工成可以安装的 Android 应用。

构建过程由 Gradle 组织，并拆分为许多 Task。

例如：

```text
:app:processDebugResources
:app:dexBuilderDebug
:app:mergeProjectDexDebug
:app:packageDebug
:app:assembleDebug
```

可以暂时理解为：

```text
项目内容
   ↓
多个 Gradle Task
   ↓
处理代码 / 资源 / 打包
   ↓
得到 APK
```

构建日志中可能出现：

```text
30 up-to-date
```

表示 Gradle 判断这些 Task 的输入没有变化，可以直接复用之前的结果，不需要重新执行。

---

## 2. Build 的产物

Debug 构建完成后，可以在：

```text
app/
└─ build/
   └─ outputs/
      └─ apk/
         └─ debug/
            ├─ app-debug.apk
            └─ output-metadata.json
```

找到构建结果。

`app-debug.apk` 是真正可以安装到 Android 设备上的应用文件。

`output-metadata.json` 则是描述构建产物的元信息，例如 APK 文件名、版本、构建类型等。它主要供 Android Gradle Plugin、Android Studio 等构建工具使用，不是安装包本身。

可以粗略理解为：

```text
app/src/
→ 自己维护的源码和资源

app/build/
→ Gradle 构建过程中生成的中间文件和最终产物
```

一般不手工修改 `build/` 中的内容。

---

## 3. Run 是什么

Run 不只是“启动程序”。

大致过程是：

```text
检查 / 构建应用
      ↓
得到可部署的应用
      ↓
安装 / 更新到目标设备
      ↓
启动应用入口
```

因此：

```text
Build
→ 把应用做出来

Run
→ 把应用部署并跑起来
```

---

## 4. 应用启动入口

项目的 `AndroidManifest.xml` 中：

```xml
<activity
    android:name=".MainActivity">

    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>

</activity>
```

这里：

```xml
android:name=".MainActivity"
```

表示这个 `<activity>` 对应 `MainActivity` 类。

而：

```text
android.intent.action.MAIN
android.intent.category.LAUNCHER
```

不是对 `MainActivity` 的引用，而是 `intent-filter` 中的两个字符串标识。

它们因为写在 `<activity>` 内部，所以属于这个 Activity：

```text
MainActivity
└─ intent-filter
   ├─ action = MAIN
   └─ category = LAUNCHER
```

Android 因此知道这个 Activity 可以作为应用的启动入口。

---

## 5. adb

`adb` 是 Android Debug Bridge。

可以先理解成：

> Android Studio 与模拟器 / 真机之间的控制通道。

整体关系：

```text
Android Studio
      ↓
     adb
      ↓
模拟器 / 真机
```

Run 时 Android Studio 会通过 adb 完成部署、启动等操作。

例如：

```text
adb shell am start ...
```

表示通过 adb 在 Android 设备内部执行命令，让 Android 系统启动 Activity。

Run 输出中的：

```text
android.intent.action.MAIN
android.intent.category.LAUNCHER
```

正好和 Manifest 中声明的启动规则对应。

---

## 6. Build / Run / Debug

三者可以这样区分：

```text
Build
→ 把应用构建出来

Run
→ 构建 / 部署并运行应用

Debug
→ 运行应用，并连接调试器
```

Debug 模式下可以进一步使用：

- 断点
- 查看变量
- 单步执行

这些内容放到后面的调试目标继续学习。

---

## 7. 两种不同含义的 Debug

Android Studio 中有两个容易混淆的 Debug。

例如：

```text
app-debug.apk
```

这里的 Debug 表示一种 **Build Type（构建类型）**。

而点击 Debug 按钮时，表示：

```text
启动应用
+
连接调试器
```

所以这是两个不同维度：

```text
构建类型
├─ debug
└─ release

启动方式
├─ Run
└─ Debugger
```

是否能够连接调试器，主要取决于这个构建是否允许调试。

概念上可以理解为：

```text
debuggable = true
→ 可以连接调试器

debuggable = false
→ 通常不能连接调试器
```

因此 Release 构建理论上也可以配置成可调试，但正式发布版本通常不会这样做。

## 8. Run Configuration

Android Studio 顶部显示的：

```text
app
```

通常是一个 **Run Configuration** 的名字。

在 Run/Debug Configurations 中可以看到：

```text
Name: app

Module:
learn_android_from_AI.app
```

这两者不是一回事。

`Name` 只是 Run Configuration 的显示名称，可以随意修改，例如：

```text
app
test-run
local-debug
```

`Module` 才真正指定这次运行哪个 Android 模块。

因此：

```text
Run Configuration Name ≠ Module
```

默认情况下两者看起来都叫 `app`，只是 Android Studio 自动生成的配置刚好这样命名。

## 9. 运行时需要确定的几个东西

运行一个 Android App 时，Android Studio 至少需要知道：

```text
运行哪个模块？
→ app

使用哪个构建变体？
→ debug

运行到哪个设备？
→ Medium Phone
```

然后才进入：

```text
构建
↓
部署
↓
启动
```

## 10. Build Type

在 `app/build.gradle.kts` 中：

```kotlin
android {
    buildTypes {
        release {
            optimization {
                enable = false
            }
        }
    }
}
```

`buildTypes` 用来配置不同的构建类型。

Android Gradle Plugin 默认提供：

```text
debug
release
```

即使没有显式写：

```kotlin
debug {
}
```

Debug Build Type 仍然存在。

当前项目中的：

```kotlin
optimization {
    enable = false
}
```

表示当前 Release 配置关闭了这项构建优化。

可以先这样理解 `defaultConfig` 与 `buildTypes`：

```text
android { ... }

├─ defaultConfig
│  └─ 不同构建类型共享的基础配置
│
└─ buildTypes
   └─ 不同构建类型之间的差异
```

---

## 11. Debug 与 Release

两者目标不同：

```text
Debug
→ 面向开发和调试

Release
→ 面向最终交付和发布
```

Debug 通常更强调：

- 开发方便
- 可连接调试器
- 构建速度

Release 通常更强调：

- 正式签名
- 优化
- 更接近最终用户拿到的 App
- 默认不允许调试

---

## 12. APK 签名

Android APK 需要签名。

Debug 构建时，Android Studio / Android 构建工具通常会自动使用 Debug Key，因此开发时几乎感觉不到这个过程。

可以先理解成：

```text
Debug APK
→ 自动使用 Debug Key 签名
→ 方便直接安装和运行

Release APK
→ 正式发布时使用自己的正式签名
```

签名的具体机制以后再展开。

---

## 13. Build Variants

Android Studio 的 `Build Variants` 窗口可以选择某个模块当前使用的构建变体。

当前项目是：

```text
Module    Active Build Variant

app       debug (default)
```

可以切换：

```text
debug
release
```

如果项目存在多个模块，每个模块可以分别选择自己的 Active Build Variant。

不过前提是对应模块本身定义出了相应的构建变体。

---

## 14. 可以自定义 Build Type

Build Type 不局限于：

```text
debug
release
```

也可以自行定义，例如：

```kotlin
android {
    buildTypes {
        debug {
        }

        create("staging") {
        }

        release {
        }
    }
}
```

这样就可以出现：

```text
debug
staging
release
```

例如：

```text
Debug
→ 日常开发

Staging
→ 内部测试 / QA

Release
→ 正式发布
```

具体如何配置这些类型，后面学习 Gradle 时再展开。

```text
Android 项目
│
├─ Module
│   └─ app
│
├─ Build Type / Variant
│   ├─ debug
│   ├─ release
│   └─ 也可以自定义
│
├─ Gradle Build
│   └─ 多个 Task
│
├─ APK
│   └─ app-debug.apk
│

│
└─ Android 系统
    └─ 根据 Manifest 启动 MainActivity
```

需要分清：

```text
Build ≠ Run ≠ Debug

Build Type ≠ Debugger

Run Configuration Name ≠ Module

源码目录 src ≠ 构建目录 build
```
