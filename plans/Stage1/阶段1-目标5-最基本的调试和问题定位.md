# 阶段 1 - 目标 5：最基本的调试和问题定位

## 目标

能够使用 Android Studio 和 Android 提供的基础诊断工具，对常见问题进行最基本的定位。

重点不是记住所有调试功能，而是知道：

- 程序崩溃时先看什么。
- 程序没崩但结果不对时怎么观察现场。
- 程序卡住时怎么判断主线程在做什么。
- 已经运行起来的 App 如何临时附加 Debugger。

---

## 1. Logcat 是什么

Logcat 不是某个日志库，而是 Android 的系统日志查看机制。

Android Studio 里的 Logcat 只是一个图形化前端；命令行也可以通过：

```bash
adb logcat
```

查看同一套 Android 系统日志。

应用代码里常见的是：

```kotlin
import android.util.Log

Log.d("Stage1", "Greeting name = $name")
```

这里：

- `Log` 是 Android SDK 提供的日志 API。
- `"Stage1"` 是 Tag，用于分类和过滤。
- `"Greeting name = $name"` 是 Message。
- `d` 表示 Debug 级别。

只要其他日志库最终也把内容写入 Android 系统日志，Logcat 一样可以看到。

如果日志只写到文件、服务器等其他目标，Logcat 就看不到。

---

## 2. 一条 Logcat 日志的基本格式

示例：

```text
2026-09-20 10:46:56.286  5332-5332  Stage1  com.example.learnandroidfromai  D  Greeting name = Android
```

可以拆成：

```text
时间 | PID-TID | Tag | 包名/进程 | 级别 | Message
```

其中：

- `PID`：进程 ID。
- `TID`：线程 ID。
- `Tag`：由代码自己定义。
- `D`：Debug 日志级别。
- `Message`：日志正文。

常见日志级别：

```text
Log.v   VERBOSE
Log.d   DEBUG
Log.i   INFO
Log.w   WARN
Log.e   ERROR
```

Stage 1 阶段先简单理解：

```text
调试信息 -> Log.d
明显错误 -> Log.e
```

即可。

Logcat 不会为普通 `Log.d()` 自动补上函数名、文件名和行号。异常 stack trace 中出现这些信息，是另一套机制。

---

## 3. Logcat 过滤

Android 系统日志很多，因此过滤很重要。

例如：

```text
package:mine
```

只看当前 App。

```text
tag:Stage1
```

只看指定 Tag。

也可以组合：

```text
package:mine tag:Stage1
```

这样可以快速把系统和第三方日志排除掉。

---

## 4. 断点调试

Android Studio 的 Kotlin/Java 调试方式和常见 IDE 基本一致。

基本流程：

```text
设置断点
-> Debug 启动
-> 程序命中断点并暂停
-> 查看变量
-> 单步执行
```

常见单步操作：

```text
Step Over -> 执行当前行，停到下一行
Step Into -> 进入当前调用的函数
Step Out  -> 从当前函数返回到上一层
```

在变量窗口中看到的内容，本质上属于当前选中的 stack frame，而不是“整个线程的所有变量”。

---

## 5. 调用栈

调用栈回答的问题是：

> 程序是怎么一层一层运行到当前这里的？

例如：

```text
Android framework
    ↓
Compose
    ↓
Greeting()
    ↓
Thread.sleep()
```

实际排错时，经常需要沿调用栈找到第一层属于自己代码的 frame。

Android / Compose 的调用栈通常很长，不需要从头逐行研究系统内部实现。

---

## 6. 崩溃定位

故意抛出异常：

```kotlin
throw IllegalStateException("Stage1 debug test")
```

Logcat 中会出现类似：

```text
FATAL EXCEPTION: main
java.lang.IllegalStateException: Stage1 debug test
    at com.example.learnandroidfromai.MainActivityKt.Greeting(MainActivity.kt:35)
```

基础排查顺序：

```text
FATAL EXCEPTION
↓
异常类型和 Message
↓
找到自己代码的第一行
↓
点击文件名和行号直接跳转
```

Android Studio 会把 stack trace 中的源码位置做成可点击链接。

---

## 7. App 卡住时：暂停进程看线程

如果 App 没崩，但界面卡住，可以使用 Debugger 手动暂停整个 App 进程。

例如：

```kotlin
Thread.sleep(10000)
```

如果发生在主线程，暂停后可以看到：

```text
"main" ... : SLEEPING
```

线程列表中还会看到：

```text
RenderThread
FinalizerDaemon
ReferenceQueueDaemon
Profile Saver
...
```

这里显示的是当前 App 进程中的线程，不是整个 Android 系统中的全部线程。

线程状态如：

```text
RUNNING
WAIT
SLEEPING
```

表示 Debugger 冻结现场那一瞬间，这些线程原本所处的 JVM 状态。

手动 `Pause Program` 会暂停被调试 App 进程里的线程，但 Android 系统进程仍继续运行。

因此 App 被暂停太久，系统仍可能认为它不响应并触发 ANR。

---

## 8. 线程状态和调用栈的关系

仅看到：

```text
main : SLEEPING
```

只能知道“主线程正在睡眠”。

真正定位原因还要看调用栈：

```text
Thread.sleep(...)
↓
Greeting(...)
↓
Compose ...
```

这样才能知道是谁让主线程睡眠。

所以卡顿排查时可以先按这个顺序：

```text
看 main 线程状态
↓
看 main 的调用栈
↓
找到第一层自己的代码
```

如果 App 长时间卡住，可以：

```text
暂停 -> 看调用栈
继续
暂停 -> 再看
继续
暂停 -> 再看
```

如果每次都停在相同位置，就能更有把握地判断真正的阻塞点。

---

## 9. 某些线程为什么看不到 frame

有些线程选中后会显示：

```text
Frames are not available
```

例如部分 `RenderThread` 场景。

这通常意味着当前 Java/Kotlin Debugger 没有可展示的 Java/Kotlin stack frame。

有些执行过程发生在 native 层，普通 Java/Kotlin Debugger 只能知道线程存在和状态，拿不到完整 Kotlin/Java 调用栈。

右侧如果还残留之前的变量，不代表它们属于当前线程；它们可能仍然是上一次选中的 stack frame 的内容。

---

## 10. Attach debugger to Android process

除了直接用 Debug 启动 App，还可以给已经运行的 Android 进程附加 Debugger。

两种方式的区别：

```text
Debug
= 启动 App，并从一开始附加 Debugger

Attach
= App 已经在运行，现在才把 Debugger 接进去
```

Android 专用的 Attach 窗口应该能看到设备，例如：

```text
Emulator Medium_Phone Android 17
└─ com.example.learnandroidfromai
```

选择自己的包名后即可附加。

注意不要混淆 IDE 通用的 `Attach to Process...`；那个可能列出的是 Windows 本机上的 GradleDaemon、KotlinCompileDaemon 等 Java 进程，而不是模拟器里的 Android App。

## 11. ANR

ANR = Application Not Responding，应用无响应。

它和崩溃不同：

```text
崩溃
= 程序发生严重错误并结束

ANR
= 进程还活着，但长时间无法及时响应用户或系统
```

稳定复现输入超时 ANR 的实验：

```kotlin
Button(
    onClick = {
        Thread.sleep(20_000)
    }
) {
    Text("触发 ANR")
}
```

点击按钮后，主线程被阻塞，输入事件无法及时处理。

系统随后可能弹出：

```text
learn_android_from_AI isn't responding

Close app
Wait
```

这就是 Android 系统正式判定的 ANR。

---

## 12. ANR 的 Logcat 信息

ANR 日志中最关键的部分类似：

```text
ANR in com.example.learnandroidfromai
PID: 6359
Reason: Input dispatching timed out (...)
Parent: com.example.learnandroidfromai/.MainActivity
ErrorId: ...
Frozen: false
Load: ...
```

优先关注：

```text
ANR in ...
Reason: ...
```

例如：

```text
Reason: Input dispatching timed out
```

说明是输入分发超时。

`Frozen: false` 表示这个进程当时不是被 Android 的进程 freezer 冻结导致的不响应。

---

## 13. ANR 日志里的系统资源信息

ANR 日志还会记录系统当时的资源状态，用来判断：

> 是 App 自己卡住了，还是整个系统当时已经非常繁忙？

常见内容包括：

```text
/proc/pressure/memory
/proc/pressure/cpu
/proc/pressure/io
```

这些属于 Linux PSI（Pressure Stall Information），用于描述：

```text
memory pressure -> 内存资源是否紧张
cpu pressure    -> CPU 是否经常排队
io pressure     -> I/O 是否经常阻塞
```

还会看到：

```text
CPU usage from ...
```

以及各进程 CPU 用量。

例如：

```text
1.2% process_name: 0.4% user + 0.8% kernel
```

其中：

- `user`：用户态 CPU 消耗。
- `kernel`：内核态 CPU 消耗。

`faults: ... minor` 中的 `minor fault` 通常是虚拟内存正常的缺页/映射行为，并不等于程序发生了“错误”。

Stage 1 阶段看 ANR 日志时，优先级可以先记成：

```text
1. Reason
2. 主线程 stack trace
3. CPU / memory / IO 是否异常
```

---

## 14. Android 系统 freezer

Android 可以把某些后台进程暂时 freeze，以减少 CPU 和电量消耗。

可以简单理解：

```text
kill
= 进程结束

freeze
= 进程还在，但线程暂时不执行
```

之后系统可以再把它解冻继续运行。

ANR 日志中的：

```text
Frozen: false
```

表示当前 ANR 不是因为系统主动把这个进程 freeze 导致的。

---

## 15. 最基本的问题定位思路

有其他语言开发经验时，Android 这一阶段最需要新增的是 Android 自己的工具和运行环境。

可以保留这张最小排错图：

```text
构建失败
    ↓
看 Build Output / IDE 编译错误

运行后崩溃
    ↓
Logcat
    ↓
FATAL EXCEPTION
    ↓
stack trace

运行正常但结果不对
    ↓
日志 + 断点 + 变量

App 卡住 / 无响应
    ↓
暂停 App 进程
    ↓
看 main 线程
    ↓
看调用栈

系统正式判定不响应
    ↓
ANR
    ↓
看 Reason + 主线程栈 + 系统资源状态
```
